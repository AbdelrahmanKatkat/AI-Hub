Module 0 · Robot foundations

What a robot is, and the mathematics it needs before anything else: a robot senses, thinks and acts in a loop, every part of it has its own coordinate frame, and its motion lives in a space of joint values rather than in the room. By the end you can place a robot arm in space with a matrix, count how many ways it can reach a point, and say how fast its software loop must run.

What a robot is: sense, think, act

The questionA warehouse arm must pick a box from a conveyor and place it on a shelf. Which parts of that job are sensing, which are deciding and which are moving? And how do we describe the arm so that a program can move it to a point it has never been to before?

Intuition

Strip away the metal and every robot runs one loop, over and over:

  • Sense — read the world and the machine itself: joint encoders say how far each joint has turned, a camera or lidar says where the objects are.
  • Think — decide what to do next: estimate where things are, plan a path, compute the motor command that moves the arm closer to the goal.
  • Act — drive the motors (the actuators) so the machine changes its state, which the next sensing step then measures.

The loop is closed: the action changes what the next sense reports. That is why robotics is about feedback, and why a robot that thinks perfectly but senses badly fails in the real world.

There are two broad families. A manipulator is a chain of links joined by joints, fixed to a table or a floor, like an arm. A mobile robot moves through space on wheels or legs, like a delivery robot or a rover. Most of this module is about manipulators, because their geometry is the cleanest place to learn the ideas.

A joint is what lets two links move relative to each other. A revolute joint rotates, like a hinge; its value is an angle. A prismatic joint slides, like a telescope; its value is a length. The number of independent joint values needed to set the whole machine is its degrees of freedom (DOF). A planar arm with two hinges has 2 DOF: two numbers fix every pose it can take.

Build it up: one joint, one loop

Take the smallest possible control problem: one revolute joint that starts at \theta=0^\circ and must reach a target of 30^\circ. The simplest controller is proportional: command a speed that is proportional to the remaining error. The speed in degrees per second is K_p times the error, with K_p=5\ \text{s}^{-1}. The joint keeps that speed for one control period \Delta t, then the loop senses again.

The loop rate is the number of times per second that the sense–think–act cycle runs. A rate of 10 Hz means \Delta t=0.1\ \text{s}.

Worked example

Start at \theta=0^\circ, target 30^\circ, K_p=5\ \text{s}^{-1}. Each tick: error e=30^\circ-\theta, speed \omega=5e, new angle \theta\leftarrow\theta+\omega\,\Delta t.

At 10 Hz (\Delta t=0.1\ \text{s}):

  • tick 1: e=30^\circ, \omega=150^\circ/\text{s}, \theta=15.0^\circ
  • tick 2: e=15.0^\circ, \omega=75^\circ/\text{s}, \theta=22.5^\circ
  • tick 3: e=7.5^\circ, \omega=37.5^\circ/\text{s}, \theta=26.25^\circ

The error halves on every tick. At 100 Hz (\Delta t=0.01\ \text{s}) the first tick gives \theta=1.500^\circ, the second 2.925^\circ, the third 4.279^\circ: slower, but smooth. At 1 Hz (\Delta t=1\ \text{s}) the first tick jumps to 150^\circ, the second to -450^\circ, the third to 1950^\circ. The same controller with the same gain has run away.

The reason is one number. Each tick multiplies the error by (1-K_p\Delta t): at 10 Hz that is 1-0.5=0.5, at 100 Hz it is 0.95, at 1 Hz it is 1-5=-4. A factor of magnitude above 1 grows, and a negative one flips the sign every tick. The loop rate is not a detail; it decides whether the robot is stable at all.

The formal definition

\theta_{k+1}=\theta_k+K_p\,\Delta t\,(\theta^\star-\theta_k),\qquad e_{k+1}=(1-K_p\Delta t)\,e_k

The loop is stable (the error shrinks) when |1-K_p\Delta t|<1, which for positive gains means K_p\Delta t<2. This is a discrete-time stability condition; module 6 gives the continuous version.

Lab

Try this
  1. Start at 10 Hz and Kp = 5. Watch the joint settle in about four ticks, without overshoot.
  2. Drop the rate to 1 Hz. Notice that the joint overshoots, then runs away. Read the readout: Kp·Δt is 5 and the stability limit is 2.
  3. Raise the rate back to 200 Hz and turn on sensor noise (0.5°). The joint now jitters around the target: a fast loop cannot remove noise that the sensor puts in.
  4. Set Kp to 8 at 10 Hz and watch the joint ring. Then find the highest Kp that still settles at 10 Hz.
Common traps
  • A faster loop is not always better. A faster loop reacts sooner, but every tick needs compute and a sensor reading, and noise is not removed by sampling faster.
  • Degrees and radians. Trigonometric functions in code take radians. A joint command in degrees fed to sin() gives nonsense without any error message.
  • Joint DOF is not task DOF. A planar arm with three hinges has 3 DOF, but placing its tip needs only 2 numbers. The spare one is redundancy (lesson 0.4).
Pipeline view. Stage: control (with sensing in front). Loop rate: 10 Hz to 1 kHz depending on the joint. Stores: the current joint state and the last command.
Where it shows up in AI
  • Every embodied system runs this loop: industrial arms, delivery robots, drones and humanoids all close a feedback loop over sensed state.
  • Learned robot policies (module 7) are one more "think" step: they map what the robot senses to what it should do next, and they run inside the same loop with the same timing limits.

Check yourself

1. A gripper jaw slides along a rail. Is that joint revolute or prismatic, and what is its value?
Prismatic. It slides rather than turns, so its value is a length (metres), not an angle.
2. A planar arm has three revolute joints and its tip is placed in the plane. How many DOF does the arm have, and how many does the task need?
The arm has 3 DOF. Placing the tip in a plane needs 2 numbers, so there is 1 spare degree of freedom.
3. Kp = 4 per second and the loop runs at 10 Hz. Is it stable? By what factor does the error shrink each tick?
Kp·Δt = 4 × 0.1 = 0.4, which is below 2, so it is stable. Each tick multiplies the error by 1 − 0.4 = 0.6.

Takeaways

  • A robot is a closed loop: sense, think, act, then sense what the action changed.
  • Revolute joints give angles, prismatic joints give lengths; DOF counts the independent joint values.
  • For a proportional loop, the error is multiplied by (1 − Kp·Δt) each tick: the loop rate decides stability, so Kp·Δt must stay below 2.

Coordinate frames & homogeneous transforms

The questionA camera on the arm's wrist sees a mug 0.30 m in front of its lens. The gripper must close on that mug, but the arm is controlled in its own base frame. How do we turn "the mug is at a point in the camera" into "the mug is at a point in the base", and how do we chain that with the arm's own motion?

Intuition

A point has no coordinates on its own; it has coordinates in some frame. A frame is a coordinate system with an origin and two (in 2-D) or three (in 3-D) axes. The camera has a frame, the gripper has a frame, the table has a frame, and the robot base has a frame. Each link of an arm carries its own frame, which moves with the link.

Converting a point from one frame to another takes two operations, in this order: rotate the point by how the two frames are turned relative to each other, then move it by where the second frame's origin sits. Think of a ruler lying on a table: first you turn it, then you slide it.

Doing this with two separate operations for every link would be painful. A trick fixes it: write each point with one extra coordinate equal to 1 (its homogeneous form), and pack the rotation and the translation into one 3×3 matrix (in 2-D) or 4×4 matrix (in 3-D). Then converting frames is a single matrix multiplication, and chaining frames is multiplying matrices.

Build it up: one frame in 2-D

Start with a rotation alone. Turning a frame counter-clockwise by an angle \alpha is the matrix R(\alpha)=\begin{bmatrix}\cos\alpha&-\sin\alpha\\\sin\alpha&\cos\alpha\end{bmatrix}. Its columns are the new x and y axes, written in the old frame. The rotated point is R\,\mathbf p. Adding the origin of frame B, \mathbf t, gives \mathbf p^{A}=R\,\mathbf p^{B}+\mathbf t: rotate, then move.

To make it one matrix, append a 1: \begin{bmatrix}\mathbf p^A\\1\end{bmatrix}=\begin{bmatrix}R&\mathbf t\\0\,0&1\end{bmatrix}\begin{bmatrix}\mathbf p^B\\1\end{bmatrix}. The matrix on the left is the transform T_B^A. The bottom row (0, 0, 1) keeps the 1 at 1, which is why the trick works.

Worked example

Frame B is rotated 30^\circ relative to the base frame A, and its origin sits at (2,\,1) m in A. So

T_B^A=\begin{bmatrix}0.866&-0.500&2\\0.500&0.866&1\\0&0&1\end{bmatrix}

A point at (1,0) m in frame B (one metre along B's x axis) is \begin{bmatrix}0.866\cdot1-0.500\cdot0+2\\0.500\cdot1+0.866\cdot0+1\\1\end{bmatrix}=\begin{bmatrix}2.866\\1.500\\1\end{bmatrix} in A. In words: the point is 2.866 m right and 1.500 m up from the base.

Now go back. The inverse matrix is T_A^B=\begin{bmatrix}R^\top&-R^\top\mathbf t\\0&1\end{bmatrix}=\begin{bmatrix}0.866&0.500&-2.232\\-0.500&0.866&0.134\\0&0&1\end{bmatrix}. Applying it to (2.866,1.500) returns (1.000,0.000), the original point in B.

Chaining is multiplication. Suppose link 2 is attached to the end of link 1 (frame B), and frame C is rotated another 45^\circ relative to B and sits 1 m along B's x axis. Then T_C^A=T_B^A\,T_C^B, where T_C^B is the rotation by 45° with translation (1, 0). Multiplying gives a rotation of 30^\circ+45^\circ=75^\circ and an origin at (2.866,\,1.500): the last column is where frame C's origin sits in A. The order matters: a rotation then a move is not the same as a move then a rotation (see the traps).

The formal definition

\mathbf p^{A}=R_B^A\,\mathbf p^{B}+\mathbf t_B^A,\qquad T_B^A=\begin{bmatrix}R_B^A&\mathbf t_B^A\\\mathbf 0^\top&1\end{bmatrix},\qquad T_A^C=T_A^B\,T_B^C,\qquad (T_B^A)^{-1}=\begin{bmatrix}R^\top&-R^\top\mathbf t\\\mathbf 0^\top&1\end{bmatrix}

In 3-D the same form holds with a 3×3 rotation R and a 4×4 transform. The inverse is cheap because R^{-1}=R^\top for any rotation matrix: its columns are orthonormal.

Lab

Try this
  1. Set a₁ = 30° and a₂ = 0°, then compare the readout with the worked example: T₀¹ is a rotation by 30° and the gripper point moves with it.
  2. Set a₂ = 45°. The second frame rotates relative to the first, so the total rotation of the gripper frame is a₁ + a₂ = 75°. Confirm it from the matrix: the cosine of 75° is 0.259.
  3. Move the point p slider in the gripper frame. Its base coordinates change, but the point stays fixed on the gripper: that is what a frame attached to a link means.
  4. Change the link lengths. The last column of the matrix (the gripper origin) changes; the rotation block depends only on the angles.
Common traps
  • Order of multiplication. T_A^B T_B^C is not T_B^C T_A^B. Read a product from the outside in: the left matrix is the frame you are closest to the base of the chain.
  • Active versus passive. Rotating a point by α and rotating the frame by α give opposite rotations. Decide which one a formula means before you multiply.
  • Translation lives in the parent frame. The offset t is measured in A, not in B. Adding t to coordinates given in B is the most common bug in hand calculations.
  • Units. A transform mixes rotations (no units) and translations (metres). Keep all translations in one unit, usually metres.
Pipeline view. Stage: estimate (the frame tree is a state of the robot). Rate: recomputed at every control tick, because joint angles change. Stores: a tree of transforms, for example the ROS 2 tf2 library's frame graph.
Where it shows up in AI
  • Pose estimation returns a transform from the camera to an object; grasping needs that transform chained to the robot base.
  • Hand–eye calibration finds the fixed transform between a camera and the gripper, once, so that every later camera measurement can be mapped into the robot's frame.
  • Coordinate reference systems are the same idea on the Earth: GeoAI transforms between map projections, and a robot does this between its own frames.

Check yourself

1. Frame B is rotated 90° and sits at the origin of A. What are the base coordinates of the point (1, 0) in B?
Rotating (1, 0) by 90° gives (0, 1). With zero translation, the base coordinates are (0, 1).
2. In T_B^A the translation column is (2, 1). What does the number 2 mean, and in which frame is it measured?
It is the x-coordinate of frame B's origin, measured in frame A, in the same unit as the points (here metres).
3. Using the worked example, check that the inverse maps (2.866, 1.500) back to (1, 0). Show the arithmetic.
x: 0.866×2.866 + 0.500×1.500 − 2.232 = 2.482 + 0.750 − 2.232 = 1.000. y: −0.500×2.866 + 0.866×1.500 + 0.134 = −1.433 + 1.299 + 0.134 = 0.000. The point returns to (1, 0).

Takeaways

  • A frame is a coordinate system attached to something; a point has coordinates in a given frame.
  • A homogeneous transform packs rotation and translation into one matrix: rotate, then move.
  • Chain frames by multiplying transforms in order; invert a transform with R⊤ and −R⊤t.

Joint space & configuration space

The questionAn arm must move from where it is to a goal without touching a shelf. The shelf is an obstacle in the room. But the arm does not move in the room: it moves its joints. How do we make the shelf and the arm live in the same space, so that a planner can search for a path?

Intuition

Describe the robot by its configuration: the list of all its joint values, \mathbf q=(\theta_1,\theta_2,\dots) for a revolute arm. Every configuration fixes the whole machine, so the list is a complete description of the robot's shape. The set of all possible configurations is the configuration space (C-space). For an arm, it is joint space: each point of it is one arm pose.

The point of the idea is this. In the room, the arm is a complicated shape and the shelf is a box. In C-space, the arm is a single point, and the shelf becomes a region: the set of joint values at which some part of the arm would touch the shelf. Moving the arm without collision is now the same problem as moving a point around a region, which is a problem computers handle well.

Two facts beginners find surprising. First, C-space is often not a flat box: each revolute joint turns through a full circle, so the angle -180^\circ and 180^\circ are the same pose, and a two-joint arm lives on a torus (a doughnut). Second, a straight line in C-space is not a straight line in the room, and it is usually not what the arm should do.

Build it up: a two-link arm and one obstacle

Take a planar arm with links L_1=L_2=1\ \text{m}. With joint angles \theta_1 (base) and \theta_2 (elbow, measured relative to link 1), the elbow sits at (L_1\cos\theta_1,\ L_1\sin\theta_1) and the tip at the elbow plus (L_2\cos(\theta_1+\theta_2),\ L_2\sin(\theta_1+\theta_2)). Put a round obstacle of radius r=0.3\ \text{m} at (1.5,\,0) m. Call a configuration in collision if any point of either link lies within r of the obstacle centre.

Worked example

Test four configurations, measuring each link's closest distance to the obstacle centre:

  • \mathbf q=(0^\circ,0^\circ): elbow (1, 0), tip (2, 0). Link 2 runs from (1, 0) to (2, 0) and passes right through (1.5, 0), distance 0 m. Collision.
  • \mathbf q=(0^\circ,90^\circ): elbow (1, 0), tip (1, 1). Link 2 runs up from (1, 0); the closest point is (1, 0), at distance 0.5 m. Link 1 is also 0.5 m away. Both exceed 0.3 m. Free.
  • \mathbf q=(90^\circ,0^\circ): elbow (0, 1), tip (0, 2). Link 1's nearest point is (0, 0), distance 1.500 m; link 2's is (0, 1), distance 1.803 m. Free.
  • \mathbf q=(45^\circ,0^\circ): elbow (0.707, 0.707), tip (1.414, 1.414). Distances 1.062 m and 1.061 m. Free.

So the point (0^\circ,0^\circ) lies in the forbidden region of configuration space, and the other three are free. Testing only the tip would have wrongly passed the first case, which is the first trap below.

If we test every configuration on a fine grid of (\theta_1,\theta_2), the forbidden cells form a shape in C-space. Obstacles in the room become such shapes; a planner then looks for a path through the free cells. The lab below draws this exactly.

The formal definition

\mathcal C=\{\mathbf q\}, \qquad \mathcal C_{\text{obs}}=\{\mathbf q:\ \mathcal A(\mathbf q)\cap\mathcal O\neq\varnothing\}, \qquad \mathcal C_{\text{free}}=\mathcal C\setminus\mathcal C_{\text{obs}}

Here \mathcal A(\mathbf q) is the set of points the robot occupies at configuration \mathbf q, and \mathcal O is the set of points of the obstacle. A motion is valid if every configuration along it lies in \mathcal C_{\text{free}}. For the disc in the example, \mathcal C_{\text{obs}} is the set of \mathbf q where some link comes within r of the centre.

Lab

Try this
  1. Move the obstacle centre to (1.0, 0.0) and watch the red region in the right-hand grid. The straight yellow line from S to G crosses it; the readout says where first.
  2. Press Play and watch the arm's configuration (the dot) cross the red region. In the workspace the arm turns red at the same moment.
  3. Grow the radius from 0.3 m to 0.6 m. The forbidden region grows, and the straight line may now hit it earlier. A bigger obstacle is a bigger shape in C-space, not a bigger shape in the arm.
  4. Move the obstacle far from the arm (for example x = −2). The forbidden region shrinks towards nothing.
Common traps
  • Checking only the tip. The worked example's first configuration has its tip clear of the obstacle yet its link passes through it. Every point of every link must be checked.
  • Thinking the straight line is safe. A straight line in joint space is a smooth motion for the joints, but the arm's links may sweep through an obstacle along the way. Planners check the whole motion, not only its ends.
  • Forgetting the wrap. Revolute angles repeat every 360°. A planner that treats −180° and 180° as far apart will walk the long way round.
  • Sampling misses thin obstacles. A grid of configurations can jump over a thin wall. A test must be finer than the thinnest feature, or check the path between samples.
Pipeline view. Stage: plan (collision checking is run inside the planner). Rate: planning is offline or per request, often in tens of milliseconds; the collision check must be fast. Stores: the obstacle model (a set of shapes) and the robot model (link geometry).
Where it shows up in AI
  • Motion planners such as sampling-based planners in MoveIt (which uses OMPL) search configuration space for collision-free arm paths (module 5).
  • Learned policies that output joint targets are trained or checked against the same notion of a valid configuration.

Check yourself

1. For the worked obstacle, why is q = (0°, 0°) forbidden even though its tip is 1 m from the obstacle centre?
Because the second link lies along the line through the obstacle centre (1.5, 0). A point of the link is at distance 0 from the centre, which is inside the 0.3 m radius. The tip was never the test.
2. Two revolute joints each turn through a full circle. What shape is their configuration space, and why is θ₁ = −180° the same configuration as θ₁ = +180°?
A torus (a doughnut). Each angle wraps around, so −180° and +180° point the link in the same direction and give the same pose.
3. If an obstacle grows, does the free region of configuration space grow or shrink? Why?
It shrinks. A larger obstacle means more configurations have some link within the radius, so 𝒞obs grows and 𝒞free = 𝒞 ∖ 𝒞obs shrinks.

Takeaways

  • A configuration is the vector of joint values; the set of all configurations is configuration space.
  • A workspace obstacle becomes a forbidden region in configuration space, where the whole body, not just the tip, is checked.
  • Planning is search for a path of free configurations; revolute joints make the space a torus, and straight lines in C-space are not straight in the room.

Workspace, degrees of freedom & redundancy

The questionA two-link arm is asked to put its tip on a point 1.0 m from its base. Is it possible? If yes, how many ways are there to do it? And if we add a third link, how does the answer change?

Intuition

The workspace is the set of points the tip can reach. For a two-link arm it is not a disc but a ring. The outer edge is the arm fully stretched, at distance L_1+L_2. The inner edge is the arm folded back on itself, at distance |L_1-L_2|. Inside the inner circle is a hole the arm cannot reach, because even folded fully, its two links cannot come back that close to the base.

Each point inside the ring usually has two ways to be reached: the elbow can bend one way or the other. Imagine your own arm pointing at a door handle; you can keep the elbow up or let it drop, and the hand lands on the same handle.

This is where the earlier idea of degrees of freedom becomes useful. The arm has m joints, and the task (here, placing the tip in the plane) needs k numbers. If m>k the arm is redundant: it has m-k spare degrees of freedom, and infinitely many joint vectors reach the same tip. A three-link planar arm placing only its tip has one spare degree of freedom. Many real arms (for example some seven-joint arms) are redundant on purpose, because the spare joint lets them avoid obstacles or keep the elbow clear.

Finally, some poses are singular: the arm loses the ability to move the tip in some direction, however the joints move. A stretched-out arm can move its tip only along its own line, not sideways. Near a singular pose, a tiny tip motion demands a large joint motion.

Build it up: the ring, by hand

Take L_1=1.0\ \text{m} and L_2=0.6\ \text{m}. The reachable workspace is 0.4\ \text{m}\le r\le 1.6\ \text{m}, where r is the distance of the tip from the base. Our target is at distance r=1.0 m and angle 30°, that is (0.866,\ 0.500) m.

Find the elbow angle first, using the law of cosines on the triangle formed by the base, the elbow and the tip:

\cos\theta_2=\frac{r^2-L_1^2-L_2^2}{2L_1L_2}
Worked example

With r^2=1, L_1^2=1, L_2^2=0.36: \cos\theta_2=\frac{1-1-0.36}{1.2}=-0.300, so \theta_2=\pm107.46^\circ. Two solutions exist because cosine is even.

Then the base angle: \theta_1=\operatorname{atan2}(y,x)-\operatorname{atan2}\big(L_2\sin\theta_2,\ L_1+L_2\cos\theta_2\big). The target angle is \operatorname{atan2}(0.5,\,0.866)=30^\circ.

  • Solution A, θ₂ = +107.46°: \theta_1=30^\circ-34.92^\circ=-4.92^\circ. Check: the elbow is at (\cos(-4.92^\circ),\ \sin(-4.92^\circ))=(0.996,\,-0.086) m, and the tip is the elbow plus 0.6(\cos 102.54^\circ,\ \sin 102.54^\circ)=(-0.130,\,0.586), giving (0.866,\,0.500). ✓
  • Solution B, θ₂ = −107.46°: \theta_1=64.92^\circ. The elbow lies on the other side and the tip lands on the same point. ✓

The determinant of the Jacobian (the quantity that measures singularity, module 2) is L_1L_2\sin\theta_2=0.6\times0.954=0.572\ \text{m}^2 for solution A: far from zero, so the pose is not singular.

Now the three-link arm, with L_1=L_2=L_3=1 m and the tip fixed at (1.5,\,1.0) m. Fix the gripper angle \varphi (the absolute direction of the last link). Then the wrist point, \text{tip}-L_3(\cos\varphi,\sin\varphi), must be reached by the first two links, which is the two-link problem above. Each choice of \varphi gives a valid arm:

  • \varphi=0^\circ: (\theta_1,\theta_2,\theta_3)=(7.42^\circ,\ 112.02^\circ,\ -119.45^\circ)
  • \varphi=30^\circ: (-27.93^\circ,\ 132.38^\circ,\ -74.45^\circ)
  • \varphi=60^\circ: (-52.07^\circ,\ 119.41^\circ,\ -7.33^\circ)
  • \varphi=90^\circ: (-41.41^\circ,\ 82.82^\circ,\ 48.59^\circ)

Four different arm shapes, one tip. Here θ₂ and θ₃ are relative angles (each measured from the link before), and the gripper angle is their sum with θ₁: \varphi=\theta_1+\theta_2+\theta_3.

The formal definition

\mathcal W=\{\,p(\mathbf q):\ \mathbf q\in\mathcal Q\,\},\qquad \text{2-link: } |L_1-L_2|\le r\le L_1+L_2,\qquad \text{redundancy}=m-k

The workspace \mathcal W is the image of the joint limits \mathcal Q under the forward map p (the tip position). The ring formula holds when the joints can turn freely; joint limits shrink the real workspace. A pose is singular when the Jacobian J(\mathbf q) loses rank, which for the two-link arm is \det J=L_1L_2\sin\theta_2=0, at \theta_2=0^\circ or 180^\circ.

Lab

Try this
  1. Keep L₁ = 1.0 and L₂ = 0.6. Drag the target to (0.2, 0.0), inside the hole. The arm reports unreachable and gives the reason.
  2. Set the target to (0.866, 0.5). Press "Switch solution" and watch the arm fold from solution A to solution B. Between the two poses the tip leaves the target: the joints move in a straight line, not the tip.

Common traps
  • Reaching a point is not reaching it in any orientation. The ring tells you the tip can be placed; it says nothing about which way the gripper can point there.
  • More joints is not free. A redundant arm has more solutions to choose from, but it also has more to compute, more to check for collisions and more joints that can fail.
  • Singularities hurt. Near a singular pose, a small tip motion needs very large joint speeds. Controllers must slow down or refuse the motion there.
  • Joint limits. The ring is the reach with unlimited joints. A real elbow that can turn only 120° has a smaller workspace.
Pipeline view. Stage: plan and control (reachability is checked before a motion is planned, and redundancy is resolved during control). Rate: a reachability check is a few microseconds; redundancy resolution runs at the control rate. Stores: the joint limits and the link lengths, which define the robot model.
Where it shows up in AI
  • Arm design sets link lengths so that a task's workspace is covered; redundant arms are chosen when obstacles or human co-workers are close.
  • Teleoperation maps a human's hand pose into the robot's workspace; redundancy resolution keeps the robot's elbow clear while the tip follows the human.
  • Learned controllers trained on demonstrations can produce joint targets that are outside the workspace or near singularities, so practical systems check reachability first.

Check yourself

1. A two-link arm has L₁ = 2 m and L₂ = 1 m. Can its tip reach a point 0.5 m from the base?
No. The inner edge is |L₁ − L₂| = 1 m, so 0.5 m lies inside the hole.
2. A planar arm has three revolute joints and only its tip position is specified. What is the redundancy? How many tip positions along one orientation can it realise?
Redundancy = 3 − 2 = 1. For any reachable tip position, a whole family of joint vectors reaches it (one for each gripper angle that works), so there are infinitely many.
3. For the two-link arm, at which elbow angles is the pose singular, and why does that matter?
When sin θ₂ = 0, that is θ₂ = 0° or 180°, the arm is fully stretched or fully folded and det J = 0. The tip cannot move sideways there, so tiny tip motions demand large joint motions.

Takeaways

  • The workspace of a two-link arm is a ring between |L₁ − L₂| and L₁ + L₂; the law of cosines gives the elbow angle.
  • DOF is the number of joints; redundancy is joints minus task numbers, and a redundant arm has a continuum of solutions.
  • Singular poses are where the arm loses a direction of motion; check for them before commanding fast tip motion.

The robot software stack

The questionA camera delivers 30 frames per second, a state estimator runs at 50 Hz, a planner replans at 10 Hz, and the motor controller must update 1000 times per second. An emergency stop must act within milliseconds. Which program runs where, how do they talk, and how can we be sure that the fast loop always meets its deadline?

Intuition

A robot is not one program. It is a stack of programs, each owning one part of the sense–think–act loop, passing messages to its neighbours:

  • Sensor drivers read cameras, lidars, encoders and force sensors and publish their raw data.
  • Estimation fuses those readings into one belief about the robot's state and surroundings (module 3).
  • Planning decides where to go, slowly, from that belief.
  • Control turns the plan into motor commands, fast, against the current state.
  • Actuator drivers send the commands to the motors and read back their status.

Each layer runs at its own rate, because each has its own job: a motor loop must be fast and predictable; perception can be slower but heavier. They talk through topics with a publish–subscribe pattern: a node publishes messages on a named topic, and any node that subscribes receives them. ROS 2 is a widely used middleware that provides exactly this, with nodes, topics and services, and a DDS communication layer underneath.

There is one more distinction. A real-time task has a deadline: a result that arrives late is wrong, like a motor command that comes 10 ms late. A best-effort task only needs a good average: a logging write can be delayed without harm. Real-time guarantees come from the operating system and the scheduler, not from the message layer, so a fast middleware on a slow scheduler is still not real time.

Build it up: can three tasks meet their deadlines?

Give the controller a period of T=1\ \text{ms} and a compute time of C=0.2\ \text{ms} per run. The estimator runs every 10\ \text{ms} and needs 2\ \text{ms}. The planner runs every 100\ \text{ms} and needs 20\ \text{ms}. Each task's utilisation is the fraction of the processor it needs: C/T.

Worked example

Controller: 0.2/1=0.200. Estimator: 2/10=0.200. Planner: 20/100=0.200. Total U=0.600: the processor is busy 60% of the time.

Is that safe? For three tasks scheduled by fixed priorities (shortest period first, the rate-monotonic rule), the Liu–Layland test says that all deadlines are met if U\le n(2^{1/n}-1). For n=3 the bound is 3(2^{1/3}-1)=0.780. Since 0.600\le0.780, the schedule is guaranteed to meet every deadline. The test is sufficient, not necessary: a set above the bound may still be schedulable.

Now the data age. The estimator publishes at R_e=50\ \text{Hz}, and a message takes L=2\ \text{ms} to reach the controller. The controller ticks at t_c=0.100\ \text{s}. The newest estimate that has arrived by then was published at t_p=\lfloor(0.100-0.002)\times50\rfloor/50=\lfloor4.9\rfloor/50=0.080\ \text{s}. Its age is t_c-t_p=20\ \text{ms}. In general the age lies between L and L + 1/Re (here 2 ms and 22 ms).

The formal definition

U=\sum_{i=1}^{n}\frac{C_i}{T_i}\ \le\ n\,(2^{1/n}-1),\qquad t_p=\frac{\lfloor (t_c-L)\,R_e\rfloor}{R_e},\qquad \text{age}=t_c-t_p
nnumber of periodic tasks
Ti, Ciperiod and worst-case compute time of task i, in seconds (or ms)
Utotal utilisation: the fraction of the processor needed
tctime of a controller tick (the moment the command is computed)

Common traps
  • Average rate hides the worst case. A controller at 1 kHz that is usually on time can still miss a deadline once a second. Real-time analysis uses the worst case, not the mean.
  • Real-time middleware is not real time. ROS 2 moves messages; deadlines depend on the operating system, the scheduler and how the nodes are configured.
  • Perception in the control thread. A slow camera callback that shares a thread with the motor loop makes the motor loop late. Keep hard loops isolated.
  • Forgetting the bus. Each hop adds latency. A pipeline of four hops at 2 ms each has at least 8 ms of delay before any processing time.
Pipeline view. Stage: deploy and monitor, across all six stages: the stack is what runs them. Rates: from 1 kHz (motor control) to 1–10 Hz (planning) and beyond. Stores: the message log and the configuration of each node, which the monitoring of module 9 reads.
Where it shows up in AI
  • ROS 2 is the usual middleware for research and many commercial robots: nodes for each stage, topics for their data, and a launch file that wires them together.
  • Learned policies run as one more node. Their inference time must fit the control period, which is why module 8 discusses action chunking: one slow policy call produces several fast actions.
  • Industrial controllers run the hard loops on dedicated hardware with a real-time operating system, and keep the learned or planning software out of that path.

Check yourself

1. Why does the controller run every 1 ms while the planner runs every 100 ms? What would go wrong if both ran every 1 ms?
The motor needs fresh commands at a rate that keeps it stable (module 0.1: Kp·Δt must stay below 2), while planning is slow and expensive. Running the planner every millisecond would need far more compute than the processor has and would leave no time for the control loop.
2. Three tasks have U = 0.90. The bound is 0.780. What can you conclude?
The Liu–Layland test cannot guarantee that all deadlines are met, because 0.90 is above the sufficient bound. It does not prove a miss either: the set may still be schedulable, so an exact response-time analysis or a simulation is needed.
3. An estimator publishes at 100 Hz and the bus latency is 5 ms. What is the range of the controller's data age?
From L = 5 ms to L + 1/Re = 5 + 10 = 15 ms. The age can never be smaller than the latency, and it never exceeds one estimator period plus the latency.

Takeaways

  • A robot is a stack of nodes, one per stage, passing messages on topics at their own rates.
  • Real-time means meeting a deadline in the worst case; the average is not enough. Fixed priorities with utilisation below the bound give a guarantee.
  • Data age is set by the estimator period and the bus latency; measure it, because the controller always acts on old information.
