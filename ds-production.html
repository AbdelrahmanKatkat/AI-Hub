Module 9 · Communicating, deploying & responsible data science

An analysis is only useful if others can trust it, re-run it, and keep it healthy after it ships. This module covers the last two stages of the data science loop: communicating the work so it reproduces, documenting data and models, watching a deployed model drift, measuring fairness honestly, protecting personal data, and planning your own path in the field.

9.1

Reports people can trust and reproduce

The questionA shop manager reads your report: "mean order value is 102.50". Three months later an auditor asks you to produce that number again, and you get 95.00. What went wrong, and what should have been written down so that the number comes back every time?

Intuition: a number is a recipe, not a fact

A figure in a report is the output of a recipe: some raw data, some steps, some tools. If you keep only the figure, you have the cake but not the recipe. Anyone who doubts it, including you in three months, can only taste it. A report people can trust keeps the recipe next to the cake: the data, the method and the limits, in a form a stranger can re-run.

This sits at stage 5 of the data science loop (communicate), but it is decided in stage 2: if you cleaned the data by hand in a spreadsheet and never wrote down what you did, no amount of care at the end repairs it.

Build it up

Step 1, the simplest case. Eight orders, with two refunds recorded as negative amounts. The manager wants the mean order value of real sales.

row12345678
amount12080−3095150−4511060
Worked example, one recipe, three results

Recipe: drop rows with a negative amount (refunds), then take the mean. Six rows remain: 120, 80, 95, 150, 110, 60. Their sum is 615 and 615/6=102.50. That is the published number.

Forgetting the rule. The mean of all eight rows is 540/8=67.50. A different recipe, a different number, and nothing in the report says which was used.

A hand edit. Someone "corrects" row 5 from 150 to 105 in the file. The mean of the six kept rows becomes 570/6=95.00, exactly the auditor's number. The data changed, silently.

Every one of the three results is arithmetic done correctly. The failure is not the arithmetic: it is that the inputs, the rule and the code were not pinned down.

Step 2, what must be pinned. A result is a function of four things:

\text{result}=f\bigl(\text{raw data},\ \text{code version},\ \text{environment},\ \text{random seed}\bigr)
Symbols. f: the whole analysis, from raw file to figure. Raw data: the untouched input file, never edited by hand. Code version: the exact script or notebook, for example a version-control commit. Environment: language and package versions. Random seed: the starting value of any random number generator, so that sampling, splits and bootstraps repeat. If all four are the same, the result must be the same; if you cannot say which one changed, you cannot explain a difference.

Step 3, the habits that pin them.

  • Raw data is read-only. Every change is made by code that reads raw and writes a new file. Then "what did you do to the data?" is answered by reading the script. A fingerprint (a checksum of the file) lets anyone check they hold the same bytes.
  • Version control. Commit the code with messages that say why. A diff then shows exactly what changed between two published numbers.
  • One command from raw to report. If reproducing needs eleven manual steps, it will not be reproduced.
  • Write the method, the data and the limits. Method: every filter and its row count ("8 rows, 2 refunds dropped, 6 kept"). Data: source, date pulled, what is missing. Limits: sample size, uncertainty, what the analysis cannot say (intervals belong next to every estimate).
Try this
  1. Press Re-run with the defaults and watch the packet. The report should reproduce 102.50. Note the fingerprint of the raw file.
  2. Change the row 5 value to 105 and re-run. Which message explains the mismatch, and how would a version-control diff have shown it?
  3. Reset, untick the refund rule, and re-run. Then reset and tick "hand-type the number". Why is a hand-typed number the hardest failure to find?
Common traps
  • Fixing data in the spreadsheet. A manual edit leaves no trace. Do it in code, or record it in a cleaning log with the rule and the row count.
  • Pasting numbers into the report. Generate figures and tables from the script so the text and the analysis cannot drift apart.
  • Unpinned randomness. A bootstrap interval that changes in the third decimal each run looks like a bug. Seed it, and say the seed.
  • Reproducible is not correct. A script can reproduce a wrong answer perfectly. Reproducibility lets others find the error; it does not prove there is none.
Where it shows up in AI
  • Experiment tracking: a model's accuracy only means something with the data version, code commit, hyperparameters and seed attached (see experiments and registry).
  • Research and audits: results that cannot be re-run from raw data cannot be audited, and training-set changes that were never logged are a common reason a retrained model behaves differently.

Check yourself

1. Using the printed table, what is the mean if refunds are dropped but row 5 is changed from 150 to 105?
Kept rows: 120, 80, 95, 105, 110, 60, sum 570, so 570 / 6 = 95.00.
2. Name the four inputs that, if all equal, must give the same result.
Raw data, code version, environment (package versions) and random seed.
3. A colleague says "my script runs and gives the same number every time, so it is right". What is wrong with that?
Reproducible means repeatable, not correct. A script with a wrong rule, for example one that keeps refunds (67.50 instead of 102.50), repeats its error perfectly. Reproducibility makes the error findable; review and checks make it absent.

Takeaways

  • A reported figure is the output of raw data, code, environment and seed; keep all four.
  • Never edit raw data by hand; transform it in code and log row counts at each step.
  • A good report states the method, the data and the limits, with the uncertainty beside each estimate.
9.2

Documenting datasets and models: datasheets and model cards

The questionA hospital team receives your model with the note "accuracy 85%". They serve two patient groups, and one of them is only a quarter of your test data. What else must the note say before they can decide whether to use it?

Intuition: a nutrition label for data and models

A food label does not say "good". It lists what is inside and who should be careful. A datasheet does that for a dataset (why it was collected, how, by whom, what is missing). A model card does it for a model (what it is for, what it was trained on, how it was evaluated, where it fails). The idea, proposed in the "Datasheets for Datasets" and "Model Cards for Model Reporting" papers, is simple: the people who will use the thing should not have to guess its limits.

Build it up

The fields. A short model card answers six questions: Intended use (and what is out of scope). Training data (source, period, size, known gaps). Evaluation data and metrics. Results by subgroup. Known failure modes and limits. Owner, version and date. A datasheet adds how the data was collected, consent and licence, preprocessing, and recommended uses.

Why the subgroup line matters. A single headline number is an average, and an average can hide a weak group. Here is a test set of 80 cases split into two groups.

groupcases ncorrectaccuracy95% interval (Wilson)
A60540.9000.80 to 0.95
B20140.7000.48 to 0.85
overall80680.8500.76 to 0.91
Worked example, a headline that hides a group

Overall accuracy is 68/80=0.85, a weighted average of the groups: \tfrac{60}{80}(0.90)+\tfrac{20}{80}(0.70)=0.675+0.175=0.85. Group B is 20 points lower, but because B is only a quarter of the data it moves the average by just 5 points.

Group B is also small, so its estimate is uncertain. The standard error is \sqrt{0.7\times0.3/20}=0.1025, giving a rough interval of about ±0.20. The Wilson interval, better for small n, is 0.48 to 0.85. So the honest sentence is "accuracy for B is 0.70, and with 20 cases we can say only that it is somewhere between about 0.5 and 0.85".

If we had 100 cases of B with the same 70% accuracy, the interval would tighten to 0.60 to 0.78. More data from the group you are most worried about is often the most valuable data to collect.

\mathrm{acc}_g=\frac{1}{n_g}\sum_{i\in g}\mathbf 1[\hat y_i=y_i],\qquad \mathrm{acc}=\sum_g\frac{n_g}{n}\,\mathrm{acc}_g,\qquad \mathrm{SE}_g\approx\sqrt{\frac{\mathrm{acc}_g(1-\mathrm{acc}_g)}{n_g}}
Symbols. g: a subgroup such as an age band or a region. n_g: test cases in that group; n: all test cases. \hat y_i: the model's prediction for case i; y_i: the true label. \mathbf 1[\cdot]: 1 if the statement is true, 0 otherwise. \mathrm{SE}_g: standard error of the group accuracy; about 95% of the time the true accuracy lies within roughly \pm1.96\,\mathrm{SE}_g, a rough rule that is poor when n_g is small.
Try this
  1. Leave the defaults and watch cases arrive. Which whisker stays wide for longer, and why?
  2. Raise group B's share to 50%. How does the overall accuracy move relative to the two group lines, and how does B's interval change?
  3. Set both accuracies to 0.80. The overall and the groups agree. Now set B to 0.60: how many cases does it take before the model card line clearly shows the gap?
Common traps
  • One number for everyone. Always report by the subgroups your users care about. Choosing them is a judgement; ask who is affected.
  • Reporting a subgroup without its n. "70%" from 20 cases and from 2000 cases are different claims.
  • Documenting only the good news. The failure modes section is the most useful one. If you do not know any, say how you looked.
  • A card that is written once. Models and data change; stale documentation is worse than none because it is trusted.
Where it shows up in AI
  • Responsible AI documentation: model cards and datasheets are standard artefacts for released models and datasets, and are the first thing an auditor asks for (see governed ML and interpretability and fairness).
  • Foundation models: evaluation tables broken down by language, domain or demographic slice are model-card results at scale.

Check yourself

1. A model scores 0.90 on 50 cases of group A and 0.60 on 50 cases of group B. What is the overall accuracy, and what does it hide?
Overall = (45 + 30)/100 = 0.75. It hides a 30-point gap between the groups.
2. Why does the interval for group B in the table (0.48 to 0.85) look wider than group A's (0.80 to 0.95)?
B has only 20 cases against 60, and a lower accuracy gives a larger p(1-p). Both increase the standard error.
3. Name three things a model card should say besides accuracy.
Any three of: intended and out-of-scope use, training data and its gaps, evaluation data and metrics, results by subgroup, known failure modes, owner, version and date.

Takeaways

  • Document datasets (datasheets) and models (model cards): purpose, data, evaluation, limits, owner.
  • Overall accuracy is a weighted average that can hide a weaker group; report each group with its n and interval.
  • Known failure modes are the most valuable section; keep the card up to date.
9.3

Monitoring: data drift, concept drift and alerts

The questionYour model has been live for two months. The true outcomes (did the customer actually repay?) arrive weeks late, so you cannot yet compute accuracy. How can you tell today that the model's world has changed, and when should it raise an alarm?

Intuition: compare today's inputs with the inputs you trained on

A model is a memory of the past. It works while tomorrow's inputs look like the training inputs. When they stop looking alike, performance can fall, and you often see the change in the inputs long before you see it in the outcomes, because inputs are available immediately and labels are not.

Two kinds of change are worth separating. Data (covariate) drift: the distribution of the inputs P(x) moves, for example customers get older. Concept drift: the relationship between inputs and the outcome P(y\mid x) moves, for example the same customer profile now behaves differently after a price change. Data drift is visible without labels; concept drift needs labels (or proxies) to detect. Either can hurt a model, and a model can also be fine under data drift if it still sits in the range it learned.

Build it up

Step 1, bin the feature. Cut a feature into bins using the training data. Record the share of training rows in each bin, e_i ("expected"), and the share of live rows, a_i ("actual").

order value<2020–4040–6060–8080+
training share e0.100.200.400.200.10
live share a0.050.150.350.250.20

Step 2, score each bin. The population stability index adds up, over bins, how much each share moved, weighted by how surprising the log-ratio is:

\mathrm{PSI}=\sum_{i=1}^{B}(a_i-e_i)\,\ln\frac{a_i}{e_i}
Symbols. B: number of bins. e_i: share of training data in bin i. a_i: share of live data in bin i. \ln: natural logarithm. Each term is zero when a_i=e_i and is never negative, because a_i-e_i and \ln(a_i/e_i) always have the same sign. Swapping a and e gives the same value, so PSI is symmetric. An empty bin makes \ln blow up, so implementations add a tiny floor.
Worked example, PSI for the printed table

Bin by bin, (a-e)\ln(a/e):

<20: (-0.05)\ln(0.5)=(-0.05)(-0.6931)=0.0347
20–40: (-0.05)\ln(0.75)=(-0.05)(-0.2877)=0.0144
40–60: (-0.05)\ln(0.875)=(-0.05)(-0.1335)=0.0067
60–80: (0.05)\ln(1.25)=(0.05)(0.2231)=0.0112
80+: (0.10)\ln(2)=(0.10)(0.6931)=0.0693

Total \mathrm{PSI}=0.1362. Half of it comes from the top bin: live customers order big more often than the training data said. A commonly quoted rule of thumb reads below 0.1 as stable, 0.1 to 0.25 as worth watching, and above 0.25 as a large shift. These are folk thresholds from credit scoring, not laws: set yours by watching how PSI relates to real accuracy for your model.

Step 3, alert and act. Compute PSI on a schedule (daily, weekly) for each important feature and for the model's score. An alert fires when it crosses a threshold. The response is a human decision: investigate (data pipeline bug? a new product?), then maybe retrain, recalibrate or roll back. Retraining triggers usually combine PSI with accuracy once labels arrive, because input drift does not always mean the model got worse.

Try this
  1. Press Play with the defaults. Watch the orange histogram slide away from the blue training curve and the PSI line climb. On which day does the alert fire, and what is the accuracy then?
  2. Lower the alert threshold to 0.1 and then raise it to 0.4. Alerts that come too early cause false alarms; too late, damage is done. Where does accuracy start to fall in relation to the alert?
  3. Set the drift to 0 and let it run. The PSI is not exactly zero: it wiggles from sampling noise. What does that tell you about setting the threshold?
Common traps
  • Drift is not harm. The model is only hurt if the inputs move to where it is wrong. Check against accuracy once labels arrive.
  • Bins from the live data. Always cut bins from the training data, or the comparison is against itself.
  • Monitoring only the score. A stable output can hide shifting inputs that cancel out. Watch key features too.
  • Alert fatigue. Dozens of features with a noisy threshold means alerts nobody reads. Pick the features that matter and a threshold that survives a quiet week.
  • Seasonality is not drift. December shopping differs from June every year. Compare to the same season or to a longer window.
Where it shows up in AI
  • Production ML: drift monitors, delayed-label dashboards and retraining triggers are core to every deployed model (the engineering view is in ML production).
  • Large language models: the same idea applied to prompts and topics: when the kinds of questions users ask shift, an evaluation set built last year stops representing today.

Check yourself

1. One bin had a training share of 0.50 and a live share of 0.30. What is its PSI term?
(0.30-0.50)\ln(0.30/0.50)=(-0.20)(-0.5108)=0.1022.
2. Why can PSI warn you earlier than accuracy does?
PSI needs only the inputs, which arrive immediately. Accuracy needs true labels, which often arrive weeks later, and the model may stay accurate until the inputs travel far enough from its training range (in the lab, the alert fires while accuracy is still near its starting level).
3. Data drift versus concept drift: which one needs labels to detect, and why?
Concept drift: it is a change in P(y\mid x), the link between inputs and outcomes, so you must see outcomes. Data drift is a change in P(x), visible from inputs alone.

Takeaways

  • Compare live inputs with training inputs, bin by bin: \mathrm{PSI}=\sum(a_i-e_i)\ln(a_i/e_i); the table above gives 0.1362.
  • Data drift is visible without labels; concept drift needs outcomes; neither automatically means the model got worse.
  • An alert should lead to a human investigation and a retraining decision, with thresholds tuned to your own history.
9.4

Fairness metrics and their trade-offs

The questionA model approves loans using a score from 0 to 1. Group A and group B both apply. How would you check whether the model treats them fairly, and can you always make every reasonable check pass at once?

Intuition: "fair" can mean several different things

Ask three people what fair means here. One says "the same share of each group should be approved". Another says "among people who would repay, each group should have the same chance of being approved". A third says "an approval should mean the same thing for everyone: the same chance of repaying". All three are reasonable, each is a precise formula, and, as we will see, they cannot all hold at once when the groups differ in how often the outcome occurs. Choosing among them is a decision about values and law for the specific use, not a calculation. This lesson shows the formulas and their limits honestly.

Build it up

Step 1, the printed table. Eight applicants per group, with a score and what actually happened (1 = would repay). Approve when score ≥ 0.50.

group A score0.900.800.700.600.550.400.300.20
repays?11101100
group B score0.850.650.600.450.400.350.200.10
repays?10110000

Group A: 5 of 8 repay (base rate 0.625). Group B: 3 of 8 repay (base rate 0.375). The groups differ in base rate, which matters below. With 8 people each this table is for arithmetic, not for conclusions.

Step 2, three families of metric. Let \hat Y=1 mean "approved", Y=1 "would repay", G the group.

\text{Demographic parity: }P(\hat Y=1\mid G=A)=P(\hat Y=1\mid G=B)
\text{Equal opportunity: }P(\hat Y=1\mid Y=1,G=A)=P(\hat Y=1\mid Y=1,G=B)
\text{Predictive parity (precision): }P(Y=1\mid \hat Y=1,G=A)=P(Y=1\mid \hat Y=1,G=B)
Symbols. P(\cdot\mid\cdot): probability among the people satisfying the condition. Demographic parity compares selection rates. Equal opportunity compares true-positive rates (qualified people approved); requiring the false-positive rates to match as well is called equalised odds. Predictive parity compares precision (PPV): of those approved, the share who repay. A closely related idea, calibration within groups, asks that a score of 0.7 mean a 70% repay rate in every group (see calibration). In practice gaps are measured as differences or ratios, and "equal" means "close enough for the decision at hand".
Worked example, the table at threshold 0.50

Group A. Approved (score ≥ 0.50): 0.90, 0.80, 0.70, 0.60, 0.55, which is 5 of 8, so selection rate 5/8=0.625. Of the 5 who repay, those approved are 0.90, 0.80, 0.70, 0.55, so TPR 4/5=0.800. The one approved non-repayer is 0.60: FPR 1/3=0.333. Precision 4/5=0.800.

Group B. Approved: 0.85, 0.65, 0.60, so selection rate 3/8=0.375. Of the 3 who repay (0.85, 0.60, 0.45) two are approved: TPR 2/3=0.667. One non-repayer approved (0.65) of 5: FPR 1/5=0.200. Precision 2/3=0.667.

Gaps. Demographic parity gap 0.625-0.375=0.250. Equal opportunity gap 0.800-0.667=0.133. FPR gap 0.333-0.200=0.133. Precision gap 0.800-0.667=0.133.

Move the threshold to 0.40. Group A approves 6 (selection 0.750, TPR 5/5 = 1.000, FPR 1/3, precision 5/6 = 0.833). Group B approves 5 (selection 0.625, TPR 3/3 = 1.000, FPR 2/5 = 0.400, precision 3/5 = 0.600). Now equal opportunity holds exactly (both 1.000), the demographic parity gap is 0.125, but the precision gap grew to 0.233 and the FPR gap changed sign (group B is now the higher one, by 0.067). Fixing one metric moved the others.

Step 3, why not all at once. Counting shows the tension. For any group with base rate p (the share who truly have Y=1), a binary classifier satisfies an identity:

\mathrm{FPR}=\frac{p}{1-p}\cdot\frac{1-\mathrm{PPV}}{\mathrm{PPV}}\cdot(1-\mathrm{FNR})
Symbols. p: the group's base rate. \mathrm{PPV}: precision. \mathrm{FNR}=1-\mathrm{TPR}: false-negative rate. \mathrm{FPR}: false-positive rate. Check with group A at 0.50: \tfrac{0.625}{0.375}\cdot\tfrac{0.2}{0.8}\cdot0.8=0.3333, the FPR we counted. For group B: \tfrac{0.375}{0.625}\cdot\tfrac{1/3}{2/3}\cdot\tfrac23=0.2000.

The impossibility result (Kleinberg, Mullainathan and Raghavan 2016; Chouldechova 2017), stated carefully. If the two groups have different base rates and the classifier is not perfect, then it is impossible for equal PPV, equal FPR and equal FNR to hold simultaneously. Read the identity: if PPV, FNR are equal in both groups but p differs, then FPR must differ. In the same spirit, a score that is calibrated within each group and also has equal false-positive and false-negative rates across groups is possible only with a perfect predictor or equal base rates. Demographic parity conflicts with these too when base rates differ, since a classifier that is accurate must approve groups at different rates. The result is a mathematical fact about counting, not a fault of any one model. It does not say fairness is impossible; it says you must choose which criterion matters for this decision, justify it, and say what it costs on the others.

Two honest cautions. First, equal base rates are rare, and base rates themselves can reflect past unfairness in the data (who was given loans before), so "just match the data" is not neutral. Second, the group variable can be correlated with other features, so simply deleting it from the inputs does not guarantee fairness metrics improve.

Try this
  1. With the threshold at 0.50 and linked, read the four gaps. Press Play and watch them change as the threshold sweeps. Is there any threshold where all four gaps are near zero?
  2. Untick "same threshold" and set group B's threshold lower than A's. Which gap shrinks, and which grows? You have just chosen a criterion.
  3. Use the score shift slider to push group B's scores down (a model that underrates B). Which metric reveals it most clearly?
Common traps
  • Picking the metric that looks best. Choose the criterion before looking at results, and record why.
  • Tiny groups. With few people per group, gaps are mostly noise; show counts and intervals (lesson 9.2).
  • Fairness through unawareness. Dropping the sensitive column does not remove proxy features such as postcode.
  • A metric is not an outcome. A parity number tells you nothing about whether the decision helps or harms people downstream; involve the people affected.
  • Legal tests differ by jurisdiction. This lesson is not legal advice; for a real system get legal and domain review.
Where it shows up in AI
  • Credit, hiring and health: audits compute selection rates, TPR and precision by group, and teams document which criterion they chose and why (governed ML).
  • Mitigation: options include reweighting data, group-specific thresholds, and post-processing; each trades one metric for another.

Check yourself

1. Using the printed table at threshold 0.50, what is group B's selection rate and the demographic parity gap?
B approves 3 of 8 = 0.375. A approves 5 of 8 = 0.625. Gap = 0.250.
2. At threshold 0.40, what is the equal opportunity gap, and what does it show about the metrics?
Both groups have TPR 1.000, so the gap is 0. Yet the precision gap is 0.833 − 0.600 = 0.233, so satisfying one criterion does not satisfy the others.
3. State the impossibility result in one careful sentence.
When the groups' base rates differ and the classifier is imperfect, equal precision, equal false-positive rate and equal false-negative rate across the groups cannot all hold at the same time, so a choice among criteria must be made and justified.

Takeaways

  • Demographic parity, equal opportunity and precision (calibration) are different, precise, and often incompatible definitions of fair.
  • With different base rates and an imperfect classifier, equal PPV, FPR and FNR cannot all hold; the identity \mathrm{FPR}=\tfrac{p}{1-p}\tfrac{1-\mathrm{PPV}}{\mathrm{PPV}}(1-\mathrm{FNR}) shows why.
  • Choose and document the criterion with the affected people and legal review; report gaps with counts and uncertainty.
9.5

Privacy: anonymisation, consent and aggregation

The questionYou remove the names from a patient table and publish it. Someone with a public list of local residents works out which row is a named neighbour, and reads their diagnosis. How did that happen, and how much detail must you remove before it stops?

Intuition: you can be identified by a combination, not only a name

A name or a national ID is a direct identifier: remove it first. But age, postcode and sex are quasi-identifiers: each is common, yet the combination can be nearly unique, like a fingerprint made of ordinary facts. If your table has one 44-year-old woman in one postcode, and a public record says exactly one such woman lives there, then a name-free table is not anonymous. A famous study estimated that a large share of the US population could be pinned down by ZIP code, birth date and sex alone (Sweeney, 2000; later re-estimates were lower but still high). The lesson is that "anonymous" is a claim you must test, not a property that removing names grants.

Build it up

Step 1, group by the quasi-identifiers. An equivalence class is the set of rows that share the same quasi-identifier values. k-anonymity asks that every class contain at least k rows, so each person hides among at least k look-alikes.

rowageZIPsexdiagnosis
13410115Fflu
23610117Fflu
35210115Masthma
45510117Mdiabetes
53310115Fflu
65810116Masthma
74110215Fasthma
84410218Fdiabetes
k(T)=\min_{c\in\mathcal C}\ \lvert c\rvert,\qquad T\text{ is }k\text{-anonymous}\iff k(T)\ge k
Symbols. T: the table. \mathcal C: the set of equivalence classes (rows sharing all quasi-identifier values). \lvert c\rvert: number of rows in class c. k(T): the size of the smallest class, which is the best k the table can claim.
Worked example, raising k by generalising

Exact values (age, ZIP, sex): all 8 rows are different, so every class has 1 row and k=1. Anyone who knows a neighbour's age, ZIP and sex finds their row.

Generalise: age to a decade, ZIP to its first 3 digits. Classes: (30s, 101, F) = rows 1, 2, 5, size 3; (50s, 101, M) = rows 3, 4, 6, size 3; (40s, 102, F) = rows 7, 8, size 2. Now k=2.

Generalise more: age to "under 40 / 40+", ZIP to 2 digits, drop sex. Classes: (under 40, 10) = rows 1, 2, 5, size 3; (40+, 10) = rows 3, 4, 6, 7, 8, size 5. Now k=3. Each step cost detail: we can no longer say where in the city, or how old exactly.

But look at the first class: rows 1, 2 and 5 all have the diagnosis "flu". An attacker who knows a neighbour is a woman in her 30s in that area learns her diagnosis, even though k=3. This is the homogeneity attack: k-anonymity protects against being singled out, not against learning the sensitive value. Extensions such as l-diversity (each class has at least l different sensitive values) address this, and each has its own weaknesses.

Step 2, beyond one table. Anonymisation often fails in practice for three reasons: linkage (another dataset supplies the missing attribute), high dimensions (the more columns, the more unique each row; a few dozen ordinary attributes can make almost everyone unique) and repeated release (several "safe" releases about the same people can be combined). Better practice combines several measures:

  • Minimise: collect and keep only the fields you need, for as long as you need.
  • Consent and purpose: use the data for what people agreed to; consent rules differ by place and sector (this is where legal advice matters).
  • Aggregate and suppress: publish counts and averages, and hide any cell with fewer than some minimum number of people. The threshold is a policy choice.
  • Differential privacy: add calibrated random noise to released statistics so that one person's presence changes the output distribution by at most a factor e^{\varepsilon}: \Pr[M(D)\in S]\le e^{\varepsilon}\Pr[M(D')\in S] for datasets D,D' differing in one person. A smaller \varepsilon means stronger privacy and more noise. It gives a guarantee that does not depend on what other data an attacker has.
  • Access control and logs for the raw data, whatever you publish.
Try this
  1. At level 0, read k and the number of unique people. Press Play and watch the boxes merge as detail is removed. At which level does the table first become 3-anonymous?
  2. Raise the target k to 6 and step through the levels. What do you lose in detail to reach it, and what does the group count tell you?
  3. Look for dashed boxes: groups where everyone has the same diagnosis colour. Does a larger k always remove them?
Common traps
  • "We removed the names." Quasi-identifiers still identify. Test with a k count or a linkage attempt.
  • k-anonymity is not full privacy. The homogeneity attack above, background knowledge, and repeated releases all remain.
  • Hashing an ID is not anonymising it if the possible IDs are few and an attacker can hash them all.
  • Small cells in aggregates. A table of counts with a cell of 1 reveals that person. Suppress or merge.
  • Labs here are illustrative; legal definitions of anonymous or personal data vary by law and need professional review.
Where it shows up in AI
  • Personal-data pipelines: training sets from health, location or purchase records need minimisation, access control and release checks before any model or table leaves the team.
  • Model memorisation: a model can reproduce parts of its training data, so a model trained on personal data can itself be personal data (see governed ML).

Check yourself

1. For the printed table, what is k with exact (age, ZIP, sex)?
k = 1: all eight rows are different, so each class has one row.
2. After generalising to (under 40 / 40+, 2-digit ZIP), what is k and what remains risky?
Class sizes are 3 and 5, so k = 3. The class of rows 1, 2 and 5 is all "flu", so the diagnosis of anyone known to be in it is revealed anyway.
3. Why is a postcode a quasi-identifier but not a direct identifier?
A postcode alone does not name anyone, but combined with age and sex it can narrow a person down to one row, especially when matched against another dataset such as a public register.

Takeaways

  • Direct identifiers name you; quasi-identifiers (age, postcode, sex) identify you in combination.
  • k-anonymity needs every group of look-alikes to have at least k rows; generalising raises k at the cost of detail, but it does not stop homogeneity attacks.
  • Real protection combines minimisation, consent and purpose limits, aggregation thresholds, access control and possibly differential privacy; get legal review for real data.
9.6

Working as a data scientist: scope, collaboration and next steps

The questionA manager says "can you use data to improve retention?" You have the skills from this whole topic. What do you do in the first week, how do you know what to build, and how do you show others what you can do?

Intuition: most of the job is deciding what the job is

Technical skill is necessary and rarely the bottleneck. The common failure is an excellent answer to a question nobody needed. So the first skill is scoping: turning a wish into a decision, a metric, a dataset and a deliverable, and agreeing it with the person who will act on it. The second is collaboration: the data you need is owned by engineers, the decision is owned by a manager, and the context is held by domain experts. The third is evidence of work: a small set of projects others can open and re-run.

Build it up

Step 1, scope with four questions.

Notice what the second row does. It names who decides, what they will do differently, how success is measured and what the data is. Note also the honest checks hidden inside: can we get that data, is it legal and ethical to use it for this (lesson 9.5), and could the effect be measured by an experiment (Module 5)?

Step 2, plan the loop. Estimate effort for each of the six stages: ask and agree, collect, clean, explore, model or test, communicate, deploy and monitor. Unclear questions cost extra, because late changes force earlier stages to be redone.

Worked example, a toy plan

Suppose you plan Ask 1 day, Collect 3, Clean 5, Explore 3, Model 4, Communicate 2, Deploy 2: 20 days. The work after the Ask stage is 3+5+3+4+2+2=19 days. In this teaching toy, we assume rework equals r\,(1-c) times that downstream work, with r=0.6 and c the clarity of the question between 0 and 1. The numbers are an assumption for illustration, not a measured rule.

If c=0.5: rework =0.6\times0.5\times19=5.7 days, total 25.7. If the question is perfectly clear (c=1): total 20. If it is hopelessly vague (c=0): rework 11.4, total 31.4. The point is the direction: one more day of the Ask stage is cheap insurance.

T_{\text{total}}=\sum_{s=1}^{S}d_s\;+\;r\,(1-c)\sum_{s\ge2}d_s
Symbols. S: number of stages (the lab shows S=7 bars: the six stages of the loop, with "ask and collect" split into two). d_s: planned days for stage s; stage 1 is Ask. c: clarity of the question from 0 to 1. r: the toy rework constant (0.6 here). The sum from s\ge2 is the work that depends on the question being right. In the lab you can change every d_s and c.

Step 3, role families. Titles vary a lot between organisations, so read the job description, not the title. These families overlap:

  • Data / business analyst: questions, dashboards, reports; strong on SQL, visualisation, communication.
  • Data scientist (analysis, experiments): statistics, causal questions, A/B tests, modelling for decisions.
  • Machine learning engineer: builds and runs models in production; strong software and monitoring (ML production).
  • Data engineer: builds the pipelines and tables everyone else relies on.
  • Research scientist: new methods; usually deep in maths and papers.

No single family is the "real" one. Pick by what you enjoy: answering questions, building systems, or inventing methods.

Step 4, a portfolio of reproducible projects. Three small, finished projects beat ten half-done ones. For each, the reader should find: the question and decision it informs; where the data came from and its licence; a script or notebook that runs from raw data in one command (lesson 9.1); a baseline and an honest evaluation (Module 7); a short README with method, limits and uncertainty; and, if it concerns people, a note on privacy and fairness (9.4, 9.5). Public data you care about makes better projects than another generic tutorial dataset.

Try this
  1. Press Reset and watch the playhead walk the plan. Note the sentence at the bottom: what does the stakeholder see at each stage?
  2. Slide the question clarity to 100% and then to 0%. How much of the total is rework in each case?
  3. Give the Ask stage 3 days and keep clarity at 50%. Then raise clarity to 80% with the same other numbers. Does the extra day pay for itself under the toy assumption?
Common traps
  • Starting with a model. "We will use machine learning" is a solution, not a question. Start from the decision.
  • Hiding in the notebook. Share early drafts and surprises. Disagreement found in week one is cheap.
  • Unscoped "just a quick look". Without a deliverable and a stopping rule the work never ends or quietly changes meaning.
  • Portfolio as a gallery of tutorials. The same famous dataset with the same model shows little. Show a question you chose, a decision, and limits.
  • Believing a figure about the job market. Demand, titles and tools change; look at current postings in your region instead of trusting any single number, including numbers in courses.
Where it shows up in AI
  • Career planning: the families above map to the rest of this hub: machine learning (ML), computer vision, and later NLP and generative AI. Pick one project in a topic you want to work in.
  • Every AI project that fails for non-technical reasons failed at scoping, data access or deployment: the three places this module teaches you to look.

Check yourself

1. Turn "understand our customers" into a decision, a metric and a deliverable (any reasonable example).
Decision: which of two onboarding emails to send to new customers. Metric: share still active after 30 days. Deliverable: a one-page recommendation from a randomised comparison, with the interval. Any answer naming a decision, a measure and a concrete output is fine.
2. In the toy plan, total planned days are 20 with 19 downstream. What is the rework when clarity is 0.8?
0.6\times(1-0.8)\times19=2.28 days, so the total is 22.28.
3. Why is a re-runnable project a better portfolio piece than a screenshot of a result?
A reader can verify and extend it, which shows the habits of lesson 9.1 (raw data, code, seed, limits), not only that you obtained a number once.

Takeaways

  • Scope first: a decision, a metric, data and a deliverable agreed with the person who will act.
  • Role families overlap and titles vary; choose by what you want to do and read the actual descriptions.
  • A few reproducible, honestly evaluated projects with stated limits are the best evidence of skill.
