What is machine learning?

The questionYou want a program that estimates the price of a flat from its size. You could sit down and write the rule yourself — "price = 2.5 × size". But where did 2.5 come from? And what happens next year when the market moves and every flat costs more? Is there a way for the computer to find the rule itself, from past sales?

Intuition

Ordinary programming is a recipe. A person works out the steps, writes them down, and the computer follows them exactly: rules + data → answers. This works wonderfully when you know the rules (add up a bill, sort a list). It fails when the rules are too many, too subtle, or secretly unknown: what makes an email spam? what makes a photo a cat? You can feel the answer but cannot write it down.

Machine learning flips the arrangement: data + answers → rules. You show the computer many examples where the answer is known — flats with their real selling prices — and it works out a rule that fits them. The rule it finds is called the model. Then you hand the model a flat it has never seen and it produces an estimate.

Think of how a child learns "dog". Nobody gives the child a definition. They are shown many dogs and non-dogs and told which is which; their brain adjusts until the word fits. A model does the same, only with numbers, and the "adjusting" is arithmetic.

Build it up: a model is a function with knobs

In the maths course you met functions with knobs (Functions): f(x;a,b)=ax+b. Here x is the input that changes from example to example; a and b are the knobs that decide which line we have. A model is exactly that: a function \hat y=f(x;\theta) where x describes the thing (size of the flat), \theta (theta) is the list of all knobs (called parameters), and \hat y ("y-hat") is the prediction. Learning is choosing \theta — and to choose we need a way to say how good a choice is.

The usual way: for each training example compare the prediction with the true answer, square the difference, and average. This is the loss (here the mean squared error, Σ notation). A small loss means the model fits the examples; learning means searching for the knobs with the smallest loss.

Worked example — four flats

Sizes (m²) and prices (k$): (50, 150), (70, 190), (90, 250), (110, 290). Model: \hat y=wx+b.

Guess 1 — hand-written rule w=2.5,b=0: predictions 125, 175, 225, 275; errors −25, −15, −25, −15; squares 625, 225, 625, 225; loss = 1700/4 = 425.

Guess 2 w=2,b=50: predictions 150, 190, 230, 270; errors 0, 0, −20, −20; loss = (0+0+400+400)/4 = 200.

Guess 3 w=3,b=0: predictions 150, 210, 270, 330; errors 0, 20, 20, 40; loss = 2400/4 = 600.

The best line (the one with the smallest possible loss): mean size 80, mean price 220; deviations from the means are −30, −10, 10, 30 and −70, −30, 30, 70. Slope w=\frac{\sum(x-\bar x)(y-\bar y)}{\sum (x-\bar x)^2}=\frac{4800}{2000}=2.4, intercept b=220-2.4\cdot80=28. Predictions 148, 196, 244, 292; errors −2, 6, −6, 2; loss = 80/4 = 20. For a new 100 m² flat the model says 2.4·100+28 = 268 k$.

Nobody wrote "2.4" and "28" — they were found by minimising the loss. That is learning.

When the market moves, the hand-written rule is stuck until a person edits it. The learned model is simply re-fitted on fresh data. This — rules that update themselves from data — is the practical superpower. It comes with a price: you need enough good data, the model can be wrong in ways you cannot easily inspect, and it only knows what the examples taught it.

The formal definition

\hat\theta=\arg\min_{\theta}\;L(\theta),\qquad L(\theta)=\frac1N\sum_{i=1}^{N}\ell\big(f(x_i;\theta),\,y_i\big)
(xi, yi)the i-th training example: its input description and its known answer; there are N of them
f(x; θ)the model: a function of the input with parameters θ
ŷ = f(x; θ)the prediction for input x
ℓ(ŷ, y)the loss for one example: how wrong one prediction is (e.g. (ŷ−y)²)
L(θ)the average loss over the training set; a function of the knobs
argminθ"the value of θ that makes what follows smallest" — the answer is a θ, not a number
θ̂the chosen (learned) parameters

How do we actually find the smallest loss when there is no neat formula? We take small downhill steps — gradient descent (Optimisation). You will watch it work in the third lab below.

When is ML the right tool? Use it when (1) the rule is hard to write but examples are plentiful, (2) the world changes so rules need constant updating, (3) a good-but-imperfect answer is valuable. Do not use it when the rule is known and exact (tax arithmetic), when you have almost no data, when mistakes are intolerable and cannot be checked, or when a simple rule already does the job.

Common traps
  • "The model understands." It has found a rule that fits the examples. Outside the range of its examples it can be confidently wrong.
  • Confusing the model with the algorithm. The algorithm (gradient descent) searches; the model (the line with w=2.4, b=28) is what it found.
  • ML for everything. If you can state the rule exactly, write the rule; it is cheaper, testable and explainable.
Where it shows up in AI
  • Spam filters, credit scoring, recommendations: a model trained on past labelled examples, re-trained regularly as behaviour changes.
  • Deep learning is the same recipe with a very large f: a network with millions of knobs θ, the same loss, the same descent.
  • Language models learn by minimising a loss on predicting the next word of enormous text collections — "data + answers → rules" at scale.

Check yourself

2. Name the three things that make "ML is the right tool" a good bet.

3. In ŷ = f(x; θ), which part changes while learning and which changes from example to example?

Takeaways

  • Programming: rules + data → answers. ML: data + answers → rules (the model).
  • A model is a function ŷ = f(x; θ); learning is choosing θ to minimise the average loss on examples.
  • More (good) data improves the model until noise or model limits dominate.
  • Use ML when rules are hard to write, data is plentiful and the world changes.

Types of learning & tasks

The questionYou have a table of students: hours studied, hours slept, exam score. Your manager says "do something useful with it." Useful how? Predict who will pass? Predict the score? Group similar students? Rank them? The same table supports completely different problems — how do we choose, and what changes in the method?

Intuition

Two questions classify any ML problem. First: what kind of feedback does the learner get? Second: what kind of answer must it produce?

  • Supervised learning — every training example comes with the right answer (a label), like a teacher marking homework. Most commercial ML is this.
  • Unsupervised learning — no answers, only inputs. The learner finds structure itself: groups, outliers, simpler summaries. Like sorting a pile of unlabelled coins by looking at them.
  • Self-supervised learning — the data supplies its own labels: hide a word of a sentence and learn to predict it; hide part of an image and learn to fill it in. Labelling is free, so it scales to the internet — the basis of modern language models.
  • Reinforcement learning — no labelled answers, but an agent acts and receives rewards (a game score, a robot reaching the goal). It learns a strategy by trial and error.

Within supervised learning the type of answer defines the task: classification (pick a category: pass/fail, spam/not-spam), regression (predict a number: the exam score, a price). Unsupervised tasks include clustering (group similar items). Others: ranking (order items by relevance, as search engines do) and generation (produce new text, images or audio resembling the data).

A new student studied h = 5 hours. Three framings, three different answers.

Classification (label: passed). All fails are at h ≤ 3 and all passes at h ≥ 6, so a threshold halfway, h = 4.5, separates them perfectly (6/6 correct). h = 5 > 4.5 → pass.

Regression (target: score). The best line through (h, score) has slope 7.04 and intercept 24.13, so \hat y=24.13+7.04\cdot5=59.3 → score ≈ 59.3.

Clustering (no labels at all, k = 2). Start with centres at h = 1 and h = 9. Assign each student to the nearer centre: A, B, C → centre 1; D (|6−1|=5 vs |6−9|=3), E, F → centre 2. Move centres to the means: (1+2+3)/3 = 2 and (6+8+9)/3 = 7.67. Re-assign: nothing changes — converged. The new student at h = 5 is |5−2| = 3 from the first centre and |5−7.67| = 2.67 from the second → cluster 2 ("studies a lot").

The same input, but the answers are a category, a number and a group id. The data, not the maths, decides which are possible: clustering needed no labels; the other two needed them.

The formal definition

\text{supervised: } \{(x_i,y_i)\}_{i=1}^N,\; f:\mathcal X\to\mathcal Y\qquad \text{unsupervised: } \{x_i\}_{i=1}^N
xi ∈ 𝒳input (features) of example i; 𝒳 is the set of all possible inputs
yi ∈ 𝒴the label / target. Classification: 𝒴 is a finite set of classes {0,1,…}. Regression: 𝒴 = ℝ
f : 𝒳 → 𝒴the function we want to learn
unsupervisedonly the xi; the goal is structure (clusters, low-dimensional summary, density)

Self-supervised learning is supervised learning where y is carved out of x (e.g. the next word). Reinforcement learning replaces labels by a reward signal and a sequence of actions.

Common traps
  • Turning a regression into a classification carelessly. "Passed" throws away how close each score was to the line.
  • Labels that are really outcomes of the model. If you only label what the current system flagged, you never learn about what it missed.
  • Calling anything "AI" supervised. Always ask: where do the labels come from, and who pays for them?
Where it shows up in AI
  • Classification: fraud/not fraud, tumour/not tumour, which of 1000 ImageNet classes (Computer Vision).
  • Regression: house prices, delivery time, demand forecasts.
  • Clustering: customer segments, grouping documents; also used to compress colours or build vocabularies.
  • Self-supervised: GPT-style next-token prediction, masked image models. RL: game agents, robot control, RLHF for chat models.

Takeaways

  • Feedback type: supervised (labels), unsupervised (none), self-supervised (labels from the data itself), reinforcement (rewards).
  • Answer type: classification (category), regression (number), clustering (groups), ranking (order), generation (new data).
  • The same table can be framed several ways; choose from the decision you must support.

The ML pipeline end to end

The questionA data scientist says "my model has 94% accuracy" and the team celebrates — yet six months after launch the product is losing money. What did the 94% leave out? Where does a model really live, what does each step of its life cost in compute and storage, and where can things silently break?

Intuition

A trained model is like a chef, but a restaurant is more than a chef. Ingredients must be bought (data), washed and chopped (preprocessing), the chef trains on recipes (training), customers order (inference), the plate is arranged and checked (post-processing), and the kitchen keeps records of orders, waste and complaints that decide tomorrow's menu (storage and monitoring). Most failures happen in the kitchen around the chef, not in the chef.

Every machine-learning system — a spam filter, a face unlock, a language model — runs the same six stages, which this whole course is organised around. Click each one below to see what it computes and what it stores.

  1. Data collection: gather examples (x,y) from databases, sensors, logs, people. Version them.
  2. Preprocessing: clean, encode, scale — turn raw records into a numeric matrix X (next lesson). Fit these transforms on training data only.
  3. Training: search for parameters \theta that minimise the loss. Heavy compute, done offline, rarely.
  4. Inference: apply the frozen model to new inputs. Light per request, but done millions of times, often under a time limit.
  5. Post-processing: scores become decisions — thresholds, ranking, explanations, business rules.
  6. Storage & monitoring: log inputs and outcomes, watch for drift, feed fresh labelled data back to stage 1. The loop never ends.

Build it up: shapes, sizes and costs

Each stage changes the shape of the data and has its own cost. Learning to estimate these on a napkin is a core engineering skill.

Worked example — a small tabular project

Data: N = 10 000 customers, 10 raw columns: 8 numbers and 2 categories with 4 and 6 values. Raw: 10 000 × 10.

Preprocessing: one-hot encode the categories (4 + 6 = 10 columns) → d = 8 + 10 = 18 numeric features. X is 10 000 × 18; stored as 32-bit floats (4 bytes): 10 000 · 18 · 4 = 720 000 bytes ≈ 0.7 MB.

Training: a tiny neural network 18 → 32 → 1 has P = 18·32 + 32 + 32·1 + 1 = 609 parameters. One pass over the data costs about 6·P·N = 6 · 609 · 10 000 ≈ 3.7 × 10⁷ floating-point operations (≈2 for the forward pass, ≈4 for gradients per parameter and example). A laptop does that in milliseconds; checkpoints weigh 609 · 4 = 2 436 bytes.

Inference: one request ≈ 2·P = 1 218 operations — microseconds. The cost is dominated by moving data and network time, not the maths.

Storage: logging each request with 200 bytes at 1 000 000 requests/day = 200 MB/day → 73 GB/year. Monitoring storage dwarfs the model.

Scale N to 10⁸ rows and P to 10⁹ parameters and everything flips: training needs GPUs for weeks, while the model alone no longer fits in one machine's memory. Same pipeline, different bottleneck.

Offline versus online. Offline (batch) work runs on a schedule over big piles of data — training, nightly scoring. Online work responds to one request now — inference behind an API with a latency budget (say 50 ms). Many systems mix them: train offline weekly, serve online, monitor continuously.

The formal view

\text{predict}(x_{\text{raw}})=\text{post}\big(f(\text{pre}(x_{\text{raw}});\hat\theta)\big)
pre(·)the preprocessing function, with parameters (means, vocabularies) learned from training data and then frozen
f(·; θ̂)the trained model, parameters fixed
post(·)post-processing: threshold, rank, calibrate, format
xrawone new raw record as it arrives

The crucial point: the same \text{pre} must run in training and in production. A mismatch ("training-serving skew") is one of the most common silent bugs.

Common traps
  • Only measuring the model. A production system also has latency, cost, freshness and failure handling.
  • Fitting preprocessing on all data including the test rows (leakage, lesson 0.5).
  • No monitoring. Inputs drift (customers change), accuracy decays quietly, nobody notices for months.
  • Forgetting the loop. Without logging outcomes there will be no new labels to improve the model.
Where it shows up in AI
  • Every deployed model: recommenders, fraud detection, voice assistants, vision systems (the vision pipeline is the same six stages with image-specific steps).
  • LLM products: tokenisation (pre), the transformer (inference), sampling and safety filters (post), prompt/response logging and evaluation (monitoring).
  • MLOps tooling: feature stores, experiment trackers, model registries and drift monitors each exist to manage one stage — see Module 9.

Check yourself

1. With N = 50 000 rows, d = 30 float32 features, how many MB is X?
50 000 · 30 · 4 = 6 000 000 bytes = 6 MB.
2. Which stage typically costs the most compute per model version, and which costs the most per year of operation?
Training dominates per version (heavy, offline). Over a year, inference (millions of requests) and storage/monitoring of logs often dominate the total bill.
3. Why must the mean used for scaling be computed from the training data only, then reused for new data?
New data arrives one record at a time with no dataset to average, and using test rows would leak information the model cannot have in production. The frozen training statistics are part of the model.

Takeaways

  • Six stages: data → preprocessing → training → inference → post-processing → storage & monitoring, looping back to data.
  • Each stage changes the data's shape and has its own compute and storage cost; training is heavy and offline, inference is light but frequent.
  • Preprocessing learned on training data is part of the model and must be identical in production.
  • Monitoring closes the loop; without it models rot silently.

Data, features & labels

The questionA property agency gives you a spreadsheet: size, bedrooms, neighbourhood name, "has garden: yes/no", and the sale price. A model can only eat numbers arranged in a very particular way. How do you turn this spreadsheet into what the algorithm needs — and what can go wrong with the data itself before any algorithm runs?

Intuition

A dataset is a table. Each row is one example (one flat). Each column is one measurement (size, bedrooms…). One special column is the thing we want to predict — the label or target (price). The other columns are the features: the clues we give the model.

The model sees the clues, never the answer, during prediction. During training it also sees the answer so it can check itself.

Build it up: from a spreadsheet to X and y

Algorithms need numbers. Features come in different types, each needing its own treatment:

  • Numeric (size, age): already numbers; often rescaled.
  • Binary (has garden): 0 or 1.
  • Categorical (neighbourhood A/B/C): no order. Writing A=1, B=2, C=3 would claim that C is "three times" A (the trap from Mathematics). Instead use one-hot encoding: one 0/1 column per category.
  • Ordinal (small/medium/large): ordered categories; integers 1,2,3 are fine.
  • Text, images, dates: need their own transformations into numbers (later modules).

Encode: garden → 0/1; area → three one-hot columns (A,B,C). The feature matrix has d = size, bedrooms, garden, A, B, C = 6 columns:

X=\begin{pmatrix}50&1&0&1&0&0\\70&2&0&0&1&0\\90&3&1&1&0&0\\110&3&1&0&0&1\\80&2&1&0&1&0\end{pmatrix},\qquad y=\begin{pmatrix}150\\190\\250\\290\\220\end{pmatrix}

So X\in\mathbb R^{5\times6} (N = 5 rows, d = 6 columns) and y\in\mathbb R^{5}. Row i of X is the vector x_i — one point in \mathbb R^6.

Scale the size column: mean = 80; deviations −30, −10, 10, 30, 0; variance = (900+100+100+900+0)/5 = 400; standard deviation = 20; standardised sizes z=(x-80)/20 = −1.5, −0.5, 0.5, 1.5, 0. Now size is on the same footing as the 0/1 columns.

Labels have a cost. Prices come free from sales records; "is this scan cancerous" needs an expert for ten minutes each. Label cost shapes the project: how many examples can we afford, can we reuse existing signals, can we label only the most informative ones?

Data is never neutral. Models copy their data. If the training flats are mostly in one city, predictions elsewhere are unreliable; if past loan decisions were unfair, a model trained to imitate them reproduces the unfairness. Typical problems: sampling bias (examples not representative), label noise (wrong answers), missing values, duplicates, leakage (a feature that secretly contains the answer, like "price per m²" when predicting price) and drift (the world changes after collection).

The formal definition

X=\begin{pmatrix}x_{11}&\cdots&x_{1d}\\\vdots&&\vdots\\x_{N1}&\cdots&x_{Nd}\end{pmatrix}\in\mathbb R^{N\times d},\qquad y=(y_1,\dots,y_N)^\top,\qquad \mathcal D=\{(x_i,y_i)\}_{i=1}^N
Nnumber of examples (rows)
dnumber of features (columns) after encoding
xijvalue of feature j for example i
xithe i-th row of X, a vector in ℝd (see Linear algebra)
yvector of N labels (numbers for regression, class ids for classification)
𝒟the dataset, the set of (x, y) pairs

Common traps
  • Integer codes for categories (A=1, B=2, C=3) invent an order and distances.
  • Leakage: any feature computed from the label or from the future. It makes training look brilliant and production useless.
  • High-cardinality categories (ZIP codes, user IDs): one-hot produces thousands of mostly-zero columns; other encodings exist (Module 1).
  • Believing "more data" fixes bias. A million examples from the wrong population are still the wrong population.
Where it shows up in AI
  • Every tabular model (linear, trees, boosting) reads exactly this X and y — Modules 2–4.
  • An image is an X row of 784 or 150 528 numbers; a sentence becomes token ids then embeddings: the "table" idea at larger scale.
  • Data-centric AI: in practice improving labels and coverage often beats switching algorithms. ImageNet's and web-text's quality filters are examples.

Takeaways

  • Rows are examples, columns are features; one column (or more) is the label.
  • Models need a numeric matrix X (N × d) and a vector y of N labels; categories become one-hot columns.
  • Labels cost money and effort; bias, noise, leakage and drift live in the data, not the algorithm.

Generalisation: train, validation, test

The questionA student memorises last year's exam answers word for word and scores 100% on that paper. On this year's exam, with new questions, they fail. Has the student learned? A model can do exactly the same: perfect on its training data, useless on new data. How do we tell the difference before deploying?

Intuition

What we really want is not low error on the examples we have, but low error on examples we have not yet seen. This ability is generalisation. Memorising the training set is easy and worthless; spotting the pattern behind it is the goal.

The cure is simple: hide some data. Before training, set aside examples the model will never touch. Judge it on those. A student who is marked on a surprise paper cannot have memorised it.

  • Training set — the textbook: the model learns from it.
  • Validation set — the practice exam: we use it to choose between models and settings (how flexible to be, how long to train).
  • Test set — the real exam: used once, at the very end, to report the honest score. If we peek and then adjust, it becomes just another practice exam and the final score is optimistic.

Build it up: under- and overfitting

Give a model too little flexibility — a straight line through a curved pattern — and it misses the shape even on the training data: underfitting (high error everywhere). Give it too much flexibility — a wiggly curve with a knob for every point — and it passes through every training point including the random noise, then swings wildly between and beyond them: overfitting (tiny training error, large error on new data). In between is the sweet spot.

Worked example — five points, three models

Training data (x, y): (0, 1.0), (1, 2.6), (2, 2.7), (3, 4.4), (4, 4.6). Validation data: (0.5, 1.9), (2.5, 3.6), (5, 5.9). We fit polynomials of degree 1, 2 and 4 by least squares and compute the mean squared error on both sets.

degreecurvetrain MSEvalidation MSE
1y = 1.26 + 0.90x0.1300.021
2y = 1.089 + 1.243x − 0.086x²0.1100.199
4y = 1 + 4.933x − 5.142x² + 2.067x³ − 0.258x⁴0.00047.3

Degree 4 has five knobs for five points and threads every one exactly — training error zero — yet its validation error (47) is thousands of times worse than the plain line's (0.021). Judged on training error alone we would pick the worst model. Judged on validation error we pick the line. (With only 5 points the numbers are noisy; the lab uses many.)

Learning curves. Plot training and validation error against the amount of data. Training error starts near zero (easy to fit few points) and rises; validation error starts huge and falls; they approach each other. A big gap that closes with more data → overfitting: collect data or simplify. Both curves high and flat, close together → underfitting: more data will not help, use a richer model or better features.

The formal definition

\hat R_{\text{train}}=\frac1{N_{\text{tr}}}\sum_{i\in\text{train}}\ell\big(f(x_i;\hat\theta),y_i\big),\qquad \hat R_{\text{val}}=\frac1{N_{\text{val}}}\sum_{i\in\text{val}}\ell\big(f(x_i;\hat\theta),y_i\big)
\text{generalisation gap}=\hat R_{\text{val}}-\hat R_{\text{train}}
θ̂parameters chosen using training data only
R̂trainaverage loss on the training examples (optimistic)
R̂valaverage loss on held-out examples: an estimate of the error on new data
gaphow much worse the model is on unseen data; a large gap signals overfitting
Ntr, Nvalsizes of the two sets; a small validation set gives a noisy estimate

Typical splits: 60/20/20 or 70/15/15; for huge datasets a few percent is enough for validation and test. Data must be split randomly (or by time/group where examples are not independent — Module 1) and before any preprocessing that learns from the data.

Common traps
  • Reporting training accuracy. It rewards memorisation.
  • Tuning on the test set. Every peek-and-adjust leaks test information into the model; the final score is no longer honest.
  • Preprocessing before splitting (e.g. scaling with the global mean): validation information leaks into training.
  • Related examples on both sides (the same patient in train and test): the model recognises people, not disease.
  • A tiny validation set: one lucky split can mislead; later modules introduce cross-validation.
Where it shows up in AI
  • Every benchmark (ImageNet, GLUE) has a held-out test set; leaderboard contamination — test data leaking into training — is a serious concern for large language models.
  • Early stopping in neural networks: stop training when validation loss stops improving.
  • Regularisation, dropout, data augmentation are all tools against overfitting (Modules 2, 6). Double descent and modern huge models complicate the classic picture, but the held-out test remains the arbiter.

Check yourself

1. Model A: train error 2%, validation error 3%. Model B: train 0%, validation 15%. Which do you prefer and why?
A. B overfits (gap 15 points); A's validation error is the honest estimate and is much lower.
2. You try 20 model settings, pick the best by test error, and report it. What is wrong?
The test set was used for selection, so the reported error is optimistically biased. Use validation for choosing; touch the test set once.
3. Both training and validation error are high and nearly equal, and more data does not move them. What now?
Underfitting: increase model capacity, add informative features, train longer, or reduce regularisation.

Takeaways

  • The goal is generalisation: low error on unseen data, not on training data.
  • Split into train (learn), validation (choose), test (report once). Split before any preprocessing.
  • Underfit = high error everywhere; overfit = low train error, high validation error. Learning curves tell which you have.
