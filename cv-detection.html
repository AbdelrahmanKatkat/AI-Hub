6.1

Boxes & IoU

The questionA detector draws a box and the ground truth says another box is correct. They are not identical — one is a bit to the right and a bit too tall. Is the detector right? "Roughly" is not a number. How do we turn "how well do two rectangles agree?" into one value between 0 and 1 that a computer can threshold, and that a network can even be trained to maximise?

Intuition

Cut two rectangles out of paper and lay them on a table. Two things matter: how much area they share and how much area they cover together. If they are the same rectangle, shared = covered together. If they are far apart, shared = nothing. The ratio "shared ÷ covered together" is a perfect score: 1 for identical, 0 for disjoint, and smoothly in between. That ratio is Intersection over Union.

Before that we need a vocabulary for a box. Detectors store a box in one of three ways, and converting between them is daily work:

  • Corners (x_1,y_1,x_2,y_2): top-left and bottom-right (PASCAL VOC, torchvision, most NMS code).
  • Corner + size (x,y,w,h): top-left corner and width/height (COCO annotations).
  • Centre + size (c_x,c_y,w,h): used by anchors, YOLO and DETR, because a box's centre and size are the natural things to predict.

Image coordinates start at the top-left with y growing downward. Some detectors also normalise to 0…1 by dividing by the image width and height, so the numbers do not depend on resolution.

Build it up

Two boxes A and B. The intersection is itself a rectangle (or empty). Its left edge is the larger of the two left edges, its right edge the smaller of the two right edges, and the same for top and bottom. If that width or height comes out negative, there is no overlap, so we clip it at 0.

Worked example: IoU with real coordinates

A = (100, 100, 300, 260), B = (180, 150, 380, 330), in pixels.

  1. Areas: A = (300−100)·(260−100) = 200·160 = 32,000. B = (380−180)·(330−150) = 200·180 = 36,000.
  2. Intersection edges: left = max(100,180) = 180; right = min(300,380) = 300; top = max(100,150) = 150; bottom = min(260,330) = 260. Width = 300−180 = 120, height = 260−150 = 110, so I = 13,200.
  3. Union = A + B − I = 32,000 + 36,000 − 13,200 = 54,800 (we subtract I once because the sum counted the overlap twice).
  4. IoU = 13,200 / 54,800 = 0.241. The boxes look clearly "on the same object" to the eye, yet IoU is low — a hint of how strict 0.5 is.

The flaw of IoU. When boxes do not overlap, IoU = 0, whether they are 1 pixel or 1000 pixels apart. As a loss (1 − IoU) it has zero gradient there: the network gets no hint which way to move the box. GIoU (Generalised IoU) repairs this by also looking at the smallest box C that encloses both. The empty space inside C that belongs to neither box is penalised:

Worked example: GIoU

Same A and B. The enclosing box C = (100,100,380,330) has area 280·230 = 64,400. Wasted area C − (A∪B) = 64,400 − 54,800 = 9,600.

GIoU = 0.241 − 9,600/64,400 = 0.241 − 0.149 = 0.092.

Now a disjoint pair: P = (100,100,200,200) and Q = (420,100,520,200), each 100×100, IoU = 0. C = (100,100,520,200) has area 420·100 = 42,000, union = 20,000, so GIoU = 0 − 22,000/42,000 = −0.524. Move Q to (300,100,400,200): C = 300·100 = 30,000, GIoU = −10,000/30,000 = −0.333. Closer boxes score higher even with zero overlap — a usable gradient.

DIoU / CIoU go further: DIoU subtracts the squared distance between box centres relative to the squared diagonal of C; CIoU adds a term that compares aspect ratios. Both make boxes converge faster. (For our A and B: centres 100 px apart horizontally and 60 apart vertically, d² = 10,000, c² = 280²+230² = 131,300, so DIoU = 0.241 − 0.076 = 0.165.)

The formal definition

\mathrm{IoU}(A,B)=\frac{|A\cap B|}{|A\cup B|}=\frac{|A\cap B|}{|A|+|B|-|A\cap B|},\qquad \mathrm{GIoU}(A,B)=\mathrm{IoU}(A,B)-\frac{|C\setminus(A\cup B)|}{|C|}
|A|area of box A (width × height; 0 if the box is degenerate)
A ∩ Bthe intersection: the shared rectangle, empty if the boxes do not overlap
A ∪ Bthe union: everything covered by at least one box
Cthe smallest axis-aligned box that contains both A and B
C \ (A ∪ B)the part of C that is in neither box (the "wasted" area)
IoU ∈ [0,1], GIoU ∈ (−1,1]GIoU equals IoU when the boxes fill C exactly and tends to −1 as they drift apart

As a regression loss, \mathcal L_{\mathrm{GIoU}}=1-\mathrm{GIoU} is used by DETR and many YOLO versions, usually next to an L1 loss on the coordinates.

Common traps
  • Off-by-one and format mix-ups. Feeding (x,y,w,h) to code that expects (x1,y1,x2,y2) gives plausible-looking but wrong IoUs. Convert explicitly, and check one box by hand.
  • Forgetting to clip at zero. Two disjoint boxes give a negative "width"; multiplying two negatives gives a positive fake intersection. Always max(0, …).
  • IoU is not "percent overlap". Overlapping by half of each box gives IoU = 1/3, not 1/2, because the union is 1.5 boxes. Half-and-half agreement is already below the usual 0.5 threshold.
  • Axis-aligned only. This IoU is for upright rectangles. Rotated boxes and masks need polygon or pixel IoU.
Where it shows up in AI
  • Evaluation: a detection counts as correct if IoU with a ground-truth box exceeds a threshold (0.5 for PASCAL VOC; 0.5…0.95 averaged for COCO) — lesson 6.7.
  • Training targets: anchors are labelled positive or negative by their IoU with ground truth (lesson 6.3).
  • Post-processing: NMS compares IoU between predictions (lesson 6.5).
  • Loss: GIoU/DIoU/CIoU losses in YOLOv5–v8, DETR, FCOS.

Check yourself

1. Boxes (0,0,10,10) and (5,0,15,10). Compute IoU.
Intersection x from 5 to 10 = 5, y 10, so I = 50. Areas 100 + 100, union = 150. IoU = 50/150 = 0.333.
2. Why can a model not be trained with 1 − IoU as a loss when the predicted box misses the target entirely?
With no overlap IoU is exactly 0 and constant in a neighbourhood, so its gradient is zero: nothing tells the box which way to move. GIoU adds the enclosing-box term, which changes as the boxes approach each other.
3. A = (0,0,2,2) and B = (0,0,4,4). Find IoU and GIoU.
I = 4, union = 16, IoU = 0.25. The enclosing box is B itself (area 16) so the penalty is (16−16)/16 = 0 and GIoU = 0.25. For nested boxes GIoU equals IoU.

Takeaways

  • A box is four numbers; know which of the three formats you are holding.
  • IoU = shared area / covered area; 1 = identical, 0 = disjoint.
  • IoU gives no gradient without overlap; GIoU/DIoU/CIoU fix this for losses.
  • IoU thresholds define "correct" in training, post-processing and evaluation alike.
6.2

From sliding windows to Faster R-CNN

The questionYou already have a good image classifier. A photo contains a dog somewhere, size unknown, plus a cat, plus a bicycle. How do you turn "classify the whole image" into "find every object and draw a box around it" — without running a network a million times?

Intuition

The most obvious plan: cut the image into small crops, ask the classifier "what is in this crop?" for every crop, and keep the confident ones. It works, and it is how detection began. The trouble is counting crops. Objects can be small or large, tall or wide, so you must try several window sizes and shapes; and the object can be anywhere, so you must slide each window across the whole picture. Each placement is a full network pass.

The history of detection is the story of removing wasted work from this loop, in three moves: (1) don't look everywhere, only at promising regions (proposals); (2) don't run the whole CNN again for each region — run it once and cut the regions out of the feature map; (3) don't use a hand-made proposal algorithm — let a small network propose regions from those same features.

Build it up

Worked example: how many windows?

A 640×480 photo, three window sizes 64, 128, 256 (square), stride 8 px. For a w×w window the number of positions is (\lfloor(640-w)/8\rfloor+1)\cdot(\lfloor(480-w)/8\rfloor+1):

w = 64: (72+1)·(52+1) = 73·53 = 3,869 · w = 128: (64+1)·(44+1) = 65·45 = 2,925 · w = 256: (48+1)·(28+1) = 49·29 = 1,421.

Total = 8,215 windows. Allow three aspect ratios and it is ≈ 25,000. At 15 ms per classifier pass that is 123 s for one photo — and the boxes are still only as precise as the stride.

The four stages in order:

  1. R-CNN (2014). A classical algorithm, selective search, merges similar-looking pixel regions into ≈ 2,000 region proposals (≈ 2 s per image). Each region is cropped, warped to a fixed size, and sent through a CNN; an SVM classifies the features and a linear regressor refines the box. Accurate for its time, but 2,000 separate CNN passes ≈ 47 s per image, and training was a multi-stage mess.
  2. Fast R-CNN (2015). Run the backbone once on the whole image to get a feature map. Project every proposal onto that map (divide coordinates by the stride, e.g. 16) and apply RoI pooling: split the projected rectangle into a 7×7 grid and max-pool each bin, so every region becomes the same 256×7×7 block regardless of size. Two small FC layers then output class scores and box refinements — one network, trained end to end. ≈ 0.3 s plus the 2 s of selective search.
  3. Faster R-CNN (2015). Replace selective search with a Region Proposal Network (RPN): a tiny conv head that slides over the shared feature map and, for each location, scores a set of anchor boxes as object / not-object and refines them. Proposals become nearly free: ≈ 0.2 s per image in total, 5 fps.
  4. Modern two-stage detectors add an FPN (feature pyramid) so that small and large objects are handled on different levels, and replace RoI pooling by RoIAlign (Mask R-CNN).

RoI pooling vs RoI Align. Pooling rounds the projected box to whole feature cells, which shifts it: a box x ∈ [100,300] at stride 16 is x ∈ [6.25, 18.75] on the map; rounding to [6,18] and then to integer bins loses up to a quarter cell ≈ 4 px of the original image. For classification that hardly matters; for tight boxes and masks it does. RoIAlign never rounds: it divides the exact rectangle into 7×7 bins of width 12.5/7 = 1.786 cells, places a few sample points inside each bin, and reads each value by bilinear interpolation from the four nearest cells, then averages.

The formal definition: the Faster R-CNN pipeline

Faster R-CNN is four stages: backbone → RPN → RoIAlign → heads.

\text{image}\xrightarrow{\text{backbone+FPN}}\{P_2,\dots,P_6\}\xrightarrow{\text{RPN}}\{\text{proposals}\}\xrightarrow{\text{RoIAlign}}\mathbb R^{256\times7\times7}\xrightarrow{\text{FC heads}}(\text{class},\,\text{box})

It is trained with a sum of four losses: RPN objectness (binary cross-entropy), RPN box regression (smooth-L1 on offsets), final classification (cross-entropy over classes + background) and final box regression (smooth-L1, only for positive proposals). The anchor machinery that the RPN relies on is lesson 6.3.

backbonea classification CNN with its classifier removed (ResNet-50 here), producing feature maps at strides 4–32
FPNfeature pyramid: the same 256 channels at 5 resolutions P2…P6, so each object size has a suitable map
RPNregion proposal network: a 3×3 conv then two 1×1 convs giving, per anchor, an objectness score and 4 offsets
proposalan RPN box that survived decoding and NMS (≈ 1000 per image)
RoIAlignextracts a fixed 7×7×256 block from the right pyramid level, by bilinear sampling
headtwo FC layers (1024 units) then a class layer (K+1) and a box layer (4K)

Common traps
  • "Two-stage" does not mean two networks trained separately. Faster R-CNN is trained jointly; "stage 1" is the RPN, "stage 2" the box head.
  • Proposals are class-agnostic. The RPN only says "object-like". Classes are decided in stage 2.
  • Stride matters. Projecting a box to a stride-32 map without RoIAlign loses precision; a 20×20 map cannot localise a 16-pixel object at all, hence FPN.
  • Runtime scales with the number of proposals. The heads run once per proposal (1000×), which is why fewer proposals speed up inference.
Where it shows up in AI
  • Mask R-CNN (instance segmentation, Module 7) is Faster R-CNN plus a mask head on the same RoIAlign features.
  • Cascade R-CNN, Libra R-CNN and most COCO leaderboard detectors until 2020 are two-stage refinements.
  • Autonomous-driving perception, document layout analysis (tables, figures) and medical lesion detection still often use two-stage models when accuracy matters more than speed.

Check yourself

1. A 224×224 crop is fed to a CNN for each of 2000 proposals. What does Fast R-CNN change so that the CNN runs only once?
It runs the backbone on the entire image once, then maps each proposal onto the resulting feature map (dividing coordinates by the stride) and pools that window to a fixed 7×7 size. The expensive convolutions are shared by all proposals.
2. Why is RoIAlign more accurate than RoI pooling?
RoI pooling rounds the box to integer feature cells (and the bins to integers again), shifting the region by up to a fraction of a cell, which is many pixels at stride 16 or 32. RoIAlign keeps the exact real-valued coordinates and uses bilinear interpolation, so there is no misalignment.
3. How many windows does a 100×100 image need with a 20×20 window and stride 10?
Positions per axis = ⌊(100−20)/10⌋ + 1 = 9, so 9·9 = 81 windows for this single size.

Takeaways

  • Sliding windows need tens of thousands of CNN passes; detection history is about sharing and avoiding work.
  • Faster R-CNN: backbone → (FPN) → RPN proposals → RoIAlign 7×7 → FC heads for class and box.
  • RoIAlign uses bilinear sampling instead of rounding.
  • Two-stage detectors are accurate but slower than single-shot ones.
6.3

Anchors & detection heads

The questionA conv layer outputs numbers per location. An image has an unknown number of objects of unknown sizes at unknown places. How can a fixed-size tensor of outputs represent "three boxes here, none there"? And when 99.9% of all candidate places contain only background, how can the training signal avoid being drowned by the boring majority?

Intuition

Make the problem easier by guessing in advance. At every position of the feature map we lay down a small set of anchor boxes — fixed template rectangles of several sizes and shapes, like a tailor's pattern pieces. The network no longer has to invent a box from nothing. For each anchor it answers two modest questions: "is there an object matching this template?" and "how should I nudge and stretch the template to fit it exactly?" Nudges are small numbers, which are far easier to regress than absolute coordinates.

The training signal comes from matching: compute the IoU of every anchor with every ground-truth box. Anchors with high IoU are told "you are responsible for this object" (positive); those with low IoU are told "you see background" (negative); the ones in between are ignored.

Build it up

Layout. A backbone at stride 64 turns a 512×512 image into an 8×8 grid; each cell centre is an anchor centre. With 3 scales × 3 aspect ratios each cell owns K = 9 anchors, so 8·8·9 = 576 anchors. Width and height from scale s and aspect ratio r = h/w: w=s/\sqrt r,\ h=s\sqrt r, which keeps area s². RetinaNet at 640×640 uses 5 pyramid levels (strides 8…128: 80², 40², 20², 10², 5²) and K = 9: (6400+1600+400+100+25)·9 = 76,725 anchors.

Encoding the offset. For an anchor (c_x^a,c_y^a,w^a,h^a) and a ground-truth box (c_x,c_y,w,h) we regress four numbers. The shifts are divided by the anchor size, so they do not depend on the scale; width and height use a logarithm, so that "twice as wide" is +0.69 and "half as wide" is −0.69, symmetric, and the decoded size is always positive.

Worked example: encoding and decoding

Anchor (cx, cy, w, h) = (200, 200, 128, 128). Ground truth (cx, cy, w, h) = (214, 190, 160, 100).

  • tx = (214 − 200)/128 = 0.109
  • ty = (190 − 200)/128 = −0.078 (up, because y grows downward)
  • tw = ln(160/128) = ln 1.25 = 0.223
  • th = ln(100/128) = ln 0.78125 = −0.247

Decode: cx = 200 + 0.109·128 = 214 ✓; cy = 200 − 0.078·128 = 190 ✓; w = 128·e0.223 = 160 ✓; h = 128·e−0.247 = 100 ✓. (Some codebases divide the targets by "variances" 0.1, 0.1, 0.2, 0.2 to bring them to roughly unit scale: here 1.09, −0.78, 1.12, −1.23.)

The heads. On top of each pyramid level sits a small fully convolutional head applied with shared weights to every location. RetinaNet uses two sibling subnets of four 3×3 conv layers (256 channels) each: the classification subnet ends with a conv giving K·C outputs per location (9·80 = 720), the box subnet ends with K·4 = 36 outputs. A conv is the natural fit: every cell is processed identically, so the output is a map the same shape as the feature map.

The imbalance problem and focal loss. At 76,725 anchors per image, a handful are positive. Plain cross-entropy summed over all anchors is dominated by tens of thousands of easy background anchors, each contributing a small loss that adds up and swamps the few hard ones. Focal loss multiplies cross-entropy by a factor that shrinks as the prediction becomes confident and correct:

\mathrm{FL}(p_t)=-\alpha_t\,(1-p_t)^{\gamma}\,\log(p_t)
Worked example: easy vs hard

pt is the probability the model gave to the correct class. Use γ = 2, and ignore α for the moment.

  • Easy pt = 0.9: CE = −ln 0.9 = 0.105; factor (0.1)² = 0.01 → FL = 0.00105 (100× smaller).
  • Hard pt = 0.1: CE = −ln 0.1 = 2.303; factor (0.9)² = 0.81 → FL = 1.865 (only 1.2× smaller).
  • So the hard example is 22× more important than the easy one under CE, but 1,770× more important under focal loss.
  • Whole image: 76,000 easy background anchors with pt = 0.99 give CE total = 76,000·0.01005 = 764, but focal total = 76,000·(0.01)²·0.01005 = 0.076. One hard positive (CE 2.30) now dominates the sum instead of being 0.3% of it. With α = 0.25 on positives and 0.75 on background (RetinaNet) the balance is fine-tuned further.

The formal definition

t_x=\frac{c_x-c_x^a}{w^a},\quad t_y=\frac{c_y-c_y^a}{h^a},\quad t_w=\ln\frac{w}{w^a},\quad t_h=\ln\frac{h}{h^a}
\mathcal L=\frac1{N_{\text{pos}}}\Big(\sum_{\text{anchors}}\mathrm{FL}(p_t)+\lambda\!\!\sum_{\text{positives}}\mathrm{smoothL1}(t-\hat t)\Big)
cx, cy, w, hcentre and size of the ground-truth box
ca, wa, hacentre and size of the anchor
t = (tx,ty,tw,th)the target offsets the head must predict; \hat t is its prediction
ptpredicted probability of the true class of this anchor (p for a positive, 1−p for background)
γfocusing parameter (2 in RetinaNet); γ = 0 gives ordinary cross-entropy

Matching rules. Faster R-CNN's RPN: IoU ≥ 0.7 positive, < 0.3 negative. RetinaNet: ≥ 0.5 positive, < 0.4 negative. In both, the single best-IoU anchor of each ground truth is always positive, so no object is left without a trainer. SSD uses ≥ 0.5 with hard-negative mining (keep the highest-loss negatives at 3:1) instead of focal loss.

Common traps
  • Anchors are priors, not predictions. They are fixed by design (sizes, ratios, strides); only the offsets and scores are learned. Poorly chosen anchors silently cap recall.
  • Regressing absolute coordinates directly trains badly: the same error of 10 px matters hugely for a small box and not for a large one. Relative offsets fix this.
  • Using γ too large ignores moderately hard examples; γ = 2 is a robust default, but tune α and γ together.
  • Many anchors match one object (several positives): that is intended — and the reason NMS is needed afterward.
Where it shows up in AI
  • Faster R-CNN RPN (9 anchors per location), SSD (8,732 default boxes on 6 feature maps), RetinaNet (focal loss), YOLOv2–v5 (anchors from k-means clustering of box shapes).
  • Focal loss is used well outside detection: medical segmentation with tiny lesions, fraud and anomaly detection with extreme class imbalance.
  • Anchor-free detectors (FCOS, CenterNet, YOLOv8) drop the templates and regress distances from a cell centre to the box sides, keeping the same head-on-feature-map design (lesson 6.4).

Takeaways

  • Anchors are template boxes at every feature-map location; the head predicts class scores and small offsets for each.
  • Offsets (tx,ty,tw,th) are relative shifts and log-ratios, so they are scale-free.
  • IoU against ground truth labels anchors positive, negative or ignored.
  • Focal loss down-weights easy examples so rare hard ones are not drowned.
6.4

Single-shot detectors & FPN

The questionFaster R-CNN reaches 5 frames per second. A self-driving car, a drone or a phone camera needs 30–100. Most of the time goes to a two-step process (propose, then classify each proposal). Can we skip the proposals and read the answer straight off the feature map in a single forward pass? And since objects range from 10 pixels to the whole image, how can one feature map serve them all?

Intuition

Imagine a chessboard laid over the photo. Instead of asking "where are the objects?", we ask every square of the board a simple question: "is the centre of an object inside you, and if so what is it and how big?" One pass of a CNN answers all squares at once, in parallel. That is the single-shot idea, and the board is a grid that coincides with the feature map: a stride-32 map of a 640 px image is a 20×20 grid, each cell covering 32×32 pixels.

The second problem is scale. Deep feature maps (stride 32) know what things are but have blurry positions; shallow ones (stride 8) know exactly where but little about what. A feature pyramid network (FPN) merges them: the deep map is upsampled and added to the shallow one, so every level has both. Small objects are then detected on the fine levels, large ones on the coarse levels.

Build it up

YOLO v1 (2016). The image is divided into an S×S grid. A cell is responsible for an object if the object's centre falls inside it. Each cell predicts B boxes — each (x, y, w, h, confidence) — and one set of C class probabilities. The output tensor therefore has shape

S\times S\times(B\cdot5+C)

For S = 7, B = 2, C = 20 (PASCAL VOC) that is 7·7·30 = 1,470 numbers. Here x, y are the box centre relative to its cell (0…1), w, h are relative to the whole image, and the confidence is trained to equal the IoU between the predicted box and the ground truth (zero if the cell has no object).

Worked example: which cell, which numbers?

Image 448×448, S = 7, so a cell is 64×64. An object has box (x1,y1,x2,y2) = (150, 200, 350, 330). Centre = (250, 265), size 200×130.

  • Column = ⌊250/64⌋ = 3, row = ⌊265/64⌋ = 4, so cell (row 4, col 3) is responsible.
  • x = 250/64 − 3 = 0.906, y = 265/64 − 4 = 0.141 (position inside the cell).
  • w = 200/448 = 0.446, h = 130/448 = 0.290 (fractions of the image).
  • Confidence target = IoU(pred, GT) ≈ 1; the class vector is one-hot.
  • All other 48 cells get confidence target 0 and no class loss.

The cell's 30-vector: [0.906, 0.141, 0.446, 0.290, 1, (second box: 0,0,0,0,0), class one-hot of 20].

The limits of v1: a cell has just 2 boxes and one class, so a flock of small birds in one cell is mostly missed; the final FC layer (50,176 → 4096 holds 205.5 M weights) makes the model huge; and only the last, coarse 7×7 map is used.

SSD (2016) keeps the single-shot idea but predicts from six feature maps of different sizes, using anchors ("default boxes") with a conv head on each. On a 300×300 input: 38², 19², 10², 5², 3², 1² cells with 4, 6, 6, 6, 4, 4 boxes per cell = 5,776 + 2,166 + 600 + 150 + 36 + 4 = 8,732 boxes. Large maps catch small objects, tiny maps catch big ones.

The YOLO family, in one line each. v2: batch norm, anchor boxes from k-means, passthrough layer. v3: three scales (strides 32/16/8), Darknet-53, per-class sigmoids. v4/v5: CSP blocks, PAN neck (top-down and bottom-up paths), mosaic augmentation, CIoU loss. v8: anchor-free and decoupled head — separate branches for box and class. The architecture changes a lot; the idea ("a grid of predictions on pyramid levels, then NMS") stays.

Three pyramid levels, strides 8, 16, 32:

Common traps
  • "Single-shot is always less accurate." Early ones were; with FPN, focal loss or strong training tricks, single-shot models match two-stage ones on COCO at far higher speed.
  • Responsible cell is decided by the centre only. A large object covers many cells, but in v1 only one trains the box; neighbours are told "no object". Modern assigners make several nearby cells positive, which is why NMS stays necessary.
  • Counting predictions wrongly. The number of predictions (8,400) is not the number of detections; almost all are background and filtered by score.
  • FPN is not an ensemble. It is a single network whose levels share a head design; the levels differ in resolution.
Where it shows up in AI
  • YOLOv5/v8/v11 in factories (defect detection), retail shelves, traffic cameras, sports analytics; SSD-MobileNet and YOLO-nano variants on phones and microcontrollers.
  • FPN/PAN necks are in almost every detector and segmentation model (Mask R-CNN, RetinaNet, YOLO, DETR variants).
  • Real-time constraint: 30 fps video means 33 ms per frame; a head that outputs 8,400 predictions in one convolutional pass fits, 1000 proposals through FC heads often does not.

Takeaways

  • Single-shot detectors make all predictions in parallel from a grid on the feature map: S×S×(B·5+C) in v1; per-level maps of box+class channels in modern ones.
  • The cell containing an object's centre (or several near it) is responsible for it.
  • FPN/PAN necks mix fine and coarse features so every scale is handled; 640² input gives 80²+40²+20² = 8,400 predictions.
  • Anchor-free, decoupled heads (YOLOv8) are the modern default.
6.5

Non-maximum suppression

The questionYou trained a good detector and ran it on a photo of one dog. It reports nine boxes around the dog, all with high scores, all slightly different. Which do you keep, and how do you decide automatically? And what if two real dogs stand side by side?

Intuition

Every anchor and every grid cell near an object learns to fire for it. A detector is supposed to produce a cluster of overlapping boxes around each object; our job is to pick the best one per cluster. Think of a talent contest where several judges each submit a rating for the same performer: you want one verdict, the best-rated one, and you want to discard the near-duplicates — but not discard the second performer who happens to stand next to the first.

The rule: take the highest-scoring box; delete every box that overlaps it too much; repeat with what is left. "Too much" is measured by IoU (lesson 6.1) against a threshold.

Build it up

Worked example: greedy NMS on 5 boxes (threshold 0.5)
Box(x1,y1,x2,y2)Score
A(100,100,300,300)0.95
B(120,110,310,310)0.90
D(360,150,500,320)0.80
C(90,120,290,290)0.70
E(420,170,560,330)0.60

Boxes are sorted by score. The IoUs we need (computed as in 6.1): A–B: intersection 34,200, union 40,000+38,000−34,200 = 43,800, so 0.781; A–C: 32,300/(40,000+34,000−32,300) = 32,300/41,700 = 0.775; A–D = A–E = 0 (disjoint); D–E: intersection 80·150 = 12,000, union 23,800 + 22,400 − 12,000 = 34,200, so 0.351.

  1. Pick A (0.95): keep. Compare: B 0.781 > 0.5, suppress; D 0, stays; C 0.775 > 0.5, suppress; E 0, stays.
  2. Pick D (0.80, the best remaining): keep. Compare E: 0.351 ≤ 0.5, stays.
  3. Pick E (0.60): keep. Nothing is left.

Result: A, D, E. Notice E survives although it is probably a duplicate of D: the threshold 0.5 is too high to catch IoU 0.35. With threshold 0.3, E would be suppressed too.

Threshold effects. A low threshold (0.3) removes duplicates aggressively but also kills true neighbours (two people hugging). A high threshold (0.7) keeps crowds but lets near-duplicates through, hurting precision. Usual values: 0.45–0.6, and 0.7 for RPN proposals.

Soft-NMS. Instead of deleting an overlapping box, decay its score by how much it overlaps the kept box: s_j\leftarrow s_j\,e^{-\mathrm{IoU}^2/\sigma} (Gaussian) or s_j(1-\mathrm{IoU}) (linear). A box only falls below the final score threshold if its overlap is large. With σ = 0.5 in our example: B = 0.90·e−0.781²/0.5 = 0.90·0.296 = 0.27; C = 0.70·e−0.775²/0.5 = 0.21; after D is picked, E = 0.60·e−0.351²/0.5 = 0.47 — it survives with a lower score rather than being removed or kept at full strength. This helps crowded scenes.

Class-wise NMS. Run NMS separately for each class, so a "person" box never suppresses an overlapping "backpack" box. Class-agnostic NMS (all classes together) is faster and removes the same object labelled as two classes, but can delete legitimately overlapping objects of different classes.

The formal definition

\mathcal D\leftarrow\text{candidates};\quad\text{while }\mathcal D\neq\emptyset:\ m=\arg\max_{b\in\mathcal D}s_b;\ \ \mathcal K\leftarrow\mathcal K\cup\{m\};\ \ \mathcal D\leftarrow\{\,b\in\mathcal D\setminus\{m\}:\mathrm{IoU}(b,m)\le\tau\,\}
𝒟the pool of candidate boxes still undecided
𝒦the kept boxes (the output)
sbscore (confidence × class probability) of box b
mthe best remaining box
τthe IoU threshold
σsoft-NMS width: larger σ means gentler decay

Complexity: O(n²) IoU computations in the worst case; this is why detectors first drop low-score boxes (e.g. score < 0.05) and cap the number per level (top 1000).

Common traps
  • Applying NMS before the score threshold wastes time (thousands of useless boxes); apply a low score filter first.
  • Using one global threshold for crowded scenes (pedestrians, cells under a microscope) deletes real objects. Use soft-NMS, a higher τ, or a model without NMS (lesson 6.6).
  • NMS is not differentiable and sits outside the training loss, so a model can be good by its loss yet have scores that do not reflect localisation quality. That is why YOLO-style models also predict quality scores.
  • Mixing coordinate formats between the model output and your NMS function gives nonsense IoUs — see lesson 6.1.
Where it shows up in AI
  • The last step of Faster R-CNN (per-class NMS 0.5, and NMS 0.7 on RPN proposals), SSD, RetinaNet, YOLO up to v9 (later versions train NMS-free).
  • torchvision.ops.nms, batched_nms (class-wise via coordinate offsets), TensorRT's NMS plugin — deployment engineers often move NMS onto the GPU because it becomes a bottleneck at high resolution.
  • Related ideas: weighted box fusion (average overlapping boxes instead of picking one), and non-maximum suppression in edge detection and keypoint heat maps.

Takeaways

  • Greedy NMS: keep the top box, delete others with IoU > τ, repeat.
  • τ trades duplicates (high τ) against missed neighbours (low τ).
  • Soft-NMS decays scores; class-wise NMS keeps classes independent.
  • It is needed because many anchors/cells fire on one object; set-prediction models avoid it.
6.6

DETR: detection as set prediction

The questionAnchors, grids, IoU matching rules, NMS: a detector is a pile of hand-designed tricks. Could we just say "here is the image; output the set of objects" and train the network end to end with nothing hand-made in between? And if it outputs a set, how do we compare it with the ground-truth set, when neither has an order?

Intuition

DETR (DEtection TRansformer, 2020) pictures detection as a conversation. The image is turned into a sequence of tokens (the feature-map positions) and read by a transformer encoder. Then 100 learned object queries — think of 100 empty seats, each an "inspector" with a blank notebook — are sent to look at the image through cross-attention. Each inspector returns one answer: a class (or "∅, nothing") and a box. The inspectors also talk to each other (self-attention), so two inspectors learn not to report the same object — which is why no NMS is needed.

Training faces a puzzle. Ground truth is an unordered set of, say, 3 objects; the model gives 100 predictions. Which prediction should be compared with which object? The answer is a one-to-one assignment, chosen to make the total cost as small as possible. That is the Hungarian algorithm. Each real object gets exactly one query; the other 97 queries are trained to say "∅".

Build it up

The cost of pairing query i with object j combines how wrong the class is and how wrong the box is: \mathcal C_{ij}=-\hat p_i(c_j)+\lambda_{L1}\lVert b_j-\hat b_i\rVert_1+\lambda_{\mathrm{giou}}\,(1-\mathrm{GIoU}(b_j,\hat b_i)). A confident correct class and a tight box give a low (even negative) cost.

Worked example: Hungarian matching on a 3×3 cost matrix

Rows are queries Q1–Q3, columns are objects GT1–GT3:

GT1GT2GT3
Q1413
Q2205
Q3322

Why not just pick the cheapest per object? GT1 prefers Q2 (2) and GT2 prefers Q2 (0): two objects claim the same query. We need a one-to-one assignment.

Brute force. There are 3! = 6 assignments (listed as the query for GT1, GT2, GT3): (Q1,Q2,Q3) = 4+0+2 = 6; (Q1,Q3,Q2) = 4+2+5 = 11; (Q2,Q1,Q3) = 2+1+2 = 5; (Q2,Q3,Q1) = 2+2+3 = 7; (Q3,Q1,Q2) = 3+1+5 = 9; (Q3,Q2,Q1) = 3+0+3 = 6. The minimum is 5.

The Hungarian way (O(n³)). Step 1: subtract each row's minimum (1, 0, 2): [[3,0,2],[2,0,5],[1,0,0]]. Step 2: subtract each column's minimum (1, 0, 0): [[2,0,2],[1,0,5],[0,0,0]]. The zeros are the cheap candidate pairs, but they cannot yet form a complete matching (Q1 and Q2 have their only zero in GT2). Cover all zeros with the fewest lines (column GT2 and row Q3). The smallest uncovered value is 1: subtract it from uncovered cells and add it to the doubly covered cell: [[1,0,1],[0,0,4],[0,1,0]]. Now a complete zero matching exists: Q1→GT2, Q2→GT1, Q3→GT3, with original cost 1+2+2 = 5. Same as brute force.

The bipartite loss. After matching, the loss is computed only on matched pairs for the box (L1 and GIoU) and on all queries for the class (matched queries target their object's class, unmatched ones target ∅, usually down-weighted by 0.1 because they are 97% of the queries). The loss is also applied after every decoder layer ("auxiliary losses") to help training.

Why DETR was slow to train: 500 epochs on COCO (to reach 42 AP with ResNet-50), because cross-attention must learn from scratch which spatial position each query should look at; and it is weak on small objects since only the stride-32 map is used. Deformable DETR (attends to a few sampled points on multi-scale maps) and DN-DETR/DINO (denoising queries) fixed both; modern DETR-family models top COCO leaderboards.

The formal definition

\hat\sigma=\arg\min_{\sigma\in\mathfrak S_N}\sum_{i=1}^{N}\mathcal C_{\mathrm{match}}\big(y_i,\hat y_{\sigma(i)}\big),\qquad \mathcal L=\sum_{i=1}^{N}\Big[-\log\hat p_{\hat\sigma(i)}(c_i)+\mathbb 1_{c_i\neq\varnothing}\,\mathcal L_{\mathrm{box}}(b_i,\hat b_{\hat\sigma(i)})\Big]
Nnumber of queries (100); ground truth is padded with ∅ to size N
yi = (ci, bi)the i-th ground-truth object: class (maybe ∅) and box
ŷjthe prediction of query j: class distribution p̂j and box b̂j
𝔖Nall permutations of N elements (N! of them — never enumerated in practice)
σ̂the optimal assignment found by the Hungarian algorithm
𝟙c≠∅box loss only for real objects

Common traps
  • "No NMS" does not mean no post-processing. You still threshold on score and drop ∅ predictions.
  • Queries are not tied to image positions. Query 17 does not always look at the same place; queries specialise statistically (regions, sizes) but are learned vectors.
  • The matching is recomputed every training step with the current predictions; it is not a fixed label assignment, and it is not differentiated through — only the matched pairs' losses are.
  • Do not enumerate permutations. 100! is astronomically large; the Hungarian algorithm (scipy.optimize.linear_sum_assignment) solves it in O(N³) ≈ 10⁶ steps.
Where it shows up in AI
  • DETR, Deformable DETR, DINO, RT-DETR (real-time); MaskFormer/Mask2Former use queries for segmentation (Module 7); SAM's mask decoder is query-based too.
  • Hungarian matching appears in multi-object tracking (associating detections between frames), speaker diarisation, and any "match two unordered sets" problem.
  • Object queries inspired the Perceiver and the Q-Former in vision-language models.

Takeaways

  • DETR: backbone → transformer encoder → decoder with N = 100 object queries → class + box heads; the output is a set.
  • Hungarian matching gives a one-to-one assignment of queries to objects; unmatched queries learn ∅.
  • One-to-one training removes anchors and NMS, at the cost of slow convergence (fixed by deformable/denoising variants).
6.7

Measuring detection

The questionDetector A finds every dog but also draws 50 phantom boxes. Detector B draws only 3 boxes, all perfect, but misses 7 of 10 dogs. Which is better? Accuracy does not apply — there is no single "right answer" per image. We need a number that rewards finding objects, punishes phantoms, punishes loose boxes, and does not depend on one arbitrary confidence cut-off.

Intuition

Every detection has a confidence score, and you choose a cut-off: show only detections above it. Cut high: few boxes, mostly right (high precision) but many objects missed (low recall). Cut low: every object found (high recall) but cluttered with false alarms (low precision). Neither is "the" answer; the honest picture is the whole precision–recall curve as the cut-off slides. Average Precision (AP) is the area under that curve: one number summarising all cut-offs.

Build it up

First, classify every detection against the ground truth at an IoU threshold t (say 0.5). Walk down the list sorted by score:

  • True positive (TP): IoU ≥ t with a ground-truth box of the same class that has not been matched yet.
  • False positive (FP): anything else — a background box (no object), a localisation error (right object, IoU < t), a duplicate (object already matched by a better detection), or a wrong class.
  • False negative (FN): a ground-truth object with no matching detection (counted at the end).

Precision = TP/(TP+FP) = "of the boxes I drew, how many were right"; recall = TP/(number of ground-truth objects) = "of the objects present, how many did I find".

Interpolation. The raw precision zigzags. We replace it by the envelope: at each recall r, the maximum precision achieved at any recall ≥ r (a detector could always have chosen that operating point). At the rows where recall increases (rows 1, 2, 4, 7) the envelope is 1.00, 1.00, 0.75 (best of 0.75, 0.60, 0.50, 0.57, 0.50) and 0.571.

AP = area under the envelope, summing recall steps × envelope height: recall 0→0.2: 0.2·1.00 = 0.200; 0.2→0.4: 0.2·1.00 = 0.200; 0.4→0.6: 0.2·0.75 = 0.150; 0.6→0.8: 0.2·0.571 = 0.114; 0.8→1.0: 0 (never reached). AP = 0.664. (The VOC07 11-point version gives 0.695 for the same list.)

From AP to mAP. AP is per class. mAP averages AP over all classes. COCO's headline metric, mAP@[.5:.95] (written simply AP), additionally averages over ten IoU thresholds 0.50, 0.55, …, 0.95, so it rewards tight boxes: a detector with AP50 = 0.70 may have AP = 0.45. Also reported: AP50, AP75, and APS/M/L for small (< 32²), medium and large objects, plus average recall. COCO samples the curve at 101 recall points and allows 100 detections per image.

  3. Edit the IoU of a row, or change a score so that the order changes (the table re-sorts), and see how a confident false positive near the top hurts AP much more than one at the bottom.
  4. Switch the interpolation to 11-point or 101-point and note the small changes.
Common traps
  • Comparing APs from different protocols. VOC AP50, COCO AP (0.5:0.95) and Open Images AP are not interchangeable; IoU thresholds, interpolation and detection limits differ.
  • AP depends on the ranking of scores, not their calibration. A detector can have excellent AP and badly calibrated probabilities.
  • Duplicates count as false positives. Dropping NMS or setting its threshold too high lowers AP even if every box is "correct".
  • mAP hides failure types. Two models with the same mAP may fail differently (one misses small objects, the other mislocalises). Break down by size, class and error type.
  • Small test sets: AP is noisy, especially for rare classes with few ground truths.
Where it shows up in AI
  • Every leaderboard: COCO test-dev (AP), PASCAL VOC (AP50), LVIS (long-tail AP), Open Images, KITTI/nuScenes (3-D AP).
  • Choosing a deployment threshold: read the PR curve to find the cut-off that gives the precision your product needs (e.g. 95% for an automatic alert) and see what recall remains.
  • The validation loop of YOLO, Detectron2 and MMDetection prints "mAP50-95" every epoch — exactly the metric of this lesson — and model selection uses it.

Check yourself

1. 10 ground-truth objects; a detector returns 8 detections, 6 of them TP. Precision and recall?
Precision = 6/8 = 0.75; recall = 6/10 = 0.60.
2. Two detections, in score order: TP then FP, with 2 ground-truth objects in total. Compute AP (all-point).
After rank 1: P = 1, R = 0.5; after rank 2: P = 0.5, R = 0.5. The envelope is 1 for recall ≤ 0.5. Area = 0.5·1 = 0.5; recall never exceeds 0.5. AP = 0.5.
3. Why is mAP@[.5:.95] lower than mAP@0.5 for the same model?
Stricter thresholds (0.75, 0.9…) turn loosely localised detections from true into false positives, so AP at those thresholds is lower, and the average over all ten thresholds falls below the AP at 0.5 alone.

Takeaways

  • Each detection is TP or FP at an IoU threshold; precision and recall depend on the score cut-off.
  • AP is the area under the (interpolated) precision–recall curve; mAP averages over classes; COCO also averages over IoU 0.5…0.95.
  • Break results down by object size, class and error type, not only one number.
