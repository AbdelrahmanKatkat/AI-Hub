Module 5 · Deep learning for Earth observation

A satellite image is not a photograph. It has more bands than colours, the objects are tiny or enormous depending on the sensor, and the radar version sees through clouds but looks nothing like an optical picture. Here you will adapt a pretrained network to twelve bands, walk a U-Net shape by shape, check a segmentation with Dice and cross-entropy on a 2×2 mask, tile a 928-pixel scene without seams, and see why SAR backscatter must be log-scaled before a network can learn from it.

5.1

Scene & patch classification

The questionA land-use team has 2,000 hand-labelled Sentinel-2 chips of 64×64 pixels, each with 12 spectral bands, and five classes: crop, forest, urban, water and bare soil. A convolutional network trained from random weights memorises the 2,000 chips and fails on new regions. The best published networks were trained on ImageNet photographs with 3 channels (red, green, blue). How can we borrow what they learned when our input has 12 channels?

Intuition

Think of a patch classifier as a reader that looks at the whole chip and answers with one word: "forest". Its first layers learn small, generic detectors: edges, stripes, blobs of a certain colour. Those detectors are useful far beyond ImageNet. What is specific to the photograph world is only the first convolution, because that is the only layer that touches the raw input channels. Everything after it sees feature maps.

So the job is narrow: keep the detectors, replace the layer that reads the channels. The input changes from "3 colours" to "12 spectral bands", and the first layer must accept 12 numbers per pixel instead of 3.

Build it up, step by step

Step 1 — the input. A chip is a 3-dimensional array: 12 bands × 64 rows × 64 columns. Each band is one spectral measurement of the same ground cells (blue, green, red, near-infrared, several red-edge and short-wave infrared bands). Every pixel is now a vector of 12 reflectances.

Step 2 — the pretrained first layer. A ResNet-style first layer is a 7×7 convolution with 64 filters. Each filter has one 7×7 kernel per input channel. With 3 input channels the weight tensor is 64 × 3 × 7 × 7.

Worked example — counting the weights

RGB: 64\cdot3\cdot7\cdot7=\mathbf{9\,408} weights. For 12 bands: 64\cdot12\cdot7\cdot7=\mathbf{37\,632} weights. The difference is 64\cdot9\cdot7\cdot7=28\,224, which is 3136 new weights for every band (64\cdot7\cdot7=3136). Adding the 64 biases, which do not depend on the number of bands, the layer has 37 696 parameters instead of 9 472.

Step 3 — what to put in the new kernels. Random values throw away the pretrained knowledge. A better rule is to make the new layer behave the same as the old one on inputs it has seen. Consider a grey input where all 12 bands equal the same value x. The old layer computes \sum_{c\in\{R,G,B\}} w_c\,x. We want the new layer to give the same answer. Use the mean kernel over the three RGB channels, \bar w=\tfrac13(w_R+w_G+w_B), and copy it to every band, scaled by 3/12. Then the sum over 12 bands is 12\cdot\tfrac{3}{12}\bar w\,x=3\bar w\,x=(w_R+w_G+w_B)\,x. Identical.

Worked example — the adaptation preserves the output

One output position of one filter has RGB weights w=(0.2,\,-0.1,\,0.4) and a grey input x = 0.5 in every band.

Old layer: (0.2-0.1+0.4)\cdot0.5=\mathbf{0.25}.

Mean kernel \bar w=(0.2-0.1+0.4)/3=0.16667; scale 3/12=0.25; each of the 12 new kernels holds 0.25\cdot0.16667=0.041667. New layer: 12\cdot0.041667\cdot0.5=\mathbf{0.25}. The output is unchanged on grey input, and the network starts exactly where the pretrained one stood. Training then lets the bands differ.

Step 4 — the class imbalance. Real land-use data is uneven. Suppose a training set has 900 forest chips and 100 urban chips. A model that always says "forest" scores 90% accuracy and is useless. Two fixes: report balanced accuracy (the mean of per-class recall, here (1+0)/2=50\%), and weight the loss so that rare classes count more: w_c=\frac{N}{K\,n_c}. With N = 1000 and K = 2 this gives w_{\text{forest}}=0.556 and w_{\text{urban}}=5.0: one urban error costs nine times as much as one forest error.

Lab: the multi-band input adapter

Try this
  1. Start with 3 bands. The layer has 9 408 weights. Slide the bands up to 12: watch the parameter counter jump by 3 136 for each band.
  2. Choose replicate mean × 3/12 and set the input to a grey value. The pretrained and adapted outputs match exactly. Switch to random: they no longer agree.
  3. Change the kernel size from 7 to 3 and the filter count. The counter follows the formula Cout·Cin·k² + Cout.
Common traps
  • Band order is part of the model. If the pretrained RGB layer is fed bands in the order B4, B3, B2 instead of B2, B3, B4, the colours are swapped and the features are wrong. Store the band list in the model's metadata.
  • Normalisation must match. ImageNet mean and standard deviation were computed on 8-bit photographs. Sentinel-2 reflectance (÷10000) needs its own per-band statistics computed on training data only.
  • Accuracy hides imbalance. Always print per-class recall or the confusion matrix next to accuracy.
Where it shows up in AI
  • EuroSAT (Sentinel-2, 13 bands, 64×64 chips, 10 land-use classes) and BigEarthNet (Sentinel-2, multi-label, 12 bands) are the standard benchmarks for this recipe.
  • Multispectral foundation models (Module 7) pretrain on all bands directly; the first-layer adapter is the classic cheap alternative when you only have an ImageNet backbone.

Check yourself

1. How many weights does a 64-filter 5×5 first layer have for 12 bands (no bias)?
64·12·5·5 = 19 200 weights.
2. A pretrained RGB kernel set gives output 0.6 on a grey input x = 0.2 in each band. Using the mean × 3/12 rule with 12 bands, what is the adapted output?
The adapted output is the same as the old one on grey input, so 0.6. (Check: the old sum is 3·w̄·x = 0.6, and the new sum is 12 · (3/12) w̄ · x = 3 w̄ · x = 0.6.)
3. A dataset has 800 water and 200 bare-soil chips (K = 2). What are the class weights, and what accuracy does always predicting "water" give?
N = 1000: wwater = 1000/(2·800) = 0.625; wsoil = 1000/(2·200) = 2.5. Always "water" gives 80% accuracy but balanced accuracy of (1 + 0)/2 = 50%.

Takeaways

  • Only the first convolution reads raw channels; adapting it reuses the rest of a pretrained backbone.
  • Replicating the mean kernel with a 3/12 scale keeps the response on grey input exactly unchanged.
  • Weight losses by N/(K·nc) and report balanced accuracy when classes are unequal.
5.2

Semantic segmentation for land cover

The questionA 256×256 tile has 12 bands. Every one of its 65 536 pixels must receive one of five land-cover labels, and the boundary between a field and a river must be placed to within a pixel or two. A classifier that shrinks the image to one vector loses where things are. How can a network produce a full-resolution label map, how many parameters and how much memory does that cost, and how do we score overlap rather than counting correct pixels?

Intuition

Look at a map from far away and you recognise the scene: "that is a city", "that is a lake". Look at it up close and you can draw the coastline exactly, but you no longer see the whole city. A U-Net does both in turn. On the way down (the left arm of the U) it zooms out, halving the resolution at each level and doubling the number of channels so that it can describe larger, more complicated patterns. On the way up (the right arm) it zooms back in, and at each level it receives a skip connection: a copy of the detailed features from the same level on the way down. The skip is the memory of the close-up view, used to draw the edges.

Build it up, step by step

Step 1 — one encoder level. Two 3×3 convolutions with padding 1 (so the size is kept), each followed by a ReLU, then a 2×2 max-pool that halves height and width. Padding 1 is what makes every decoder step line up with its skip.

Step 2 — the bottleneck. The deepest level has the smallest map and the most channels. It knows the most about what is in the tile and the least about exactly where.

Step 3 — one decoder level. A 2×2 transposed convolution doubles the height and width and halves the channels. The result is concatenated with the skip from the matching encoder level, which doubles the channels again. Two 3×3 convolutions then mix the two sources.

Step 4 — the head. A 1×1 convolution maps the final 64 channels to K = 5 class scores at every pixel. A softmax over the classes gives probabilities p, and the label is the arg-max.

Worked example — the shape table for a 256×256×12 tile

Base width 64, four levels, bottleneck 1024, K = 5. Parameters use C_{in}\,C_{out}\,k^2+C_{out} for a 3×3 convolution and 4\,C_{in}\,C_{out}+C_{out} for a 2×2 transposed convolution.

This is why U-Net training is memory-bound, not compute-bound. Batch norm, if added after each convolution, adds 2C parameters per layer; it is omitted here.

The formal definition

For a tile with H·W pixels, K classes, one-hot truth y_{i,c}\in\{0,1\} and predicted probability p_{i,c}, the per-pixel cross-entropy and the soft Dice loss are

\mathcal L_{CE}=-\frac1{HW}\sum_{i=1}^{HW}\sum_{c=1}^{K}y_{i,c}\log p_{i,c}\qquad\mathcal L_{Dice}=1-\frac{2\sum_i p_i\,y_i}{\sum_i p_i+\sum_i y_i}\quad\text{(one class)}

Worked example — Dice and cross-entropy on a 2×2 mask

Class "built-up". Truth y=\begin{pmatrix}1&0\\1&0\end{pmatrix}, predicted probabilities p=\begin{pmatrix}0.9&0.2\\0.6&0.1\end{pmatrix} (read row by row: pixels 1 to 4 are 0.9, 0.2, 0.6, 0.1).

Soft Dice. Overlap \sum p\,y=0.9+0.6=1.5; \sum p=1.8; \sum y=2. Dice =2\cdot1.5/(1.8+2)=3/3.8=0.789, loss 0.211.

Cross-entropy per pixel, -\ln p where y = 1 and -\ln(1-p) where y = 0: pixel 1: -\ln0.9=0.105; pixel 2: -\ln0.8=0.223; pixel 3: -\ln0.6=0.511; pixel 4: -\ln0.9=0.105. Mean =0.236. The uncertain pixel 3 (0.6) costs almost five times as much as the confident pixel 1.

Hard Dice after thresholding at 0.5 gives the mask \begin{pmatrix}1&0\\1&0\end{pmatrix}, which equals the truth: Dice = 1.0. Raise the threshold to 0.7 and pixel 3 becomes 0: TP = 1, FP = 0, FN = 1, Dice = 2/3 = 0.667. The threshold is a decision you make after training, and it can move the score a lot.

Pipeline view. Training is stage 3 (model). Inference is stage 4, which reads the 12 bands, runs the U-Net and writes the probabilities; stage 5 applies the threshold and vectorises the classes.

Common traps
  • Unpadded convolutions shrink the tile at every layer, so the skip and the upsampled map no longer match in size. Either pad, or crop the skip before concatenating.
  • Pixel accuracy is 90% for a map that is 90% forest even if the rare class is never found. Report per-class IoU or Dice.
  • Dice on an empty mask is undefined for a class that is absent from both prediction and truth. Use a small smoothing constant, and say so.
Where it shows up in AI
  • Land cover and crops: U-Net variants on Sentinel-2 tiles produce national land-cover products.
  • Buildings and roads: the same encoder–decoder with skip connections is the default for footprint and road extraction (lesson 5.4 turns the masks into polygons).
  • Medical imaging is where U-Net was born (Ronneberger et al., 2015); the same loss pair is used there.

Check yourself

1. A 3×3 convolution maps 128 channels to 256 with bias. How many parameters?
128·256·9 + 256 = 294 912 + 256 = 295 168.
2. Using the 2×2 mask above but with p = (0.5, 0.5, 0.5, 0.5), what is the soft Dice?
Overlap = 0.5 + 0.5 = 1.0; Σp = 2.0; Σy = 2. Dice = 2·1.0/(2.0 + 2) = 0.5.
3. Why does a U-Net need skip connections rather than only the bottleneck?
The bottleneck has the smallest resolution (16×16 here), so it has lost exact positions. The skips carry full-resolution features from each encoder level so the decoder can place boundaries to within a pixel.

Takeaways

  • A U-Net is a stack of encoder levels (halve size, double channels), a bottleneck, and decoder levels (double size, concatenate skips).
  • For 256×256×12 with base 64 the model has about 31.0 M parameters, dominated by the bottleneck and the decoder's first level.
  • Score overlap with Dice or IoU; choose the threshold on validation data, not by eye.
5.3

Object detection in satellite imagery

The questionA harbour scene is 10 km × 10 km. At 0.5 m ground sample distance (GSD) that is 20 000 × 20 000 pixels, far too large for a detector that takes 512-pixel inputs. A ship is about 20 m long. Should we cut the scene into tiles, or shrink it to a smaller image that fits in one pass? And if we shrink it, does the ship survive?

Intuition

A detector works like a magnifying glass with a minimum useful size: it needs an object to cover enough pixels for its features to say "ship" rather than "a bright speck". Satellite objects are often tiny compared with the scene, so the question is never only "what is the object?" but "how many pixels does it cover?". Tiling keeps the resolution and cuts the scene into pieces the network can hold; shrinking keeps the whole scene but destroys the small objects. Every choice trades one of three things: resolution, context and cost.

Build it up, step by step

Step 1 — how many pixels does the object cover? Pixels across an object = length ÷ GSD.

Worked example — object size in pixels

Ship, 20 m long, 0.5 m GSD: 20/0.5=40 pixels. A 15 m ship at 0.3 m: 15/0.3=50 pixels. The same 20 m ship in Sentinel-2 at 10 m: 20/10=2 pixels, which is a dot. A typical detector needs several feature cells across the object (here we assume at least 8 pixels), so only the first two can be detected reliably.

Step 2 — how much ground does a tile hold? A tile of T pixels covers T\cdot\text{GSD} metres. A 512-pixel tile at 0.5 m covers 512\cdot0.5=256 m.

Step 3 — how many tiles? With overlap O, the stride is s=T-O, and a scene of W pixels needs \lceil (W-T)/s\rceil+1 tiles per side.

Worked example — tile count and the shrinking trade-off

W = 20 000 px, T = 512, O = 64, so stride 448. Per side: \lceil19\,488/448\rceil+1=\lceil43.5\rceil+1=45. Total 45^2=2\,025 tiles.

Shrink the scene to 2 m GSD (5 000 px per side). The ship is now 20/2=10 px, detectable but barely. Tiles per side: \lceil(5000-512)/448\rceil+1=12, total 144. That is about 14 times fewer tiles, but it is the same ship at a fifth of the detail, and a 15 m ship would drop to 7.5 px.

Step 4 — does the ship survive the tile boundary? A tile edge can slice an object in two. If an object of s pixels is placed at random, it lies wholly inside some tile when a tile start falls in an interval of length T-s. With tile starts every T-O pixels, the probability that it is fully inside a tile is

P_{\text{inside}}=\min\!\Big(1,\frac{T-s}{T-O}\Big)
Worked example — the overlap rule

T = 512, object 40 px. With O = 32 (stride 480): \min(1,\,472/480)=0.983, so about 1.7% of ships are cut in every tile that sees them and are missed. With O = 64 (stride 448): \min(1,\,472/448)=1. The overlap must be at least as large as the biggest object you want to keep: here 40 px, so O = 64 is safe.

The formal definition

\mathrm{px}=\frac{L}{g},\qquad \text{ground}(T)=T\,g,\qquad n_{\text{side}}=\Big\lceil\frac{W-T}{T-O}\Big\rceil+1

  2. Change the GSD to 10 m. The ships shrink to 2 px and become grey (too small). Find the GSD at which they turn green again.

Common traps
  • Forgetting the overlap rule. An overlap smaller than the largest object loses those objects silently; the metrics on the tile set will not show it.
  • Duplicates. Objects inside the overlap are detected twice. Merge them in scene coordinates, not in tile coordinates, or the same ship survives twice.
  • Resolution is not a free lever. Downsampling to make the scene fit saves memory and time but removes the very detail that identifies a ship.
Where it shows up in AI
  • Ships and aircraft in DOTA and xView (very high resolution, oriented boxes) are trained on tiles of about 512–1024 pixels with overlap.
  • Vehicles and mining equipment need GSD of tens of centimetres; a 4 m vehicle is a few dozen pixels.
  • Oriented boxes: ships are long and thin at any angle, so axis-aligned boxes waste area; oriented detectors predict an angle as well.

Check yourself

min(1, (256 − 100)/(256 − 16)) = min(1, 156/240) = 0.65. Raise the overlap to at least 100 px to keep every object.
3. A 10 000 × 10 000 px scene with T = 512 and O = 64: how many tiles per side?

Takeaways

  • Pixels per object = length ÷ GSD; decide the detectable minimum before you choose the tiling.
  • Tile at full resolution with an overlap at least as large as the biggest object; shrinking the scene costs small objects.
  • Merge detections in scene coordinates to remove duplicates from the overlap.
5.4

Instance segmentation of buildings

The questionA segmentation network labels every pixel "building" or "not building". Two houses that touch become one blob, and a cadastre needs one polygon per house with its area in square metres. A raw mask gives a staircase outline with hundreds of corners. How do we separate the buildings, turn each one into a polygon with few vertices, and keep the area correct?

Intuition

A semantic mask answers "which pixels are buildings?". An instance answer answers "which building does each pixel belong to?". Once each building has its own mask, the step to a polygon is geometry: walk around the edge of the mask and record the corners. The walk gives a staircase, because pixels are squares. Then we remove corners that do not change the shape much. The tool for that is the Douglas–Peucker simplification, which keeps only the vertices that deviate from the straight line by more than a tolerance.

Build it up, step by step

Step 1 — the contour of a mask. Think of every pixel as a unit square. An edge of the outline is a side of a foreground square whose neighbour across that side is background. Following these edges around gives a closed ring of pixel corners.

Worked example — a 3 × 2 block and an L-shape

A 3-column by 2-row block of building pixels has the ring (0,0)\to(3,0)\to(3,2)\to(0,2): 4 vertices. Shoelace area \tfrac12|\sum(x_iy_{i+1}-x_{i+1}y_i)|=6, equal to the 6 pixels. Good.

An L-shape with the top row full (3 pixels) and one pixel below the left corner: ring (0,0),(3,0),(3,1),(1,1),(1,2),(0,2). Shoelace: 0+3+2+1+2+0=8, area =4, which equals the 4 pixels. The shoelace area of a pixel ring always equals the pixel count, a useful check.

Step 2 — simplify with Douglas–Peucker. Draw a straight line from the first to the last vertex of a chain. Find the vertex farthest from that line. If its distance is larger than the tolerance ε, keep it and repeat on each side; otherwise drop everything between the ends. For a closed ring, first split it at the two vertices farthest apart.

Worked example — Douglas–Peucker on a noisy roof edge

Points P_0=(0,0), P_1=(1,0.2), P_2=(2,-0.1), P_3=(3,0.1), P_4=(4,0). Distances to the line P_0P_4 (the x-axis): 0.20, 0.10, 0.10.

ε = 0.25: nothing exceeds 0.25, so the chain becomes just P_0,P_4: 2 vertices.

ε = 0.16: P_1 (0.20) is kept and splits the chain. Against P_1P_4, P_2 is 0.233 away (kept) and P_3 is 0.033 away. Against P_2P_4, P_3 is 0.150 away, below 0.16, so it is dropped. Result: P_0,P_1,P_2,P_4: 4 vertices.

The distance from point p to the line through a and b is \dfrac{|(b_x-a_x)(p_y-a_y)-(b_y-a_y)(p_x-a_x)|}{\lVert b-a\rVert}. For P_1 against P_0P_4: |4\cdot0.2-0|/4=0.2.

The formal definition

d(p;a,b)=\frac{|(b_x-a_x)(p_y-a_y)-(b_y-a_y)(p_x-a_x)|}{\lVert b-a\rVert_2}\qquad\text{keep }p^\star=\arg\max_p d(p;a,b)\text{ iff }d(p^\star)>\varepsilon
A=\frac12\Big|\sum_{i=0}^{n-1}\big(x_iy_{i+1}-x_{i+1}y_i\big)\Big|\qquad\text{(indices mod }n)

Pipeline view. This is stage 5 (post-processing): the instance masks come from stage 4 (inference), the polygons go to stage 6 (publish) as GeoPackage or GeoJSON in the map's CRS. Area must be computed after reprojection to an equal-area projection, not in degrees.

Lab: from mask to polygon

Try this
  1. Press play: the outline of one building is traced pixel edge by pixel edge, then simplified. Watch the vertex count.
  2. Raise the tolerance from 0 to 1 pixel. The number of vertices falls quickly, the area barely changes. Find where the polygon starts to cut off corners.

Common traps
  • Area in degrees. A polygon in longitude and latitude has a meaningless area. Reproject to an equal-area CRS first.
  • Semantic masks merge neighbours. Use an instance head (Mask R-CNN style) or split touching blobs with distance-transform watershed.
  • Over-simplification rounds off the right angles that buildings actually have. Use tolerance in metres matched to the pixel size, and check the area against the mask.
Where it shows up in AI
  • Cadastre and building inventories (national building footprint datasets) are polygons derived from aerial or satellite masks.
  • Disaster response counts buildings per polygon before and after an event; per-building outcomes need instances, not pixels.
  • Regularisation: modern pipelines also snap edges to right angles; Douglas–Peucker is the first, simplest step.

Check yourself

1. A 2 × 4 pixel block: what are its ring vertices and shoelace area?
Ring (0,0),(4,0),(4,2),(0,2); area = 4·2 = 8, equal to the 8 pixels.
2. Points (0,0), (2,0.3), (4,0). With ε = 0.25, how many vertices remain?
The middle point is 0.3 away from the chord, which is above 0.25, so it is kept: 3 vertices.
3. Why must area be computed after reprojection?
Area is a measure in the units of the coordinates. Degrees of longitude shrink with latitude, so area in degrees is not square metres; an equal-area projection gives correct area.

Takeaways

  • Instances separate touching objects; semantic masks do not.
  • A pixel mask becomes a polygon by tracing its edge and simplifying with Douglas–Peucker.
  • Check the polygon's shoelace area against the pixel count, in an equal-area CRS.
5.5

Deep change detection

The questionAn earthquake hits a town. We have a satellite image from the week before and one from the week after. Subtracting the two pictures finds every pixel that is different, but seasons, haze and sun angle also change pixel values. How do we detect only the buildings that were destroyed or built, and how do we make the two dates comparable before we compare them?

Intuition

Imagine two photographs of the same street, one taken in July and one in January. Subtracting them lights up every tree. What we want is a way to describe each place so that the same ground gives the same description on both dates, whatever the season, and a different description only when the ground has really changed. A siamese network does this with one encoder that looks at both dates. Because the weights are shared, the two feature vectors live in the same space, and their distance measures change.

Build it up, step by step

Step 1 — encode both dates with the same network. For each pixel i we compute f_i^{(1)}=f_\theta(x_i^{(1)}) and f_i^{(2)}=f_\theta(x_i^{(2)}), using the same parameters \theta for both. If the encoders were different, a difference in features could come from the encoders rather than the ground.

Step 2 — measure the distance. The change score is the Euclidean distance between the two features, d_i=\lVert f_i^{(1)}-f_i^{(2)}\rVert_2. Threshold it: pixels with d_i>\tau are "changed".

Worked example — four pixels, two features each
pixelf (date 1)f (date 2)dchanged at τ = 0.5?
1(1, 0)(1, 0)0no
2(0, 1)(0.1, 0.9)√(0.01+0.01) = 0.141no
3(1, 1)(0, 1)√(1+0) = 1.000yes
4(0.5, 0.5)(0.5, 0.6)0.100no

One of four pixels changed: 25%. If the pixels are 10 m, each covers 100 m², so the changed area is 1\cdot100=100\ \text{m}^2 out of 400 m². Pixel 2 has a real but small change, and the threshold correctly ignores it.

Step 3 — train the encoder so the distance means change. Use labelled pairs. The contrastive loss pulls unchanged pairs together and pushes changed pairs apart until a margin m. With Y=1 for changed and Y=0 for unchanged, a common form is \mathcal L=(1-Y)\tfrac12d^2+Y\,\tfrac12\max(0,m-d)^2.

Worked example — the loss on two pairs (m = 2)

Unchanged pair with d=0.141: \tfrac12\cdot0.141^2=0.010. Changed pair with d=1.0: \tfrac12(2-1)^2=0.500. The changed pair produces 50 times the loss, so training concentrates on the rare changes.

Step 4 — the output is a map, not a number. A siamese U-Net (lesson 5.2) produces a feature map per date and the distance at every pixel, so the result is a change mask at full resolution. Class-level damage (destroyed, damaged, intact) needs a second head or a second stage.

The formal definition

xi(1), xi(2)the two co-registered image patches at pixel i, one per date

dichange distance at pixel i

Pipeline view. Stage 2 (preprocessing) must co-register the two dates to a fraction of a pixel and normalise each date; a misregistration of one pixel makes every building edge look changed. Stage 4 (inference) runs the encoder on both dates, stage 5 thresholds the map.

Lab: siamese change map

Try this
  1. Press play. Both dates are encoded, then the distance map fills in row by row. Watch which pixels light up.
  2. Turn on seasonal shift. The raw difference of the two dates lights the whole scene; the encoder's local contrast removes the shift. Compare the two maps.
  3. Move the threshold τ. The changed-area counter shows square metres, using 10 m pixels. Find the τ where the counter matches the building count you can see.
Common traps
  • Change is not damage. Crops harvested, cars moved and clouds all change pixels. Mask out clouds and shadows, and use a label definition that matches the question.
  • Misregistration between dates creates false change along every edge. Check co-registration before training.
  • Class imbalance is extreme: changes are often under 1% of pixels. Use the contrastive or focal losses, or sample changed patches more often.
Where it shows up in AI
  • Damage assessment: xBD and the xView2 challenge score building damage from pre- and post-disaster pairs, with siamese U-Net baselines.
  • Urban growth and deforestation: the Onera Satellite Change Detection (OSCD) benchmark trains siamese networks on Sentinel-2 city pairs.
  • Monitoring: operational forest alerts combine change scores with time series (Module 7).

Check yourself

1. Four pixels have d = 0.3, 0.8, 0.1 and 0.1, and τ = 0.5. Which are changed, and what fraction of the patch changed?
Only the pixel with d = 0.8 is changed (the others are below τ). The fraction is 1 of 4 = 25%.
2. Why do siamese networks share weights between the two dates?
So that identical ground produces identical features on both dates. If each date had its own encoder, the features could differ because the encoders differ, and the distance would not measure change.
3. Using the contrastive loss with m = 2, what is the loss for a changed pair with d = 1.5?
Changed (Y = 1): ½·max(0, 2 − 1.5)² = ½·0.25 = 0.125.

Takeaways

  • A siamese encoder with shared weights makes two dates comparable; the change score is the feature distance.
  • Train with a contrastive loss so the distance means change; threshold it on validation data.
  • Registration, cloud masks and class imbalance decide whether the map is usable.
5.6

Deep learning on SAR

The questionDuring a monsoon, a flood covers half of a district and clouds cover the other half. Optical satellites are blind under cloud. Sentinel-1 radar sees through cloud, but its backscatter values range from 0.001 to above 1, and every pixel carries strong speckle. Feeding the raw numbers into a network is like asking it to read a photograph whose brightness is stored in the wrong units. How do we make SAR learnable, and how do we combine it with optical data?

Intuition

A radar sends a microwave pulse and listens to the echo. A smooth water surface reflects the pulse away from the sensor, so the echo is weak and water looks dark. A building corner acts like a mirror pointing back at the sensor, so it is very bright. Between them lie thousands of intermediate values. Each pixel also mixes many tiny reflections with different phases, which makes the image grainy: speckle. Speckle is not a feature of the ground; it is noise, and it is multiplicative (brighter ground gives brighter speckle).

Build it up, step by step

Step 1 — linear values span too much range. Backscatter \sigma^0 is a power ratio. Its values are small and spread over orders of magnitude, so most of the useful contrast sits in a tiny corner of the scale.

Step 2 — convert to decibels. \mathrm{dB}=10\log_{10}\sigma^0. Every factor of 10 in power is 10 dB, and every factor of 2 is about 3 dB.

Worked example — linear to decibels
σ⁰ (linear)0.0010.010.03160.10.51.0
dB−30.0−20.0−15.0−10.0−3.010.0

The linear range runs over a factor of 1000 (0.001 to 1); the dB range is 30 dB wide and easy to read. Water (very dark) sits near −20 dB and below; bright urban pixels sit around 0 dB and above (the exact values depend on the sensor, polarisation and incidence angle, so treat them as illustrations).

Step 3 — averaging in dB is not averaging in power. Averaging dB values is a geometric mean of the linear values.

Worked example — the mean of four pixels

Linear values 0.02, 0.05, 0.01, 0.10. Their dB values are −16.99, −13.01, −20.00, −10.00. The mean of the dB values is −15.00 dB. But the dB of the mean linear value, 10\log_{10}0.045, is −13.47 dB. The two differ by 1.5 dB because a single bright pixel pulls the power mean up much more than the log mean. Decide which average the question needs, and never mix the two.

Step 4 — why the log helps with speckle. Write an observed pixel as I=\sigma\cdot n, where n is multiplicative speckle with mean 1. Then 10\log_{10}I=10\log_{10}\sigma+10\log_{10}n. The product becomes a sum: the speckle turns into additive noise with a fixed shape, which convolution filters and batch normalisation handle well. The price is a bias: for single-look intensity, E[\ln n]=-\gamma\approx-0.577, so the log of speckle averages about -2.5 dB below the true value. Remember this offset when you compare with a reference.

Step 5 — combine with optical. Stack the two dates or sensors as channels after per-modality normalisation (SAR in dB, optical reflectance scaled separately). Where clouds hide the optical bands, feed a cloud mask as an extra channel so the network learns to lean on SAR there.

The formal definition

\mathrm{dB}=10\log_{10}\sigma^0,\qquad \sigma^0=10^{\mathrm{dB}/10},\qquad I=\sigma^0\cdot n,\quad E[n]=1
σ⁰normalised radar backscatter, a linear power ratio (dimensionless)
dBthe same value on a decibel scale; negative values are common
Iobserved intensity of one pixel (single look)
nmultiplicative speckle with mean 1; its logarithm has mean −γ ≈ −0.577 nepers

Pipeline view. Stage 2 (preprocessing) converts to dB, applies speckle filtering if the model is not learned to handle it, and clips a floor (for example −30 dB) so that a zero value does not produce −∞. Stage 3 trains with SAR and optical channels normalised separately.

  2. Turn on the cloud. Optical goes blank under cloud, SAR does not. Note which pixels SAR still shows.

Common traps
  • Zero or negative values. log(0) is −∞. Clip to a floor before the log and report the floor.
  • Mixing units. Averaging dB values, or subtracting dB and linear, gives numbers with no physical meaning. Name the unit in every channel.
  • Incidence angle. Backscatter depends on the look angle; compare scenes on a normalised scale or include the angle as an input.
Where it shows up in AI
  • Flood mapping from Sentinel-1 with U-Nets (Sen1Floods11 is a standard benchmark) works through cloud, the main reason for SAR in disaster response.
  • Optical–SAR fusion is used for crop type and land cover; the network learns which sensor to trust per pixel.
  • Ship detection from SAR works at night and through weather, a case where tiling (lesson 5.3) meets dB scaling.

Check yourself

1. Convert σ⁰ = 0.25 to dB.

3. Why does a log transform make multiplicative speckle easier to learn from?
The logarithm turns the product σ·n into a sum: 10log10σ + 10log10n. The noise becomes additive with a fixed distribution, which filters and normalisation layers handle well.

Takeaways

  • SAR backscatter is a linear power ratio; convert to dB, clip a floor, and name the unit.
  • Speckle is multiplicative; the log makes it additive, at the cost of a known −2.5 dB bias.
  • Radar sees through cloud: fuse it with optical, and give the network a cloud mask.
5.7

Sliding-window inference & stitching

The questionThe model was trained on 256 × 256 tiles. The product is a land-cover map of a 928 × 928 pixel scene, and next year it must cover a country of 10 000 × 10 000 pixels. Run the network on the whole scene and the memory explodes; run it on tiles and the seams between tiles show as lines in the map. How do we predict a huge scene from a small window without visible seams?

Intuition

Slide a window across the scene, predict each window, and paste the answers together. Two details make the difference between a clean map and a patchwork. First, the windows must overlap: a network is least reliable at the edge of its input, where it has seen less context. Second, where windows overlap, the answers must be blended, with the centre of each window trusted most. A map built this way is like a mosaic of photographs taken with overlapping fields of view.

Build it up, step by step

Step 1 — the tile grid. Use tile size T = 256 and overlap O = 32. The stride is T-O=224. Tile starts are 0, 224, 448, 672, and the last tile ends at 672+256=928, exactly the scene width. Four tiles per side, 16 in total.

Step 2 — the blend weight. Give each pixel in a tile a weight that grows toward the centre: for local column j (0 to 255), w(j)=\min(j+1,\;T-j). Columns near the edge get small weight, the centre gets the most.

Worked example — one seam column

Scene column 240 lies in two tiles. In tile A it is local column 240 (start 0), weight \min(241,16)=16. In tile B (start 224) it is local column 16, weight \min(17,240)=17. Predicted probabilities: p_A=0.8, p_B=0.6.

Blended: \dfrac{16\cdot0.8+17\cdot0.6}{16+17}=\dfrac{23.0}{33}=\mathbf{0.697}.

If instead each tile simply overwrites the previous one, the value jumps from 0.8 to 0.6 at column 224, a visible seam of 0.2. The blended map changes smoothly across the overlap.

Step 3 — accumulate, then divide. Keep two arrays the size of the scene: S (weighted sum of probabilities) and W (sum of weights). Each tile adds to them. At the end, P=S/W, and the class is the arg-max of P.

Step 4 — the memory bill. A 10 000 × 10 000 scene with 5 classes in float32 costs 10^8\cdot5\cdot4=2\,\text{GB} (1.86 GiB) for probabilities alone, before any model memory. Do not hold it in RAM: write each finished window to a Cloud-Optimised GeoTIFF block by block (Module 1), and keep only the arg-max as a uint8 class map (100 MB for the same scene).

Pipeline view. This is stage 4 (inference) with its output going to stage 5 (post-processing: arg-max, vectorisation) and stage 6 (publish as COG).

S(x,y)=\sum_t w_t(x-a_t,\,y-b_t)\,p_t(x,y),\qquad W(x,y)=\sum_t w_t(x-a_t,\,y-b_t),\qquad P=\frac SW

Lab: sliding-window inference

Try this
  1. Press play in hard mode: each tile paints over the last. Look at the cross-section below the map: the profile jumps at every tile border.
  2. Switch to blend and let it finish. The jumps shrink to small wiggles. Drag the overlap to 0: the blend has nothing to blend with and the seams return.

Common traps
  • Unweighted averaging treats the tile border as reliable. Use the triangular or Gaussian weight so the centre dominates.
  • Edge effects are real. A tile border predicts worse than its centre; with overlap 0 the seams are visible. A practical starting point is an overlap of roughly 10–25% of the tile, then tuned on validation tiles.
  • Scene edges. The last tile must be clamped to end at the scene edge, otherwise the last strip is never predicted.
Where it shows up in AI
  • Country-scale land cover is produced with exactly this loop, writing COG blocks in parallel (Module 9 covers the scaling).
  • Medical whole-slide images use the same overlap-and-blend idea: a slide is far too large for the network at once.
  • Test-time augmentation averages predictions of flipped copies, which is the same weighted-average idea applied to variants rather than neighbours.

Check yourself

1. A 1000-pixel scene with T = 256 and O = 32: how many tiles per side?
⌈(1000 − 256)/224⌉ + 1 = ⌈3.32⌉ + 1 = 5 tiles per side (25 in total). The last start is clamped to 744 so that it ends at 1000.
2. Column 230 is local column 230 of tile A and local 6 of tile B (start 224), with p_A = 0.9 and p_B = 0.5. What is the blended probability?
w_A = min(231, 26) = 26; w_B = min(7, 250) = 7. P = (26·0.9 + 7·0.5)/33 = (23.4 + 3.5)/33 = 26.9/33 = 0.815.
3. Why keep only the arg-max as a uint8 class map for a 10 000² scene?
Five float32 probability layers need 2 GB; one uint8 class map needs 100 MB. The probabilities are needed only for thresholds or uncertainty, which can be stored separately.

Takeaways

  • Tile with an overlap, blend with a weight that peaks at the tile centre, and divide the accumulated sums at the end.
  • Predict edges with less context; the overlap and the blend are what hide that.
  • Stream results to COG blocks; keep the class map small.
