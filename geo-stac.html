Module 2 · Finding data with STAC

Before a model can learn from Earth imagery, you have to find the right scenes. STAC is the shared language that archives use to describe what they hold: where, when, how cloudy, and which file is which. By the end you will read a STAC Item line by line, check a search by hand, build a request body for a STAC API, turn search results into a time stack, and validate a catalogue you publish yourself.

7 lessons≈ 2 hoursNeeds Modules 0–1 (maps, CRS, rasters)
2.1

What STAC is and why it exists

The questionYou need every Sentinel-2 image over a field in Egypt from March 2026 with less than 10% cloud. The imagery sits in several archives. Each has its own website, folder names, file names and metadata format. How do you ask all of them the same question and get back answers you can process, without downloading anything first?

Intuition

Think of a library card catalogue. A book on a shelf has a title, an author, a date and a shelf mark. The card describes the book without being the book. Before standard cards, every library had its own system and you had to walk the stacks. A shared card layout means one search works everywhere.

STAC (SpatioTemporal Asset Catalog) is that card for Earth data. For each image, or group of images, it stores a small JSON record that says where the data covers (a footprint on the map), when it was captured, what it is (properties such as cloud cover, sensor or projection), and where the bytes are (links to the files). Because the record has the same shape everywhere, one program can search many archives.

Notice what a STAC record is not: it is not the image. A record is a few kilobytes; the image can be gigabytes. Searching metadata is cheap and downloading is expensive. STAC exists so that you can do the cheap part first.

Build it up: the problem, one piece at a time

Step 1: a file is not findable. A GeoTIFF holds pixels and a little georeferencing, but nothing that lets a search answer "is this over Egypt in March?" without opening the file. We need metadata sitting beside the file.

Step 2: one record per scene. We write a record for each scene: its footprint, its time, its cloud cover and its file links. STAC calls this an Item. An Item is a GeoJSON feature, a standard JSON way to write a map object with a geometry and properties.

Step 3: group the items. Scenes from the same satellite and processing level belong together. That group is a Collection. It adds shared facts such as the licence, the provider and the overall extent in space and time.

Step 4: organise the collections. A provider lists its collections in a Catalog. A catalog can hold catalogs, collections and items, so a whole archive becomes a tree you can walk.

Step 5: one door to search. A STAC API is a web service that searches every item in a catalogue by place, time and properties. You send a request body and get back the matching items, a page at a time (Lesson 2.5).

Worked example: why metadata first saves data

Suppose a search returns 3 Sentinel-2 scenes, each stored with 12 bands at full 10 m resolution. One scene is 10 980 × 10 980 pixels, with 12 bands and 2 bytes per pixel:

10980\times10980\times12\times2 = 2\,893\,449\,600\text{ bytes}\approx 2.69\text{ GiB}

Downloading the three scenes in full would cost about 3\times2.69\approx 8.1 GiB. The search itself returns three JSON records of a few kilobytes each. The search answers "which three?" before you pay for any pixels.

The formal definition

STAC describes four kinds of entity. Each Catalog, Collection and Item is a JSON object whose type field says which kind it is:

EntitytypeWhat it describesExample
Catalog"Catalog"a set of children (catalogs, collections, items) and links to them"Demo Earth archive"
Collection"Collection"a group of items with a shared licence, providers and extent"Sentinel-2 L2A"
Item"Feature"one observation: footprint, time, properties and assetsone scene captured on 14 July 2026
Asset(inside an item; no type field)one downloadable file belonging to an itemthe red band as a GeoTIFF

The surprise is the Item's type: "Feature", because an Item is a GeoJSON feature. Any tool that already reads GeoJSON can draw its footprint without knowing anything about STAC.

typewhich kind of object this is (see the table above)
stac_versionthe version of the STAC core specification the record follows, for example "1.0.0"

linksa list of pointers to related documents (Lesson 2.2)
assetsa map from short keys to files (Lesson 2.3)
Pipeline positionStage 1, Acquire. STAC stores only metadata. The pixels stay in the cloud archive, and the step reads the catalogue, not the imagery.

Lab

  1. Press play and watch the browser open the catalog, then a collection, then an item, then its assets. Each step follows one link. Read the caption at each step.
  2. Click the asset B04. Its role and href tell you what a tool would download. Nothing else is fetched.

Common traps
  • "The record is the data." It is not. The Item points to files through its assets. If those links break, the metadata still exists but you cannot use the pixels.
  • "STAC is a file format." It is a set of JSON conventions built on GeoJSON. The same records can be served as static files on a web server or through an API.
  • "One catalogue equals one archive." A catalogue can point to collections hosted elsewhere, and an Item's assets can live on a different server from the catalogue.
Where it shows up in AI
  • Major Earth observation archives publish STAC: for example Microsoft Planetary Computer, Element 84 Earth Search, and NASA and USGS catalogues. A dataset for a model begins as a search in one of them.
  • A training manifest (Module 3) should record the item ids it was built from, so that someone else can rebuild the same set.

Check yourself

1. Where is a scene's cloud cover stored: in the Item or in one of its asset files?
In the Item's properties (here as eo:cloud_cover, a field from the eo extension, Lesson 2.4). You read it from the small JSON record without opening any image file.
2. Why can a GeoJSON-only tool still show a STAC Item's footprint?
An Item has "type": "Feature" and a GeoJSON geometry, so the footprint is standard GeoJSON. The STAC-specific parts (links, assets) are extra fields the tool can ignore.
3. Three scenes of 2.69 GiB each are found by a search. Roughly how much data does the search itself transfer, compared with downloading them?
Only the three JSON records, a few kilobytes each: well under a megabyte. Downloading the scenes would be about 8.1 GiB.

Takeaways

  • STAC is a shared card catalogue for Earth data: footprint, time, properties and file links in one small JSON record.
  • The four entities are Catalog, Collection, Item and Asset; the STAC API adds one search endpoint over them.
  • Search the metadata first. Pixels are downloaded only after you know which scenes you want.
2.2

Catalogues and collections

The questionA provider's root catalogue lists 40 collections, and each collection holds thousands of items. You want the Sentinel-2 collection and nothing else. How does a program find it, and how does it know where to go next, without fetching every file on the server?

Intuition

Picture a forest of folders, each with a signpost at the entrance. The signpost at the root says "Sentinel-2 this way, Landsat that way". Each folder has its own signposts for what is inside. You never need a map of the whole forest; you only read the signs at the place you stand. A STAC catalogue works the same way: every document lists its neighbours as links.

Two document types do the signposting. A Catalog lists children and has no extent of its own. A Collection is a catalog-like document that also describes the items it holds: their shared licence, the providers, and an extent, a box in space and a span in time that covers them all.

Build it up: following signposts

Step 1: the root. Every catalogue has one entry document, usually catalog.json. It has a links list. Some entries have "rel": "child", meaning "a sub-document you may open".

Step 2: a child. Opening a child collection gives you its own links: a parent link to climb back, and item links to each item it contains.

Step 3: read the link, not the path. Programs never guess file names. They look for a link whose rel they want, then follow its href. The type says what the target file is, so a tool knows whether to parse it as JSON or GeoJSON.

Here is a small catalogue for this course. It is synthetic, but its structure is the one real providers use.

{

  "title": "Demo Earth archive",
  "description": "Synthetic catalogue for teaching. Not a real archive.",

    {"rel": "root", "href": "./catalog.json", "type": "application/json"},
    {"rel": "self", "href": "./catalog.json", "type": "application/json"},

    {"rel": "child", "href": "./demo-landsat-l2/collection.json", "type": "application/json", "title": "Landsat L2 (demo)"}
  ]
}

Worked example: the extent check by hand

Is an observation of Egypt on 15 March 2026 covered by this collection? The point is longitude 31.2°E, latitude 30.0°N, and the time is 2026-03-15.

Spatial: the extent box is [minx, miny, maxx, maxy] = [−180, −56, 180, 84]. We need -180\le 31.2\le 180 and -56\le 30.0\le 84. Both hold.

Temporal: the interval is [2026-01-01, open end]. The date is after the start and there is no end, so it holds.

Therefore the point lies inside the collection's extent. This says only that the collection may hold the observation. The items are the authority, and Lesson 2.5 checks them one by one.

The formal definition

A STAC link is a small JSON object. Its meaning is set by rel, and its target by href. The common relation types are:

relPoints from… to…Typical use
rootany document → the top cataloguestart a crawl again from the top
selfa document → its own locationknow where this copy lives
parenta document → the document one level upclimb the tree from a deep item
childa catalogue → a sub-catalogue or collectionwalk down the tree
itema collection → one of its itemslist the items of a collection
collectionan item → the collection it belongs tofind the licence and providers of an item
nexta search response → the next page of resultspagination (Lesson 2.5)
hrefthe address of the target; relative (./items/…) or absolute (https://…)
typemedia type of the target: application/json for a catalogue, application/geo+json for an item
extent.spatial.bboxa list of boxes [minx, miny, maxx, maxy] in longitude/latitude (WGS 84)
extent.temporal.intervala list of [start, end] pairs in UTC; null means open-ended
licensean SPDX identifier such as CC-BY-4.0, or a special value such as proprietary

The whole archive, as a tree, looks like this. The boxes are the documents; the lines are the links you follow:

demo-earth-archive/               Catalog     catalog.json
├── demo-sentinel-2-l2a/          Collection  collection.json
│   └── items/
│       ├── S2B_DEMO_20260714_T31UFT_L2A.json   Item  (footprint, time, properties)
│       │     └── assets: B04.tif, visual.tif
│       └── S2A_DEMO_20260701_T31UFT_L2A.json   Item
└── demo-landsat-l2/              Collection  collection.json
    └── items/ …
Worked example: the cost of walking the tree

To list the 3 items of the Sentinel-2 collection without a search, a client fetches: the root catalogue (1), the collection (2), and each item (3 more). That is 1+1+3=5 requests. The assets of each item are listed inside that item, so they need no extra requests. A single search request could return the same three items in one go (Lesson 2.5).

Pipeline positionStage 1, Acquire. The catalogue is walked by reading small documents; no pixels are touched.

Lab

Try this
  1. Start at the root. Read the links and their rel labels. Click a child link to go down into the Sentinel-2 collection.
  2. Use the filter to show only item links. How many items does the collection list?
  3. Open an item and press its parent link. Then press root. Notice that the root is always one link away from every document.
  4. Find the extent check in the worked example. Move the point and watch whether it falls inside the box.
Common traps
  • Extent is a summary, not a proof. A collection's bbox and interval should cover its items, but a loose or stale extent is common. Check the items when you need exact coverage.
  • Relative links move with the file. ./items/… keeps working when a folder is copied; an absolute https://… link keeps pointing at the old place.
  • The licence describes the terms you must check. CC-BY-4.0 in the collection is a claim about the data. Read the provider's terms before you redistribute anything.
  • Summaries are not everything. A collection's summaries list the values seen across items, which are handy but may not be complete.
Where it shows up in AI
  • A crawler that builds a dataset walks catalogues like this one and keeps the item links it needs. Browser tools for STAC show the same tree to people.
  • Model catalogues (Module 6) reuse the same tree: a model is an item, and a family of fine-tuned models is a collection linked to its base model.

Check yourself

1. From an item, which link leads to the licence and providers of its data?
The collection link (the parent link usually points to the same collection, but collection is the one that names the relationship). Licence and providers live on the collection.
2. The collection extent is [−10, 35, 5, 45] (minx, miny, maxx, maxy). An item footprint is [4, 36, 6, 37]. Is the item inside the extent?
No. minx 4 ≥ −10 and miny 36 ≥ 35 hold, but maxx 6 is greater than 5, so the item sticks out on the east side by 1 degree of longitude.
3. How many requests does a client need to list 2 items in a collection, starting from the root catalogue?
1 (root) + 1 (collection) + 2 (items) = 4 requests.

Takeaways

  • Catalogues and collections are documents that link to their neighbours; you walk the tree by following links with the rel you want.
  • A collection's extent and licence are shared facts that describe the items, but the items are the real record.
  • Relative hrefs make a catalogue portable; the tree costs one request per document.
2.3

Items and assets

The questionA satellite pass captured 13 bands, a true-colour preview, a cloud mask and a metadata file, all over one area on one afternoon. What single record tells a program where the pass was, when it happened, what was measured and which file holds each part?

Intuition

Think of a postcard. The picture on the front shows the place (the footprint). The back gives the date and the details written in the margin (the properties). The stamps and the postmarks are the physical files, and each stamp is one asset. The postcard is light; the letters inside the envelope are the heavy part. An Item is the postcard, and its assets are the stamps.

Build it up: reading an Item line by line

Step 1: the front, the footprint. The geometry is a GeoJSON polygon: the true outline of the image on the ground, as a ring of [longitude, latitude] pairs. Longitude comes first, as in GeoJSON. The ring is closed: the last point repeats the first.

Step 2: the box around the footprint. The bbox is the smallest axis-aligned rectangle that contains the geometry, written as [minx, miny, maxx, maxy]. It is cheap to test, so search engines use it first. Lesson 2.5 will check one by hand.

Step 3: the back, the properties. properties.datetime is the capture time in UTC. Other properties describe the scene: the platform, the instruments, the ground sample distance gsd, the cloud cover, the projection. Some properties come from extensions, which Lesson 2.4 explains.

Step 4: the stamps, the assets. Each entry in assets has a short key (here B04 and visual) and points to one file through href. Its type is the media type, and its roles say what the file is for: data for measurements, visual for a picture for people.

{
  "type": "Feature",
  "stac_version": "1.0.0",
  "stac_extensions": [
    "https://stac-extensions.github.io/eo/v1.1.0/schema.json",
    "https://stac-extensions.github.io/projection/v1.1.0/schema.json"
  ],
  "id": "S2B_DEMO_20260714_T31UFT_L2A",
  "collection": "demo-sentinel-2-l2a",
  "geometry": {
    "type": "Polygon",
    "coordinates": [[[10.6, 48.2], [11.9, 48.2], [11.9, 49.2], [10.6, 49.2], [10.6, 48.2]]]
  },
  "bbox": [10.6, 48.2, 11.9, 49.2],
  "properties": {
    "datetime": "2026-07-14T10:31:22Z",

The formal definition

\text{bbox}=[\min x_i,\ \min y_i,\ \max x_i,\ \max y_i]\quad\text{over all vertices }(x_i,y_i)\text{ of the geometry}
(xi, yi)a vertex of the footprint: x is longitude, y is latitude (degrees)
min, maxthe smallest and largest value over all vertices
bboxthe axis-aligned box, written as [west, south, east, north] in STAC order

The rule is that the bbox must contain the geometry. A footprint tilted 20° on the ground needs a bigger box than the footprint itself, so the bbox is always at least as large.

Worked example: computing the bbox by hand

The ring has the vertices (10.6, 48.2), (11.9, 48.2), (11.9, 49.2), (10.6, 49.2), (10.6, 48.2).

Longitudes: 10.6, 11.9, 11.9, 10.6. So \min x = 10.6 and \max x = 11.9.

Latitudes: 48.2, 48.2, 49.2, 49.2, 48.2. So \min y = 48.2 and \max y = 49.2.

Therefore bbox = [10.6, 48.2, 11.9, 49.2], exactly the value written in the item. A footprint that is a rotated quadrilateral would give the same kind of calculation, with a larger box.

Assets: the files behind the record

Each asset is a small object inside assets. Its key (B04) is only a name inside this item, so a different provider may call the same band red. The most useful fields are:

hrefwhere the file is. Relative to the item's own file unless it starts with http
typemedia type. A Cloud-Optimised GeoTIFF is image/tiff; application=geotiff; profile=cloud-optimized
roleswhat the file is for: data (measurements), visual (a picture), thumbnail, overview, metadata, and others
titlea human-readable label
Pipeline positionStage 1, Acquire. The Item is the record that says which assets to read. Stage 2 (Lesson 2.6) reads only the windows it needs from those files.

Lab

  2. Turn the tilt slider up. The footprint rotates on the ground, and the bbox grows around it. Watch the gap between footprint and box appear.

Common traps
  • bbox order. STAC writes [minx, miny, maxx, maxy], which is [west, south, east, north]. Many people write latitude first because they think "lat, lon". Swapping them still produces four valid numbers, so only a check against the geometry catches it.
  • Geometry is always longitude/latitude. The footprint is stored in WGS 84 degrees even when the pixels are in a UTM projection. The projection of the pixels is a separate property (proj:epsg, Lesson 2.4).
  • Times are UTC. 2026-07-14T10:31:22Z ends in Z for UTC. A local time without the suffix is ambiguous and can shift a scene to the wrong day.
  • Asset hrefs are relative to the item. Moving the item file without its assets breaks every relative link.
Where it shows up in AI
  • A dataset builder keeps item ids and asset keys in its manifest. Training then reads B04 from every item in the same way.
  • Footprints are used to decide which scenes overlap a label polygon before any pixels are read. A wrong bbox silently drops good scenes from training.

Check yourself

1. An item's geometry has longitudes 3.0, 4.5, 4.5, 3.0 and latitudes 52.0, 52.0, 53.1, 53.1. What is its bbox?
[3.0, 52.0, 4.5, 53.1]: minx 3.0, miny 52.0, maxx 4.5, maxy 53.1.
2. Which field tells you when the image was captured, and in which time zone is it written?
properties.datetime, written in UTC (the trailing Z).
3. Two providers name the red band B04 and red. Which field lets a tool match them without knowing the key?
The band metadata: in the eo extension, each band object has a common_name such as red. The asset key itself is only a name local to the item.

Takeaways

  • An Item is a GeoJSON feature: geometry, bbox, datetime and properties, plus a map of assets to files.
  • The bbox is the box around the geometry, stored as [minx, miny, maxx, maxy] in degrees; it must contain the footprint.
  • Assets say which file is which, through href, type and roles. The key is a local name.
2.4

STAC extensions (eo, proj, raster, …)

The questionEvery provider can say where and when a scene was taken. But the cloud cover, the band wavelengths, the projection and the raster shape are facts that only some data has. If the core standard had to list every such fact, it would never stop growing. How do you add domain-specific fields without breaking tools that have never heard of them?

Intuition

Imagine a standard postcard template. Every postcard has a front, a back and a stamp area. Now a postal service wants a sticker that says "fragile" or "express", but only for some parcels. It prints a sticker sheet, and each parcel that uses it lists the sheet on its label. A clerk who knows the sheet reads the stickers. A clerk who does not still delivers the parcel, just without the extra instructions.

STAC extensions are those sticker sheets. The core defines the template: id, geometry, bbox, datetime, assets. An extension such as eo (electro-optical imagery) adds fields about cloud cover and bands. Its fields carry a prefix, eo:, so the origin of each field is visible at a glance.

Build it up: from core to a declared extension

Step 1: start from core. The core needs only a few things. Any record with those fields is a valid Item, whatever its sensor.

Step 2: add a prefixed field. A Sentinel-2 provider adds eo:cloud_cover, a percentage of the scene covered by cloud. The prefix eo: says the field's definition comes from the eo extension.

Step 3: declare the extension. The record lists the schema URL of every extension it uses in stac_extensions. The URL names the extension and its version. A reader looks up the URL, learns what the prefixed fields mean and what is required, and then reads them.

Step 4: ignore what you do not know. A tool that understands only core can still read the geometry, the time and the assets. The extension fields are extra information it may skip. This is why extensions do not break old tools.

The fields you will meet most often, with the extension that defines them:

FieldExtensionMeaning and type
eo:cloud_covereopercent of the scene that is cloud, a number from 0 to 100
eo:bandseoa list of band objects, each with name, common_name (e.g. red) and center_wavelength in micrometres
proj:epsgprojectionthe EPSG code of the pixels' coordinate system, e.g. 32632 (WGS 84 / UTM zone 32N)
proj:shapeprojectionthe raster size in pixels as [rows, cols]
raster:bandsrasterper-band facts such as the data type, the no-data value, and scale and offset
Worked example: a band object by hand

The red band of Sentinel-2 sits near 665 nm. In micrometres that is 665\text{ nm}=665\times10^{-3}\ \mu\text{m}=0.665\ \mu\text{m}. The asset for that band can carry its band object, shown here with values rounded for teaching:

"B04": {
  "href": "./B04.tif",
  "type": "image/tiff; application=geotiff; profile=cloud-optimized",
  "roles": ["data"],
  "eo:bands": [
    {"name": "B04", "common_name": "red", "center_wavelength": 0.665}
  ]
}

A search for "the red band" can now match common_name = "red" across providers, even when one calls the asset B04 and another calls it red.

The formal definition

An extension is defined by three things: a schema at a URL that lists its fields, a prefix that every one of its fields starts with, and a rule about which fields are required. A record uses an extension by listing its URL:

\texttt{stac\_extensions}=[\,U_1,\dots,U_k\,]\quad\text{and every field }p\!:\!f\text{ must have }p\text{ declared by some }U_j
Ujthe URL of an extension schema, including its version, e.g. https://stac-extensions.github.io/eo/v1.1.0/schema.json
p:fa field: the prefix p names the extension, the rest f names the field (e.g. eo:cloud_cover)
declaredthe prefix's extension URL is in stac_extensions

The version in the URL matters. A later version can add, rename or constrain fields. A record and its validator should agree on the version they use.

Pipeline positionStage 1, Acquire. Extensions are what let Stage 2 (preprocessing) decide how to align bands (proj:epsg) and which band is red (eo:bands) before anything is read.

  4. Switch on raster and read raster:bands. Note that it is a list per band, not a single value.
Common traps
  • Using a prefixed field without declaring it. Writing eo:cloud_cover and forgetting the eo URL makes the field's meaning unverifiable. A strict validator rejects it.
  • Assuming extension fields are always required. Each extension says which of its fields are required. Many, such as eo:cloud_cover, are optional and may be missing for some items.
  • Mixing versions. v1.0.0 and v1.1.0 of the same extension can differ. Use the version your tools validate against.
  • Treating name as a band meaning. name is the provider's own label; common_name is the shared vocabulary for matching bands.
Where it shows up in AI
  • The MLM extension (Module 6) uses the same mechanism: a model's record declares the mlm: fields, so a runner can read its input bands and patch size.
  • proj:epsg and eo:bands decide whether a training stack needs reprojection and which channel becomes which network input (Modules 3 and 5).

Check yourself

1. A record has "eo:cloud_cover": 8 but its stac_extensions lists only the projection URL. What is wrong, and how do you fix it?
The eo prefix is not declared, so a strict validator flags the field and a reader cannot be sure that 8 means cloud percent in the eo sense. Fix it by adding the eo schema URL to stac_extensions.
2. The geometry is in longitude/latitude, but proj:epsg is 32632. Why do both matter?
The geometry is always WGS 84 degrees for footprints. The pixels of the asset are in EPSG 32632 (WGS 84 / UTM zone 32N), a metre-based system. Stacking or measuring pixels needs that projection, not the lon/lat footprint.
3. Red light is about 665 nm. What value does center_wavelength take if its unit is micrometres?
0.665 (since 665 nm = 0.665 µm).

Takeaways

  • The core is a shared template; extensions add prefixed fields for a domain, such as eo: or proj:.
  • A record declares each extension by its versioned schema URL in stac_extensions; undeclared prefixes are a validation error.
  • Tools that know nothing about an extension can still read the core fields. Pin the version your tools use.
2.5

The STAC API & search

The questionYou want every Sentinel-2 scene over a box 0.8° wide and 0.6° high, south of Munich, captured between 1 June and 31 August 2026, with less than 20% cloud. The archive holds hundreds of thousands of scenes. How do you ask for exactly those, in one request, and what do you do when the answer is longer than one response?

Intuition

A STAC catalogue on disk means reading documents one by one (Lesson 2.2). A STAC API is a search engine on top of the same records. You describe what you want in a request body. The server runs three filters, one after another, and returns the matching items a page at a time.

The three filters are the same questions you would ask by hand: does the footprint intersect my box? Does the capture time fall inside my interval? Does a property (cloud cover) satisfy my condition? The server does not need to open any image to answer them.

Build it up: one request, three filters

Step 1: the request body. A search is a POST to the /search endpoint with a JSON body. Here is the request for our question:

{
  "collections": ["demo-sentinel-2-l2a"],
  "bbox": [10.8, 48.4, 11.6, 49.0],
  "datetime": "2026-06-01T00:00:00Z/2026-08-31T23:59:59Z",
  "limit": 50,
  "filter-lang": "cql2-json",
  "filter": {
    "op": "<",
    "args": [{"property": "eo:cloud_cover"}, 20]
  }
}
collectionsa list of collection ids to search; without it the server searches everything it holds
bboxa search box [minx, miny, maxx, maxy] in longitude/latitude. The alternative is intersects, a GeoJSON geometry, but not both at once
datetimean interval start/end in UTC. An open end is written ..; a single instant is written alone
limithow many items to return in this page. Servers may cap it, so read the count you actually got
filter-lang, filtera condition on properties, here in CQL2-JSON. The older query field (the Query extension) does a similar job with a simpler syntax

Step 2: the bbox filter, checked by hand

Two boxes intersect when they overlap on both axes. Write box A as [minx, miny, maxx, maxy]. Boxes A and B intersect exactly when

A_{minx}\le B_{maxx}\quad\text{and}\quad B_{minx}\le A_{maxx}\quad\text{and}\quad A_{miny}\le B_{maxy}\quad\text{and}\quad B_{miny}\le A_{maxy}
Worked example: does the demo scene meet the search box?

Scene A (the footprint from Lesson 2.3): [10.6, 48.2, 11.9, 49.2]. Search box Q: [10.8, 48.4, 11.6, 49.0].

Check the four inequalities: 10.6\le 11.6 ✓, 10.8\le 11.9 ✓, 48.2\le 49.0 ✓, 48.4\le 49.2 ✓. All hold, so the boxes intersect.

The overlap has width \min(11.9,11.6)-\max(10.6,10.8)=11.6-10.8=0.8 and height \min(49.2,49.0)-\max(48.2,48.4)=49.0-48.4=0.6. Its area is 0.8\times0.6=0.48 deg².

A second scene, [12.1, 48.0, 13.0, 49.0], fails the first test: 12.1\le 11.6 is false, so it lies entirely east of the search box and is rejected.

Notice that 0.48 is in square degrees, not square kilometres. At 48° N a degree of longitude is about 74 km and a degree of latitude about 111 km. The bbox test is therefore only a cheap first pass. A server can run the exact footprint test on geometry afterwards.

Step 3: the datetime filter, checked by hand

The interval is 2026-06-01T00:00:00Z/2026-08-31T23:59:59Z. An item matches when its time span overlaps the interval. An item with a single instant t overlaps when start\le t\le end. An item with a range [s, e] overlaps when s\le \text{end}\ \text{and}\ e\ge \text{start}.

Item timeTestResult
instant 2026-07-14T10:31:22Z1 Jun ≤ 14 Jul ≤ 31 Augmatch
range 2026-05-20 → 2026-06-1020 May ≤ 31 Aug and 10 Jun ≥ 1 Junmatch (overlaps 1–10 June)
range 2026-05-01 → 2026-05-3131 May ≥ 1 Jun is falseno match

The interval end is inclusive. Writing only the date 2026-08-31 as the end would mean midnight at the start of 31 August, and a scene at 10:31 that day would be silently dropped. Always write the end as a full timestamp.

Step 4: the property filter

CQL2-JSON writes a condition as a tree. {"op": "<", "args": [{"property": "eo:cloud_cover"}, 20]} reads "the property eo:cloud_cover is less than 20". Three scenes with cloud cover 12.4, 35.0 and 4.8 give 12.4<20 ✓ (kept), 35.0<20 ✗ (dropped), 4.8<20 ✓ (kept). Two survive.

Step 5: pages and the next link

A search with 137 matches and limit 50 cannot return them all in one response. The response carries a links entry with rel: "next" when more pages exist:

{
  "type": "FeatureCollection",
  "stac_version": "1.0.0",
  "context": {"returned": 50, "limit": 50, "matched": 137},
  "features": [
    {"type": "Feature", "id": "S2B_DEMO_20260714_T31UFT_L2A", "collection": "demo-sentinel-2-l2a",
     "bbox": [10.6, 48.2, 11.9, 49.2],
     "properties": {"datetime": "2026-07-14T10:31:22Z", "eo:cloud_cover": 12.4}}
  ],
  "links": [
    {"rel": "next", "method": "POST", "href": "https://example.org/stac/v1/search",
     "merge": true, "body": {"token": "next:demo-search:50"}}
  ]
}

The features list above shows one item of the 50 for brevity. Two details matter. The token is opaque: copy it, never build it. And merge: true means the link's body is added to your original request, so your bbox and filter stay in place.

Worked example: how many requests?

137 matches with a limit of 50 need \lceil 137/50\rceil=3 requests. The pages hold 50, 50 and 37, because 137-2\times50=37. The last response has no next link, and the loop stops.

The loop, in Python with the requests library, follows the link until none is left:

import requests

def search_all(url, body):
    items = []
    while True:
        page = requests.post(url, json=body, timeout=60).json()
        items += page["features"]
        nxt = next((l for l in page["links"] if l["rel"] == "next"), None)
        if nxt is None or not page["features"]:
            return items                      # no next link: all pages read
        url = nxt["href"]
        body = {**body, **nxt.get("body", {})}  # merge: keep the original bbox and filter
Pipeline positionStage 1, Acquire. The search returns item records only. The pixels are read later, from the assets of the items you keep (Lesson 2.6).

Lab

Common traps
  • Degrees are not area. A 0.48 deg² box near the equator is a larger area than the same number at 60° N. Measure on the ground after reprojecting (Module 0).
  • A bbox over-matches. A scene whose box overlaps yours but whose footprint does not will pass the bbox test. Use intersects with the exact geometry when that matters.
  • Date-only ends drop scenes. Use full UTC timestamps for the end of the interval.
  • Cloud cover is an estimate for the scene. A scene at 4% cloud can still have cloud over your field, and a 40% scene can be clear over it. Check the cloud mask in the window (Module 1, masks).
  • Mixing query and filter. They are different extensions with different syntax. Send one, and say which filter-lang you use.
  • Assuming one page is everything. Always follow next until it is absent.
Where it shows up in AI
  • A training set is defined by its search. Save the request JSON with the dataset, and anyone can rerun the same search later.
  • Building a time series for a crop or change model means one search per region and a date interval that covers a full season.

Check yourself

1. A search has 412 matches and limit 100. How many requests, and how many items on the last page?
ceil(412/100) = 5 requests. Four pages hold 100 items each (400), so the last page holds 12.
2. Does a search box [0, 0, 2, 2] intersect an item footprint [1.5, −1, 3, 0.5]? What is the overlap area in deg²?
Yes: 0 ≤ 3, 1.5 ≤ 2, 0 ≤ 0.5 and −1 ≤ 2 all hold. The overlap is 0.5 wide (min(2,3) − max(0,1.5)) and 0.5 high (min(2,0.5) − max(0,−1)), so 0.25 deg².
3. A scene is captured at 2026-03-31T23:30:00Z and the search interval is 2026-03-01T00:00:00Z/2026-03-31T00:00:00Z. Does it match? How would you fix the request?
No. The end is midnight at the start of 31 March, and 23:30 on 31 March is later. Write the end as the full timestamp 2026-03-31T23:59:59Z.

Takeaways

  • A STAC API search filters by bbox (or intersects), a datetime interval and a property condition, and returns item records.
  • Check the bbox and datetime tests by hand: the boxes must overlap on both axes; the interval overlaps when start and end cross.
  • Pagination: follow next links, copy the token exactly, and stop when there is no next link.
2.6

From search results to a dataset

The questionYour search returned six scenes over the same field. Each provider names its bands differently, one scene has a different projection, and a whole scene is 2.69 GiB. How do you turn these search results into one clean time stack of red reflectance for a 2.56 km window, and how do you record where every value came from?

Intuition

Imagine collecting photographs of the same field on different days. You discard the days when clouds covered it, crop every picture to the same frame, put the frames in date order, and write a log saying which camera and which file each frame came from. Harvesting search results is the same work, done on satellite files. Search gave you the list. Harvest chooses the files, cuts the window, stacks it and keeps the log.

Build it up: five steps from list to stack

Step 1: pick the asset by meaning, not by name. Provider A calls the red band B04; provider B calls it red. Both carry a band object whose common_name is red. A harvest selects the asset whose common name matches, so the same code works on both archives.

Band (common_name)Provider A keyProvider B key
redB04red
nirB08nir08
greenB03green

Step 2: filter on cloud cover. Keep a scene only if its eo:cloud_cover is strictly below the threshold. Worked example: the six candidates have cloud covers 6.2, 35.0, 14.0, 3.1, 48.7 and 20.0. With the rule "below 20":

Worked example: the cloud filter by hand

6.2<20 ✓ keep. 35.0<20 ✗ drop. 14.0<20 ✓ keep. 3.1<20 ✓ keep. 48.7<20 ✗ drop. 20.0<20 ✗ drop, because 20.0 is not less than 20.

Three of six survive: scenes with 6.2%, 14.0% and 3.1% cloud. Note the scene value is for the whole tile, so it says little about one small window.

Step 3: read only the window. A 256 × 256 pixel window at 10 m resolution covers 256\times10\text{ m}=2560\text{ m}=2.56\text{ km} on each side. Because the files are Cloud-Optimised GeoTIFFs (Module 1), the harvest asks only for the bytes of that window, not the 2.69 GiB scene.

Step 4: stack in time order. The kept windows form an array with shape [T,\,H,\,W], here [3,256,256] for one band. The stack needs one grid: every window must share the same CRS, resolution and origin. Storage follows the data type: 2 bytes per pixel for uint16 reflectance.

Worked example: the size of the stack

Three kept scenes, one band, 2 bytes per pixel:

T\times H\times W\times B\times 2 = 3\times256\times256\times1\times2 = 393\,216\text{ bytes}= 384\text{ KiB}

The same window with four bands per scene is 3\times256\times256\times4\times2=1\,572\,864 bytes, which is 1.5 MiB. Both are tiny next to one 2.69 GiB scene, which is why windowed reads matter.

Step 5: keep the provenance. A stack is only useful if someone can rebuild it. The manifest below records, for each slice, the item, the asset, the cloud value and the CRS:

{
  "stack": "red-2026-05-window-A",
  "band": "red",
  "window_px": [256, 256],
  "resolution_m": 10,
  "search": {"collections": ["demo-sentinel-2-l2a"], "datetime": "2026-05-01T00:00:00Z/2026-05-31T23:59:59Z"},
  "items": [
    {"id": "S2A_DEMO_20260505_T31UFT", "datetime": "2026-05-05T10:31:22Z", "asset": "B04",
     "eo:cloud_cover": 6.2, "proj:epsg": 32632, "href": "./S2A_DEMO_20260505_T31UFT/B04.tif"}
  ]
}

A real manifest lists every kept item, not only the first. The search block lets anyone rerun the query, and the epsg field shows whether the grids can be stacked without reprojection.

Pipeline positionStage 1, Acquire, feeding Stage 2, Preprocessing. Harvest selects and cuts the data; reprojection, masking and normalisation come next (Module 1 and Module 3). Its output is a bands × H × W array plus a manifest.

Common traps
  • Assuming the same key everywhere. B04 at one provider can be a different band at another. Match by common_name, and check the eo:bands of each item.
  • Trusting scene cloud cover for a window. A 4% scene can have cloud over your window, and a 40% scene can be clear over it. Mask the window itself (Module 1, masks).
  • Stacking different grids. Items with EPSG 32632 and 32633 cannot be stacked directly. Reproject one grid to the other first.
  • Forgetting the manifest. A stack without its items, cloud values and CRS cannot be audited or rebuilt.
Where it shows up in AI
  • Time-series models for crop type and change (Module 7) take a stack like this one as input. The time order and the dates are part of the signal.
  • Training chips in Module 3 are cut from harvested stacks. The manifest is how a reviewer traces a mislabelled chip back to its source scene.

Check yourself

1. Five scenes, 256 × 256 pixels, four bands, uint16. How many bytes?

2. Provider A names the NIR band B08 and provider B names it nir08. Which field lets one harvest code select it for both?
The common_name inside the band object of eo:bands (here nir). The asset key is only a local name.
3. A scene has 4% cloud cover but a cloud sits over your 2.56 km window. Why is the scene-level value misleading here?
The cloud cover is for the whole tile (about 110 km across), so a small local cloud can be missed. Check the window itself with a cloud mask before you trust its pixels.

Takeaways

  • Harvest = select the asset by common name, filter scenes, read only the window, stack in time order, and record the provenance.
  • Stacking needs one grid: check the EPSG codes and reproject first.
  • Scene-level cloud cover is a filter, not a guarantee for your window; check the window with a mask.
2.7

Validating and publishing STAC

The questionYou have 500 scenes of your own, from a drone survey or a research satellite, and you want to publish them so that other people's tools can find and read them. How do you know the records are correct before anyone downloads a single file?

Intuition

A JSON Schema is a checklist written in a form that a machine can run: "this field must be a string", "this list must have four numbers". A validator runs the checklist over your file and lists every violation. But a checklist of shapes cannot check meaning. Four numbers in the wrong order pass the shape test and still describe the wrong place. So validation has three layers, and each catches different mistakes.

Build it up: three layers of checking

Layer 1: is it JSON? A missing comma or an unquoted key stops every tool. Parse first, always.

Layer 2: does it match the schema? The STAC core schemas say what an Item must contain. For an Item the core requires type, stac_version, id, geometry, bbox, properties, links and assets. The rule "bbox must be present when geometry is not null" and the rule "datetime, or start and end datetimes, must be present" are also schema rules. Each extension you declare brings its own schema for its prefixed fields.

Layer 3: is it true? Some rules need a calculation or a network request: the bbox must equal the bounds of the geometry; the datetime must be UTC; every asset href must resolve to a real file; the coordinates must be longitude and latitude, not metres.

Worked example: four broken items and the layer that catches each
ItemProblemCaught by
Ano datetime and no start/end pair in propertieslayer 2 (schema): the datetime rule fails
Bgeometry is set, but bbox is missinglayer 2 (schema): bbox is required with a geometry
Ceo:cloud_cover present, eo not declared in stac_extensionslayer 2 (strict): the prefixed field has no schema
Dbbox written as [48.2, 10.6, 49.2, 11.9] (latitude first)layer 3 only: four numbers pass the schema

Item D shows why layer 3 exists. Its geometry has minimum longitude 10.6 and minimum latitude 48.2, so the correct box is [10.6,\,48.2,\,11.9,\,49.2]. The stored minx of 48.2 is larger than the geometry's minimum longitude, so the test 48.2\le 10.6 fails and the box does not contain the footprint.

The formal definition

A record R is valid when it passes all three layers: parses, satisfies the schemas of its core and declared extensions, and satisfies the semantic rules. For an item with a non-null geometry these semantic rules include:

\text{bbox}=[\min x_i,\ \min y_i,\ \max x_i,\ \max y_i]\ \text{over the ring}\qquad -180\le x_i\le180,\quad -90\le y_i\le 90
xi, yithe ring's vertices in longitude and latitude (degrees)
bboxthe stored box; it must equal this box or contain it
datetimean RFC 3339 timestamp in UTC (ending in Z)

Building a static catalogue for your own data

You do not need a server to publish STAC. A static catalogue is a folder of JSON files with relative links, served by any web host:

my-drone-survey/
├── catalog.json                      Catalog, links: root, self, child
└── survey-2026/
    ├── collection.json               Collection: licence, providers, extent
    └── items/
        ├── FIELD_20260610_0930.json  Item: geometry, bbox, datetime, assets
        ├── FIELD_20260610_0930/
        │   ├── ortho.tif             the asset file, next to the item
        │   └── dsm.tif
        └── FIELD_20260611_1015.json

Publish the folder to a static host, keep the links relative, validate every JSON file, and test a few asset hrefs by fetching them. Libraries such as pystac can write this layout for you and check it; the stac-validator tool checks it against the schemas.

Pipeline positionStage 6, Publish & monitor. The catalogue is the product's index. Validation runs in the publishing job, so a broken record never reaches users.

Common traps
  • Valid JSON is not valid STAC. Parsing proves nothing about the fields.
  • A passing schema is not a correct record. Item D passes the shape test and is wrong. Add the semantic checks.
  • Projected coordinates in geometry. Footprints must be longitude and latitude in WGS 84, even when the pixels are in metres.
  • Hrefs that do not resolve. A schema can only say "this is a string". A 404 is found only by fetching the file.
  • Stale versions. A record that says stac_version 1.0.0 must be checked against the 1.0.0 rules, not the latest ones.
Where it shows up in AI
  • A dataset card (Module 3) is the human version of a manifest. Validation makes the machine version trustworthy, so the card's claims can be checked.
  • Model records use the same pipeline: an MLM item is a STAC Item with mlm: fields, validated before a model is published (Module 6).

Check yourself

1. An item has a geometry but no bbox. Which layer catches it, and which rule is it?
Layer 2, the schema. The core rule says bbox is required when geometry is not null.
2. The geometry's coordinates are (690000, 5340000) and similar metre values. Which rule fails, and in which layer?
Layer 3, the semantic rule. Footprints must be longitude and latitude in WGS 84, and these values lie far outside [−180, 180] × [−90, 90].
3. Why must you fetch each asset href during validation, when a schema already checks that href is a string?
Because a schema checks the shape of the value, not whether the file exists. Only a request shows whether the link resolves; a 404 means the item cannot be used.

Takeaways

  • Validate in three layers: parse, schema (core and declared extensions), then semantic truth (bbox vs geometry, UTC, lon/lat, hrefs).
  • A static catalogue is a folder of linked JSON files that any static host can serve.
  • Run the validator in the publishing job, so broken records never reach users.
