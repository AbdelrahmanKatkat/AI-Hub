Module 6 · Feature engineering & data pipelines

A model never sees your customers, your sensors or your sales. It sees rows of numbers. This module is about the craft of turning raw records into good numbers, without letting the future or the answer sneak in, and about wrapping the recipe so that it runs identically in training and in production. It sits in the clean and prepare stage of the data science loop and feeds the test and model stage.

6.1

Encoding categorical variables

The questionA delivery app wants to predict which customers will cancel their subscription. The table has a city column (Cairo, Giza, Alex) and a plan column (Basic, Plus, Pro). A model multiplies and adds numbers, and "Cairo" is not a number. How do we turn words into numbers without telling the model something false, and what do we do on the day a customer arrives from a city we have never seen?

Intuition: a number must mean what it says

The lazy fix is to number the cities: Alex = 0, Cairo = 1, Giza = 2. A linear model would now believe that Giza is "twice as much" as Cairo and that Cairo sits exactly halfway between Alex and Giza. None of that is true. Cities have no order and no distances. The encoding has put a fake geometry into the data.

So the right encoding depends on what the category really is. If it has no order (cities, colours, product ids) we give every value its own column. If it has a real order (small < medium < large, or Basic < Plus < Pro) a single column of ranks is honest. And if there are thousands of values (zip codes, product ids) separate columns are too many, so we sometimes replace the value by a statistic of the label for that value, which is powerful and dangerous.

Build it up

Here is a tiny training table, printed in full. churned = 1 means the customer cancelled.

rowcityplanchurned
1CairoBasic1
2GizaPlus0
3CairoBasic1
4AlexPro0
5GizaBasic1
6CairoPlus0
7AlexPlus0
8GizaBasic0

One-hot encoding. List the distinct cities seen in training, in a fixed order: (Alex, Cairo, Giza). Create one column per city. A row gets a 1 in the column of its own city and 0 elsewhere. Row 1 (Cairo) becomes (0,1,0); row 2 (Giza) becomes (0,0,1). Every pair of cities is now equally far apart, which is exactly the claim we want to make.

\text{onehot}(x)_j = \begin{cases}1 & x = c_j\\ 0 & \text{otherwise}\end{cases}\qquad j=1,\dots,K
Symbols. x: the category of one row. c_1,\dots,c_K: the K categories found in the training data, in a fixed order. \text{onehot}(x)_j: the value of column j.

Ordinal encoding. The plan has a genuine order, so Basic, Plus, Pro become 0, 1, 2. Row 4 (Pro) gets 2. Only use this when the order is real and the gaps are roughly sensible; if you are unsure, one-hot is safer.

Target encoding. Replace each city by the average churn of that city in the training rows. Counting: Cairo has 3 rows with churn (1, 1, 0), so its mean is 2/3 = 0.6667. Giza has (0, 1, 0), mean 0.3333. Alex has (0, 0), mean 0. The overall rate is 3/8 = 0.375.

A city with only two rows has an unreliable mean, so we pull it towards the overall rate. With a smoothing strength m:

\text{te}(c) = \frac{n_c\,\bar y_c + m\,\bar y}{n_c + m}
Symbols. n_c: number of training rows in city c. \bar y_c: their mean label. \bar y: the mean label over all training rows. m: a pseudo-count, "how many imaginary average rows to add". Large m shrinks everything towards \bar y.
Worked example, m = 2

Cairo: (3\cdot0.6667+2\cdot0.375)/(3+2)=2.75/5=0.55. Giza: (3\cdot0.3333+2\cdot0.375)/5=1.75/5=0.35. Alex: (2\cdot0+2\cdot0.375)/4=0.1875. The thinly-supported Alex moved from 0 to 0.1875: we no longer claim "nobody in Alex ever churns" from two rows.

The leakage risk. Target encoding uses the label to build a feature. If you encode row 5 (Giza, churned = 1) with a Giza average that includes row 5 itself, the row's own answer is already in its feature. For a category with one row the feature equals the label exactly. The model then learns "trust the city column" and is overconfident on training data, but on new data the trick is gone. The standard cures are to compute the encoding from other rows only (out-of-fold or leave-one-out), to smooth as above, and always to fit it on the training split alone. Leakage gets its own lesson (6.5).

Unseen categories. Suppose a customer from Luxor arrives. The training data has no Luxor column. One-hot gives an all-zero city block (often plus an "unseen" flag column), and target encoding falls back to the overall rate 0.375. A pipeline that crashes on new categories will crash in production.

Try this
  1. Press Play with Cairo and Basic and watch the vector appear group by group. Then pick Luxor: which columns change, and what happens to the city_te value?
  2. Set smoothing m to 0, then slowly raise it to 10. For Alex, how does its encoding move, and why is that useful when a city has only two rows?
  3. Pick Pro with Alex. Which column holds the plan, and what would a model infer if you had used 0, 1, 2 for the cities instead?
Common traps
  • Integer codes for unordered categories. A linear model, k-NN or neural network treats 2 as "bigger than" 1. Trees can cope, linear models cannot.
  • Fitting the category list on all the data. The list of columns must come from training rows only; otherwise test-set categories leak into the schema.
  • Target encoding on the training rows with their own labels. It makes the training set look separable and the test set disappoint.
  • High-cardinality one-hot. A column per product id gives thousands of mostly-zero columns; use target encoding, hashing or embeddings.
Where it shows up in AI
  • Every tabular model (linear, tree ensembles, neural nets) needs categories as numbers; gradient-boosting libraries even offer built-in ordered target statistics to avoid the leak above.
  • Embeddings: deep models learn a dense vector per category (a learned one-hot compression), used for user and item ids in recommenders.

Check yourself

1. With columns (Alex, Cairo, Giza), what is the one-hot vector for row 2 (Giza)? What about a customer from Luxor?
Giza is (0, 0, 1). Luxor was not seen in training, so the city block is (0, 0, 0), usually with an extra "unseen" flag set to 1.
2. Compute the target encoding of Alex with m = 2 using the training table.
n = 2, mean churn = 0, overall rate 0.375. (2·0 + 2·0.375) / (2 + 2) = 0.1875.
3. Why is it unsafe to compute a city's churn average from all rows and then use it as a feature for those same rows?
Each row's own label is part of its feature, so the feature secretly contains the answer (for a one-row city it equals the label). The model looks excellent on training data and fails on new customers, whose labels are not in any average.

Takeaways

  • Unordered categories: one-hot. Truly ordered ones: ordinal ranks. Many values: target statistics, hashing or embeddings.
  • Target encoding uses the label, so smooth it and compute it only from training data (out-of-fold).
  • Plan for categories you have never seen: all-zero block, an "unseen" flag, or the overall rate.
6.2

Scaling and transforming numeric features

The questionA model sees two features: an order value in dollars (tens to thousands) and the number of items (1 to 5). Does it matter that one is a thousand times bigger than the other? And when a few orders are huge, is the average still a fair summary? How should a brand-new number be treated at prediction time?

Intuition: put every feature on a comparable ruler

Many methods compare or combine features by their raw size. Distance-based methods like k-NN add up squared differences, so the dollar column drowns out the item count. Gradient descent on a linear model or neural network takes tiny steps in the dollar direction and huge ones in the other, and crawls. Putting features on a common scale fixes both. Trees do not care, because they only ask "is it bigger than a cut-off?".

Skew is a second problem. If most orders are 20 to 40 dollars and a few are 5000, the mean and the squared error are dominated by the few giants. A log turns multiplication into addition, so "twice as much" is the same step everywhere on the scale, and the long tail is pulled in.

Build it up

Standardisation (z-score). Subtract the mean and divide by the standard deviation. The result has mean 0 and standard deviation 1 on the data it was computed from, and reads "how many standard deviations from typical".

z = \frac{x-\mu}{\sigma}\qquad \mu=\frac1n\sum_i x_i,\quad \sigma=\sqrt{\frac1n\sum_i (x_i-\mu)^2}

Min–max scaling squeezes the training range onto 0 to 1:

x' = \frac{x-x_{\min}}{x_{\max}-x_{\min}}
Symbols. x: a value of the feature. \mu,\sigma: mean and standard deviation of the feature (here the divisor is n, as scikit-learn does; with n-1 the numbers change slightly). x_{\min},x_{\max}: smallest and largest training values. z,x': the scaled values.
Worked example, five training orders

Training order values (dollars): 20, 25, 30, 35, 90. Mean: \mu=200/5=40. Deviations: −20, −15, −10, −5, 50. Squares: 400, 225, 100, 25, 2500, sum 3250. Variance 3250/5=650, so \sigma=25.4951.

Standardised: 20 → −0.7845, 25 → −0.5883, 30 → −0.3922, 35 → −0.1961, 90 → 1.9612. Min–max (min 20, max 90, range 70): 0, 0.0714, 0.1429, 0.2143, 1.

Now a new order of 60 arrives. We reuse the numbers learned from training: z=(60-40)/25.4951=0.7845 and x'=(60-20)/70=0.5714. Notice the new value is not required to land in [0, 1]: an order of 140 would give (140-20)/70=1.7143, which is correct and informative.

Fit on training data only. A scaler has two phases. Fit computes \mu,\sigma (or min and max). Transform applies them. The fit must see training rows only. Suppose we lazily fit on training plus the new value: the six numbers 20, 25, 30, 35, 90, 60 give \mu=43.3333,\ \sigma=24.4381, and the new order becomes z=0.6820 instead of 0.7845. The test row has quietly influenced its own transformation. With 5 rows the gap is visible; with a bigger test set and extreme values it can flatter the score.

Log transform. For the same five orders, \ln x gives 2.9957, 3.2189, 3.4012, 3.5553, 4.4998. The gap between 35 and 90 shrank from 55 dollars to 0.9445 log-units, and the skewness of the column falls from 1.3577 to 1.0244. Use \ln(1+x) when zeros are possible. A log needs positive values; a negative input gives NaN, which the lab below will show.

Try this
  1. In the first lab leave the training values as they are and let the test value sweep from 0 to 120. Where is z equal to 0, and where does min–max leave the 0 to 1 range?
  2. Tick "fit on train + test (wrong)" and slide the test value to 60, then to 120. When does peeking change z the most, and in which direction?
  3. In the second lab press Play and watch the raw histogram build a long tail. Then try log(x), sqrt(x) and x^2: which one makes the skewness closest to 0, and what does log(x-100) do?
Common traps
  • Fitting the scaler on all the data before splitting. The test set's mean and range leak into training.
  • Scaling the label by accident, or scaling a one-hot column (harmless but pointless).
  • Min–max with an outlier. One value of 9000 squeezes every ordinary order into 0 to 0.01. Use a robust scaler (median and IQR) or log first.
  • Assuming z-scores are normal. Standardising changes the scale, not the shape: a skewed column is still skewed.
Where it shows up in AI
  • Linear models and neural nets: comparable scales make gradient descent converge faster and make penalties (L1, L2) treat features fairly.
  • k-NN and clustering: distances are only meaningful when features share a scale.
  • Normalisation layers inside deep networks apply the same idea (batch statistics during training, stored running statistics at inference).

Check yourself

1. Using the training statistics above (μ = 40, σ = 25.4951), standardise a new order of 50.
z = (50 − 40) / 25.4951 = 0.3922.
2. Min–max scaling was fitted on the training orders (min 20, max 90). What does a test order of 140 become, and is that a bug?
(140 − 20) / 70 = 1.7143. It is not a bug; the test value is just larger than anything seen in training. Do not re-fit or clip silently, since the model should see that it is extrapolating.
3. Why does a log transform help when a feature has a few enormous values?
A log turns ratios into differences: from 35 to 90 the gap is 55 dollars but only 0.9445 on the log scale. The tail is compressed, so a handful of giants no longer dominate the mean, the squared error and the scale.

Takeaways

  • Standardise with (x-\mu)/\sigma or rescale with min–max, using statistics from training rows only, and reuse them for every new row.
  • Log-type transforms tame long right tails; scaling changes the ruler, not the shape.
  • Distance-based and gradient-based models need scaling; tree models mostly do not.
6.3

Date and time features

The questionA shop wants to forecast tomorrow's sales. Each row has a timestamp. A model cannot use "2026-03-14 23:00" as it stands. What can we pull out of a timestamp that actually predicts sales, and how do we say that 23:00 and 01:00 are close when the numbers 23 and 1 are far apart?

Intuition: time is a source of many different signals

A timestamp hides several questions: what hour is it (rush hour?), what weekday, which month (season), is it a holiday, how long since the last payday, and what happened on the days just before. We pull these out as separate features. Two of them need care: things that wrap around (hours, weekdays, months) and things that look backwards (yesterday's sales).

Build it up

Cyclic encoding. If hour is the number 0 to 23, then 23 and 0 look 23 units apart, yet they are one hour apart on the clock. Put the 24 hours on a circle and describe each hour by its position, two numbers:

\text{hour}\;\mapsto\;\left(\sin\frac{2\pi h}{24},\ \cos\frac{2\pi h}{24}\right)
Symbols. h: hour of the day, 0 to 23 (it may have a fraction). 24: the period of the cycle; use 7 for weekday, 12 for month. The pair is a point on the unit circle; two numbers are needed because sine alone gives the same value for two different hours.
Worked example, hours on the circle

Hour 6 → (1, 0). Hour 12 → (0, −1). Hour 23 → (−0.2588, 0.9659). Hour 1 → (0.2588, 0.9659).

Raw gap between 23 and 1: 22. Straight-line distance between their points: 0.5176, small. Between 23 and 0 (0, 1): raw gap 23 but circle distance 0.2611. Between 6 and 18 the points are opposite, (1, 0) and (−1, 0), distance 2, the largest possible.

Lags and rolling windows. The best predictor of today's sales is often yesterday's. A lag-k feature is the value k steps ago; a rolling mean over the previous w days smooths the noise. The key rule: when predicting day t, only values from days before t may be used.

\text{lag}_k(t)=y_{t-k},\qquad \text{roll}_w(t)=\frac1w\sum_{j=1}^{w} y_{t-j}
Symbols. y_t: sales on day t, the quantity to predict. k: how many days back. w: window length. The sum starts at j=1, so today y_t is excluded.

Ten days of sales: 12, 15, 11, 18, 20, 17, 25, 28, 22, 30.

day12345678910
sales12151118201725282230
lag-1–121511182017252822

Reading the table

Day 4's past-only roll-3 is (12+15+11)/3=12.667, all known by the morning of day 4. The "including today" row would use (15+11+18)/3=14.667, which contains the 18 we are trying to predict. Days 1 to 3 have no complete window, so the feature is missing there: decide on purpose whether to drop those rows, or fill them.

Holidays and calendar events. Holidays are known in advance, so features like is_holiday and days_to_next_holiday are safe, because the calendar is a published fact rather than the future of the thing being predicted. Add them, along with day of month and payday proximity where relevant, and keep one rule: any feature must be computable at the moment you make the prediction.

Try this
  1. In the clock lab keep A at 23 and let B sweep. When B passes midnight, what happens to the raw gap, and what happens to the chord distance?
  2. Set A to 6 and watch B reach 18. Why is the chord exactly 2 there, and what hour is the farthest from 23?
  3. In the rolling lab tick "include today" and compare the feature with the bar for today. Then set holiday days to 3, 4 and read days-to-next-holiday as the cursor moves.
Common traps
  • Raw hour or month as one number for a model that treats numbers as distances; 12 and 1 (December and January) look far apart.
  • A rolling window that includes today (the default in many libraries unless you shift by one). The feature then holds the target.
  • Random train/test splits for time data. A random split puts days after the test day into training; use time-based splits (Module 7).
  • Time zones and daylight saving. "Hour" of a UTC timestamp is not the customer's local hour.
Where it shows up in AI
  • Demand forecasting: lag, rolling, calendar and holiday features are the backbone of gradient-boosted forecasters (see Module 8).
  • Churn and fraud: time since last activity and counts in the last week are among the strongest features (next lesson).
  • Transformers add sinusoidal or learned position encodings, the same idea of representing position as sines and cosines.

Check yourself

1. What is the roll-3 (past only) value for day 7 in the table?
The three days before day 7 are days 4, 5, 6 with sales 18, 20, 17: (18 + 20 + 17) / 3 = 18.333.
2. Holidays are on days 6 and 7. What is days_to_next_holiday on day 4, and is it leakage to use it?
6 − 4 = 2. It is not leakage: the holiday calendar is published in advance and is known on day 4.
3. Why do hours 6 and 18 have the largest distance after the sine/cosine encoding, and what is it?
They are half a day apart, opposite points on the circle, (1, 0) and (−1, 0). The distance is 2, the diameter.

Takeaways

  • Pull hour, weekday, month, holidays and elapsed time out of timestamps; encode cycles with sine and cosine so the ends meet.
  • Lag and rolling features must use strictly earlier rows; windows near the start are missing, which you handle on purpose.
  • Ask of every time feature: could I have computed this at prediction time?
6.4

Aggregate and window features

The questionA bank wants to flag a suspicious card transaction. A single transaction (50 dollars at 3 a.m.) says little. But "this card made 4 purchases in the last hour and 0 in the last month" says a lot. How do we turn a customer's whole history into a few numbers a model can use, as they stood at one moment in time?

Intuition: summarise the history, as of a moment

Models want one row per decision, but the real data is a log with many events per customer. We collapse the log with aggregates: counts, sums, means, maxima, over a window of time. Three families do most of the work: recency (how long since the last event), frequency (how many events), and monetary value (how much), often called RFM.

The crucial word is as of. A feature value belongs to a customer at a prediction time t. It may only use events strictly before t. If a window creeps past t, the model is shown purchases that happen after the moment it is supposed to be predicting from.

Build it up

One customer's purchases (day, amount in dollars): (1, 30), (3, 45), (4, 20), (8, 60), (9, 25), (12, 40), plus later ones. We want the features at prediction time t=10 using a 7-day window.

\text{count}_w(t)=\bigl|\{i:\ t-w\le d_i<t\}\bigr|,\quad \text{sum}_w(t)=\sum_{t-w\le d_i<t} a_i,\quad \text{recency}(t)=t-\max_{d_i<t} d_i
Symbols. d_i: day of event i. a_i: its amount. t: the prediction day ("now"). w: window length in days. The window is half-open: it includes day t-w and stops just before day t. The mean is sum divided by count.
Worked example, now = day 10

Window [3,10): events on days 3, 4, 8, 9 (amounts 45, 20, 60, 25). Count 4, sum 150, mean 150/4=37.5. The last event before day 10 was day 9, so recency is 1 day. Frequency in all history before day 10: 5 purchases (days 1, 3, 4, 8, 9), average amount 36. The purchase on day 12 does not exist yet.

Slide to now = day 13: window [6,13) holds days 8, 9, 12 (60, 25, 40): count 3, sum 125, mean 41.6667, recency 1 (day 12). Day 1, 3 and 4 have dropped out. The window slides: new events enter at its right edge and old ones leave on the left.

The look-ahead mistake. Suppose the window were allowed to end 3 days after day 10, [3,13). It would catch the day-12 purchase: count 5, sum 190, mean 38. The feature has jumped from 4 to 5 purchases by using something that happens two days after the decision. In production those days have not occurred.

Choosing windows. Short windows (1 hour, 1 day) catch sudden change; long ones (30, 90 days) catch habit. Use several at once, and also ratios such as "last-7-days spend divided by last-30-days spend". Features are cheap; the discipline is the same for all: strictly before t.

Try this
  1. Pause with now at day 10 and window 7. Read count, sum, mean and recency, and compare with the numbers printed above.
  2. Step forward to day 13 and watch which bars leave and enter the window. Then shrink the window to 3: how does recency differ from the count?
  3. Set the look-ahead to 3 at day 10. Which bar turns red, and by how much did the count and the sum change compared with look-ahead 0?
Common traps
  • One global aggregate per customer computed from the full history (total spend, total purchases) and joined to every row. A row in January then knows about purchases in December.
  • Window edges. "Last 7 days" including or excluding today changes the feature; fix the convention and write it down.
  • Customers with no history. Count 0 is meaningful, but mean of nothing is undefined: use a flag or a fill value, not 0.
  • Aggregating after the join. Joining a customer table to an event table, then averaging, can double-count rows (see Module 1 on joins).
Where it shows up in AI
  • Fraud detection: counts and sums over the last minute, hour and day, per card and per merchant, are the main inputs.
  • Recommendation: a user's recent clicks and categories, and an item's recent popularity, drive ranking models.
  • Feature stores (lesson 6.6) exist largely to compute these windowed values correctly as of each point in time.

Check yourself

1. At now = day 13 with a 7-day window, give the count, sum and recency.
Window [6, 13) contains days 8, 9, 12: count 3, sum 60 + 25 + 40 = 125, recency 13 − 12 = 1.
2. At now = day 10 with a window [3, 13) (3 days of look-ahead), what are the count and sum, and what is wrong?
Days 3, 4, 8, 9 and 12: count 5, sum 45 + 20 + 60 + 25 + 40 = 190. The day-12 purchase is in the future of the day-10 decision, so the feature uses information not available then.
3. At now = day 7, what is the recency and the total number of earlier purchases?
Purchases before day 7 are on days 1, 3, 4. The last is day 4, so recency is 7 − 4 = 3 days, and the count is 3.

Takeaways

  • Collapse an event log into counts, sums, means, recency and frequency over windows, evaluated as of a prediction time.
  • The window is half-open: it ends just before the prediction time, never after.
  • Use several window lengths and handle empty windows deliberately.
6.5

Data leakage: the silent killer

The questionYour churn model scores 92 percent on held-out data. The team celebrates, ships it, and in production it barely beats guessing. Nothing crashed and no test failed. What went wrong, how do you spot it, and how large can the effect be?

Intuition: the exam paper was in the textbook

A model is evaluated to estimate how it will do on data it has never seen. Leakage is any way the training or the features carry information that will not exist at prediction time, or that comes from the evaluation rows. The score then answers a different question (how well do you do with the answers visible?) than the one you care about. It is "silent" because the number looks like good news.

There are three common routes. (1) The label or the future inside a feature: a column that is a consequence of the outcome. (2) Train/test contamination: the same customer, document or time period appearing on both sides. (3) Leakage through preprocessing: any step that learns from data (a scaler, an encoder, a feature selector, an imputer) fitted on rows that include the test set.

Build it up

Route 1, the future creeping into the past. Predict, on the prediction day, which of 300 subscribers will cancel. A feature counts support contacts. People who are about to cancel contact support, but mostly after the prediction day, when they ask how to cancel. We build the count with a window of the 30 days before the prediction day plus s days past it. We pick the best "contacts ≥ threshold" rule on the first 150 customers and measure accuracy on the last 150. (Simulated data, seeded, so the numbers repeat.)

The numbers

Always predicting "stays" gets 0.633 on the test half. With the strictly past window (s=0) the rule scores 0.647: a little better than nothing, the honest number. Let the window reach 5 days past the prediction day: 0.793. Reach 14 days: 0.920. Same customers, same model, same code; only the window edge moved into the future. In production the future days are empty and the model falls back to about 0.65.

Route 3, leakage through preprocessing. This one fools even careful people. Take 40 rows and give every row 5 to 500 features that are pure random noise, with random labels. The honest accuracy is 0.5 by definition. Now choose the 5 features most correlated with the label, then run 5-fold cross-validation on those 5. The selector looked at all 40 labels, including the ones later held out, so the "held-out" rows already voted.

The numbers (average over 10 simulated datasets, 5 features kept, 5-fold cross-validation)

With 5 noise features available, both methods score 0.455 (nothing to select from). With 50: selecting on all rows scores 0.748, selecting inside each fold scores 0.545. With 500: 0.838 against 0.515. The more candidates, the more "signal" the selector can find in noise, and the more optimistic the leaky score. The correct pipeline does the selection inside each training fold and gets chance level, which is the truth.

The same logic applies to the scaler from lesson 6.2: fitting on all rows moved a z-score from 0.7845 to 0.6820, and the effect is larger for imputers, target encoders and anything with many parameters. The rule is simple:

\text{every learned step: } \text{fit}(\text{train rows only}) \;\longrightarrow\; \text{transform}(\text{train}),\ \text{transform}(\text{test})
Reading it. "Learned step" means any preprocessing step that computes something from data (a mean, a vocabulary, a selected feature list, a target average). It is fitted on training rows alone, and then applied to both training and test rows with the stored result.

Route 2, contamination. Several rows for one patient, several photos of one scene, several days of one customer: if some land in training and some in test, the model can recognise the entity rather than learn the pattern. Split by entity (group split) or by time. Duplicates and near-duplicates across the split behave the same way.

Detecting leakage. Be suspicious when: the score is too good for the problem; one feature dominates the importance; a feature's name suggests an outcome (refund_issued, account_closed_date, treatment_given when predicting disease); or the score collapses in production or on a later time period. Ask of every feature: at the moment of prediction, would I know this?

Try this
  1. Run the first lab from 0 future days. Note the accuracy with no future, then watch it climb. How many future days does it take to pass 0.80?
  2. Press "New random customers" and run again. Is the pattern stable, and does the no-future accuracy stay close to the dashed baseline?
  3. In the second lab watch the two lines as the number of noise features grows. Then drop "features kept" to 1 and raise it to 10: when does the gap between the lines grow or shrink?
Common traps
  • Preprocess everything, then split. The most common leak of all. Split first, or use a pipeline that fits inside each fold (lesson 6.6).
  • "The test set is clean, so I am safe." If you tune on the test set repeatedly, it leaks into your choices too (Module 7).
  • Using a post-event column (a status, a closing date, a count "to date" that includes the outcome) because it is in the table.
  • Believing a great score. Too good is a finding. Investigate before celebrating.
Where it shows up in AI
  • Medical imaging: models that "diagnose" from a hospital's marker or scanner type, or that were tested on scans from patients also in training, post impressive scores that vanish in a new hospital.
  • Benchmark contamination: a large language model that has seen test questions in its training text answers them well for the wrong reason.
  • Competitions and papers: several well-known challenges were won by exploiting a leaking identifier or ordering column.

Check yourself

1. In the simulated churn example, the test accuracy rose from 0.647 to 0.920 as the window reached 14 days past the prediction day. Is 0.920 the number to report?
No. The extra accuracy comes from contacts that happen after the prediction day, which do not exist in production. The honest estimate is the strictly past one, 0.647, only a little above the always-"stays" baseline of 0.633.
2. You select the best 5 of 500 features on all 40 rows, then cross-validate, and get 0.838. The features are pure noise. Why is the score so high, and how do you fix the procedure?
The selector saw every label, including those in the held-out folds, so it picked features that happen to match them by chance. Do selection inside each training fold only; that gives about 0.515, which is chance and the truth.
3. When predicting whether a loan will default, which is a leaky feature: (a) income at application, (b) number of missed payments in the first 6 months after the loan, (c) credit score at application?
(b). It is only known after the loan has run, so it was not available at the moment of the decision, and it is partly the outcome itself. (a) and (c) exist at application time.

Takeaways

  • Leakage is any information in training or features that will not exist at prediction time, or that comes from evaluation rows.
  • Three routes: future or label inside a feature, train/test contamination, and learned preprocessing fitted on all rows.
  • A suspiciously good score is a symptom: ask of every feature "would I know this at prediction time?" and fit every learned step on training data only.
6.6

Reproducible pipelines and feature stores

The questionThe model was trained in a notebook where someone filled missing ages, standardised them, and one-hot encoded cities by hand. Six months later the model runs in an app and a new customer sends a request with the age missing and a city nobody has seen. Which numbers does the app use, and how can we be sure they are the same ones the model was trained with?

Intuition: a recipe with remembered quantities

Feature engineering is a recipe, and a recipe has two kinds of content: the steps (impute, scale, encode) and the quantities learned from data (the mean age, the standard deviation, the list of cities). If those quantities live in someone's head or in a notebook cell, the recipe cannot be reproduced. The fix is to bundle steps and quantities into one object that has two methods.

fit looks at the training rows once and stores the quantities. transform applies the stored quantities to any rows, training or new, and never learns anything. Keeping them apart is what prevents leakage (lesson 6.5) and what guarantees that training and serving agree.

Build it up

Five training rows: ages 22, 35, 41, 29, 48 and cities Cairo, Giza, Cairo, Alex, Giza. A three-step pipeline: (1) impute a missing age with the mean, (2) standardise age, (3) one-hot the city.

\text{fit}:\ (\mu,\sigma,\ \text{cities}) \leftarrow \text{train rows}\qquad \text{transform}(x)=\Bigl[\tfrac{\text{impute}(a)-\mu}{\sigma},\ \text{onehot}(c)\Bigr]
Symbols. \mu,\sigma: mean and standard deviation of age over the training rows. a: the age in a record (maybe missing). c: its city. \text{impute}(a): a itself, or \mu if missing.
Worked example

Fit. \mu=(22+35+41+29+48)/5=35. Squared deviations: 169, 0, 36, 36, 169, sum 410, variance 82, \sigma=9.0554. Categories, in order: (Alex, Cairo, Giza).

Transform a record with age 60 in Cairo: impute (not needed), z=(60-35)/9.0554=2.7608, one-hot (0, 1, 0). Vector: [2.7608, 0, 1, 0].

A record with the age missing: impute 35, z=0. A record from Luxor: city block (0, 0, 0). Age 30 in Alex: z=-0.5522, vector [−0.5522, 1, 0, 0]. None of these needed the training table again.

Training-serving skew. Suppose the serving code instead standardises each incoming request with its own statistics. A request is one row, so its mean is its own age and its standard deviation is 0: z=0/0, undefined. Even if a batch is used, the batch mean differs from the training mean, so the model receives numbers on a scale it never learned. The same bug appears when two teams re-implement the logic (one in SQL, one in Python) and disagree on a rounding or a fill value.

A pipeline object. Libraries package this. In scikit-learn a Pipeline chains transformers and a model; calling fit fits each step on the training rows in order, and predict transforms new rows with the stored state. Cross-validation then refits the whole pipeline inside every fold, which removes the preprocessing leak of lesson 6.5 by construction. Saving that one object (with its versions and a fixed random seed) gives a reproducible model: the same input always gives the same features.

Feature stores (preview). At company scale many models share features such as "purchases in the last 7 days". A feature store is a system that (a) defines each feature once, (b) computes it for training as of each historical moment (the point-in-time correctness of lesson 6.4), (c) serves the latest values at low latency for live predictions, and (d) guarantees both use the same definition. It is the pipeline idea applied across a whole organisation. Module 9 returns to monitoring these features for drift.

Common traps
  • Notebook-only preprocessing. The model is saved but the cleaning steps are not, so nobody can recreate the inputs.
  • Calling fit on test or serving data. Use transform only; a fit there leaks or changes the scale.
  • Hidden state. Random seeds, library versions and column order are part of the pipeline; record them.
  • Two implementations of one feature. Offline (SQL/batch) and online (service) code drift apart; define the feature once.
Where it shows up in AI
  • Production ML systems package preprocessing with the model (scikit-learn pipelines, TensorFlow Transform, model-serving containers) so the same code runs in training and inference.
  • Feature stores (for example Feast, or the stores in cloud ML platforms) serve consistent features to many models, with point-in-time joins for training.
  • MLOps versions data, code and fitted pipelines together so any prediction can be reproduced and audited.

Check yourself

1. Using the pipeline fitted above (μ = 35, σ = 9.0554), what is z for a new customer aged 30?
z = (30 − 35) / 9.0554 = −0.5522.
2. Why must serving call transform and never fit?
Fit would recompute the mean, standard deviation and category list from the serving rows, which differ from the training ones (for one request the sd is 0). The model would then receive numbers on a scale it never saw. Transform reuses the stored training quantities, so training and serving features agree.
3. A request arrives from a city that was not in the training data and has no age. What does the pipeline output for those two features?
The age is imputed with the training mean 35, which standardises to z = 0. The city one-hot block is (0, 0, 0) for (Alex, Cairo, Giza). The request is handled with no error and without looking at training data again.

Takeaways

  • Bundle the steps and the quantities they learned into one object: fit on training rows once, transform everything with the stored state.
  • The same pipeline in training and serving avoids skew; fitting inside each cross-validation fold avoids leakage.
  • A feature store defines features once, computes them as of the right time for training, and serves them live.
