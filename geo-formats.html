Module 1 · Geospatial data formats & cloud-native access

A satellite scene is a very large grid of numbers with a map attached. This module shows how that grid is stored (GeoTIFF, Zarr, GeoPackage), why the storage layout decides what you can read cheaply over the internet, and how to align and clean the data before a model sees it.

GeoTIFF & Cloud-Optimised GeoTIFF

The questionA satellite scene is 10 000 × 10 000 pixels with 4 bands of 16-bit numbers. Uncompressed, that is 800 MB. Your model needs one 1 000 × 1 000 window from the middle, and the file sits on a server across the internet. How can a file let you read only that window, and not the whole 800 MB?

Intuition

Picture a very long photograph printed on one roll of paper. To see the middle you have to unroll everything before it. Now imagine the same photograph cut into a grid of numbered squares, with a table of contents at the front that says where each square starts on the roll. If you want square 37, you read the table, jump to its position and read only that square.

That is the whole idea of a tiled file. The second idea, overviews, is the atlas trick: alongside the full-resolution map, the file also stores smaller copies (half size, quarter size, and so on). When you look at the whole country you do not need every street, so you read a smaller copy.

A GeoTIFF is an ordinary TIFF image with a few extra tags that say where the pixels are on Earth: which coordinate reference system (CRS) they use and where the top-left corner sits. A Cloud-Optimised GeoTIFF (COG) is a GeoTIFF arranged so that a reader can find and fetch any tile with a few small requests. Almost every public satellite archive now offers its data in this form.

Build it up

Step 1, the plain layout. An uncompressed TIFF stores pixels row by row, one long strip after another. To read a 1 000 × 1 000 window in the middle, a reader must still skip past all the rows above it, and each row of the window is a separate piece of the file. Over the network that means many small, scattered reads.

Step 2, internal tiling. A tiled GeoTIFF cuts the image into squares, usually 256 × 256 or 512 × 512 pixels. Each tile is stored (and often compressed) as one block, and the file keeps a list of where each tile starts (TileOffsets) and how many bytes it takes (TileByteCounts). A window now touches only the tiles it overlaps.

Worked example: tile count and window cost

Tile size T = 512 and the image is W = H = 10 000 pixels.

Tiles across: \lceil 10000/512\rceil = 20, because 19 × 512 = 9 728 is less than 10 000, so one more tile is needed. The file has 20 × 20 = 400 tiles per band layout. The last tile column covers pixels 9 728 to 10 239, and the part beyond 10 000 is padding.

One tile of 4 bands at 2 bytes each is 512 \times 512 \times 4 \times 2 = 2\,097\,152 bytes (about 2.1 MB), even if it is stored uncompressed.

The window covers rows 1 000 to 1 999 and columns 1 500 to 2 499. The tile rows it touches are \lfloor 1000/512\rfloor = 1 to \lfloor 1999/512\rfloor = 3, that is rows 1, 2, 3. The tile columns are \lfloor 1500/512\rfloor = 2 to \lfloor 2499/512\rfloor = 4, that is columns 2, 3, 4. So the window touches 3 × 3 = 9 tiles.

Bytes read: 9 \times 2\,097\,152 = 18\,874\,368 B (about 18.9 MB). The exact window holds 1000 \times 1000 \times 4 \times 2 = 8\,000\,000 B. Reading whole tiles costs about 2.4 times the pixels you need, and the whole file would cost 400 × 2 097 152 = 838 860 800 B (about 839 MB).

Step 3, overviews. An overview (also called a pyramid level) is a copy of the image at half the width and height. Each level divides the size by 2 and is tiled in the same way. Starting from 10 000 pixels:

10000 \to 5000 \to 2500 \to 1250 \to 625 \to 313

With 512-pixel tiles, these levels hold 100, 25, 9, 4 and 1 tiles. Together with the 400 full-resolution tiles, the file has 539 tiles in total. A map that shows the whole scene on a 1 000-pixel screen does not need 10 000 pixels per side, so the reader picks a level whose pixels roughly match the screen.

Worked example: a coarse window

The same 1 000 × 1 000 window, read from overview level 2 (the 2 500-pixel copy, scale factor 4), becomes rows 250 to 499 and columns 375 to 624 of that copy. Tile rows: \lfloor 250/512\rfloor = 0 to \lfloor 499/512\rfloor = 0, one tile row. Tile columns: \lfloor 375/512\rfloor = 0 to \lfloor 624/512\rfloor = 1, two columns. So the reader fetches 2 tiles = 4 194 304 B (about 4.2 MB) instead of 18.9 MB, and it receives 250 × 250 pixels, which is the same ground area at a quarter of the resolution.

Step 4, the georeferencing tags. A GeoTIFF records where its pixels are. The key tags are the GeoKeyDirectory (which CRS, for example EPSG:32633 for UTM zone 33N), the ModelTiepoint (the coordinates of one pixel corner) and the ModelPixelScale (the size of a pixel, for example 10 m east-west and 10 m north-south). Together they define the geotransform: a rule that maps pixel (row, column) to map coordinates.

Step 5, the cloud-optimised layout. The COG standard orders the file so that all the image headers (IFDs) and the tile index sit at the front. A reader fetches the first few tens of kilobytes, learns where every tile is, and then issues one request per tile it needs. Lesson 1.4 turns this into byte ranges.

Where it sits in the pipeline. This is the Acquire stage: the storage layout decides how many bytes the stage must move before preprocessing can start.

Lab: tiles, overviews and one window

Try this
  1. Press Request window with the defaults. Count the orange tiles: 9. Check the readout: 18 874 368 B for a 1 000 × 1 000 window that needs 8 000 000 B.
  2. Set the window to row 500, column 500, 100 × 100. Only 4 tiles are touched (8 388 608 B), yet the window has only 80 000 B of pixels. A tiny window that straddles a tile boundary costs much more than it needs.
  3. Change the overview level to 2 with the default window. The window shrinks to 250 × 250 and touches 2 tiles. Coarse levels are cheap.
  4. Change the tile size to 1024. Fewer tiles, but each one is 4 times larger. Which is better depends on how big your windows are; a 256-pixel tile suits small training chips.
Common traps
  • A GeoTIFF is not automatically cloud-optimised. A striped, untiled file forces a reader to download nearly everything for a small window. Check the file (for example with gdalinfo or the COG validator) instead of trusting the extension.
  • Overviews are averages, not data. Use level 0 for training labels and for any measurement. Overviews are for display and quick looks.
  • Tile size is a trade-off, not a quality setting. Very small tiles mean many requests and large headers; very large tiles mean reading far more than you need.
  • Band layout matters. Pixel-interleaved tiles keep all bands together, so reading one band still reads all of them. Band-separate (planar) files let you read one band alone, at the price of more files per scene.
Where it shows up in AI
  • Most public Sentinel-2 and Landsat archives on the major cloud platforms are distributed as COGs, so a model can read a training chip without downloading the scene.
  • Windowed reads (the read window call in libraries such as rasterio) are how data loaders cut 256 × 256 chips from a scene on the fly.
  • Models that predict on a whole scene (lesson 5.7) write their output as a COG too, with the same tile and overview layout, so the next user can read it cheaply.

Check yourself

1. A single-band uint8 GeoTIFF is 6 000 × 4 000 pixels with 256 × 256 tiles. How many tiles are there?
Across: ⌈6000/256⌉ = 24, because 23 × 256 = 5 888 is short of 6 000. Down: ⌈4000/256⌉ = 16, because 15 × 256 = 3 840. Total 24 × 16 = 384 tiles.
2. A 300 × 300 window starts at row 250, column 250 of a 256-tile, 3-band uint8 file. How many bytes are read?
Rows ⌊250/256⌋ = 0 to ⌊549/256⌋ = 2, so 3 tile rows. Columns are the same, so 3 tile columns. That is 9 tiles of 256 × 256 × 3 = 196 608 B each, a total of 1 769 472 B. The exact window is only 300 × 300 × 3 = 270 000 B.
3. A web map is displayed on a 1 000-pixel-wide screen but the scene is 10 000 pixels wide. Why read an overview?
The screen can show only about 1 000 pixels across. Level 3 (1 250 pixels) or level 4 (625 pixels) carries nearly the same information for display, at a fraction of the bytes. Reading level 0 would transfer about 8 to 10 times more pixels than the screen can show.

Takeaways

  • A GeoTIFF is an image plus georeferencing tags; a COG adds internal tiles, overviews and an index at the front of the file.
  • Bytes read = the tiles a window touches × the bytes per tile, not the window's own pixels.
  • Overviews trade resolution for bytes; use them for display, use level 0 for measurement.

Vector formats: GeoJSON, GeoPackage, Shapefile

The questionYou have 3 000 building footprints drawn as polygons, a boundary file for each district, and 1.2 million GPS points that serve as labels. Which format should each one use? And why does a footprint that looks correct on screen sometimes give a wrong area, or land in the wrong country?

Intuition

Raster data is a grid of cells: every pixel has a value. Vector data is a list of things. Each thing has a shape (a point, a line or a polygon, described by its corner coordinates) and a row of attributes (a name, a class, a year). A vector layer behaves like a spreadsheet in which one column holds a shape.

Vector files differ mainly in how they store that spreadsheet. Some are plain text that you can open in an editor, some are a single database file, and some are a bundle of several files that must travel together.

Build it up

Step 1, the geometry types. A Point is one coordinate pair, such as a GPS fix. A LineString is an ordered list of points, such as a road. A Polygon is a closed ring: a list of points whose first and last entries are the same, which marks where the boundary returns to its start. A polygon may have holes (an inner ring) and a MultiPolygon is several polygons under one record, such as an island group.

Step 2, the attributes. Each feature (one geometry plus its attributes) carries values such as "class": "building" or "year": 1998. In a labelling project the attribute is the label, and the geometry is the place where it applies.

Step 3, coordinate order and CRS. In GeoJSON the order is longitude first, then latitude: [x, y] with x = lon. The Eiffel Tower is at longitude 2.2945 (east of Greenwich) and latitude 48.8584 (north of the equator), so its point is [2.2945, 48.8584]. Many APIs and maps write latitude first, so swapped pairs are a common error. We check this in the lab below.

Worked example: a footprint in degrees and in metres

Take a small square footprint in Paris with corners at longitude 2.3500 and 2.3502, latitude 48.8560 and 48.8562. Its side is 0.0002° in each direction.

Computing the area in degrees gives 0.0002 \times 0.0002 = 4 \times 10^{-8} square degrees. That number has no physical meaning, because a degree of longitude is not the same length as a degree of latitude.

At latitude 48.856°, one degree of longitude is about 111.32 \cos(48.856^\circ) \approx 73.24 km and one degree of latitude is about 110.57 km. The footprint is therefore about 14.65\ \text{m} \times 22.11\ \text{m} \approx 324\ \text{m}^2. (This local flat approximation is good enough for a single building; a projected CRS gives the same answer to within a percent.)

The rule: measure area and distance in a projected CRS, not in degrees.

Step 4, validity. A polygon must not cross itself. The "bow-tie" (0,0),(2,2),(2,0),(0,2),(0,0) has two lobes, each of area 2. Its signed shoelace area is 0, because the two lobes wind in opposite directions and cancel. Overlay and area tools fail or give nonsense on such rings, so a validity check (and a repair such as make_valid) belongs in every pipeline.

Step 5, choosing a format.

Lab: is that coordinate in the right country?

Try this
  1. Keep the defaults (Paris, stored as [lon, lat]). The reader and the producer agree, and the point lands in France.
  2. Set the producer to write [lat, lon] while the reader expects [lon, lat]. The point jumps to the Indian Ocean, and the readout says no listed box contains it.
  3. Press Nairobi with the same swapped setting. The point is read as longitude −1.29, latitude 36.82, which falls inside the approximate Spain box. The software would happily put the feature in the wrong country.
  4. Press Tokyo, swapped. The latitude becomes 139.69, which is impossible, so the validity check fails.
Common traps
  • Swapped coordinates do not raise an error. A valid-looking pair in the wrong order is still a valid point somewhere else. Validate that |latitude| ≤ 90 and check the result against an expected region.
  • Area in degrees is meaningless. Reproject to a metric CRS (for example the local UTM zone) before measuring area, buffering or distance.
  • A file without a CRS is not a georeferenced file. Shapefiles without a .prj and GeoJSON files with a legacy crs member are ambiguous. Ask for the CRS or check the source.
  • Invalid polygons spread errors. A bow-tie gives a wrong area and can make overlay results change sign. Run a validity check before every join.
Where it shows up in AI
  • Building, road and land-cover labels for segmentation are usually delivered as GeoPackage or GeoJSON polygons, and they must be rasterised onto the image grid (Module 3).
  • Open map datasets are published as GeoJSON or GeoParquet with coordinates in lon/lat, so a model trained on a metric CRS must reproject them first (lesson 1.5).
  • Annotation tools export GeoJSON features with a class property; the attribute table is the training label set.

Check yourself

1. A GeoJSON point is written as [48.8584, 2.2945]. Read by the GeoJSON rule, where is it?
Longitude 48.8584 and latitude 2.2945: a point in the Indian Ocean, a few hundred kilometres off the coast of Somalia. It is a valid coordinate, which is why the error is silent. The fix is to write [2.2945, 48.8584].
2. Why is the shoelace signed area of the bow-tie (0,0),(2,2),(2,0),(0,2),(0,0) equal to zero?
The two triangular lobes each have area 2 (unsigned total 4), but they are traversed in opposite directions. The signed sum adds +2 and −2 and gives 0. A zero area for a shape that clearly covers space is the signal that the ring is self-intersecting and invalid.
3. You must share 3 000 polygons with layer names longer than 10 characters and a 2.4 GB attribute table. Which format?
GeoPackage. Shapefiles would break the 2 GB file limit and truncate field names to 10 characters. A GeoPackage is one SQLite file that holds several layers with long names and no such limit.

Takeaways

  • Vector data is a table of geometries plus attributes; points, lines and polygons are rings and paths of coordinates.
  • GeoJSON is [longitude, latitude]; swapped pairs are valid and land somewhere else, so check ranges and expected regions.
  • Measure in a projected CRS, and validate polygons before using them.
1.3

Multidimensional arrays: NetCDF & Zarr

The questionYou have daily images of a 2 000 × 2 000 area for 1 827 days (five years), with one float32 value per pixel per day. That is 29.2 GB before any compression. Your task is to compute the average time series for one pixel. Reading the full cube to do it would take hours. How should the cube be stored so that a question about one pixel over time is cheap, and a question about one day is also cheap?

Intuition

A single GeoTIFF is naturally two-dimensional: rows and columns. A satellite time series adds a third dimension, time, so the data is a datacube: a box with axes (time, y, x). Asking a question means slicing the box, and the cheapest slice depends on how the box has been cut into pieces.

Think of a warehouse full of boxes. If each box holds one shelf of one week, finding everything about one product for one year means opening 52 boxes. If each box holds one product for one week, the same question is cheap, but a question about one whole shelf is now expensive. Chunking is the decision of how big each box is and which axes it spans.

NetCDF is a long-standing format for such arrays (its NetCDF-4 version sits on the HDF5 library and supports chunking and compression). Zarr is a newer format built for cloud object storage: each chunk is a separate object, and a small metadata file says the array's shape, chunk shape, data type and compressor. A reader can fetch just the chunk objects it needs, in parallel.

Build it up

Step 1, the cube. Our cube has shape (T, Y, X) = (1 827, 2 000, 2 000), float32 (4 bytes per value). Its size is 1827 \times 2000 \times 2000 \times 4 = 29\,232\,000\,000 B, about 29.2 GB.

Step 2, chunk shape. The array is cut into chunks of shape (ct, cy, cx). Chunk A below is 10 days by 256 by 256 pixels, which is 10 × 256 × 256 × 4 = 2 621 440 B (2.5 MiB) per chunk. The number of chunks along each axis is a ceiling division: \lceil 1827/10\rceil = 183, \lceil 2000/256\rceil = 8, \lceil 2000/256\rceil = 8, so the grid holds 183 × 8 × 8 = 11 712 chunks.

Step 3, lazy reads. A lazy library (for example xarray with dask) opens the metadata without touching any chunk. Operations such as "mean over time at one pixel" are recorded as a graph; the chunks are read only when the result is requested, and only the chunks that overlap the request.

Worked example: one pixel's time series with chunk shape A

The series for pixel (y = 1 000, x = 1 000) over all 1 827 days. Along time it overlaps \lceil 1827/10\rceil = 183 chunks. Spatially, 1 000 lies in chunk row \lfloor 1000/256\rfloor = 3 and chunk column 3, so one spatial chunk. The query therefore touches 183 chunks.

Bytes read: 183 \times 2\,621\,440 = 479\,723\,520 B, about 480 MB. The useful data is 1 827 × 4 = 7 308 B. The efficiency is 7\,308 / 479\,723\,520 \approx 0.0015\,\%. About 65 000 bytes are read for each byte needed.

Worked example: the same cube, three chunk shapes

Compare three shapes for two common questions: the pixel series at (1 000, 1 000), and one whole date (day 900, all pixels, 16 000 000 B of values).

Lab: chunks and lazy reads

Try this
  1. Keep the defaults and press Pixel time series, then Compute. Watch the time strip fill with the chunks along time, and read 183 chunks in the readout.
  2. Select shape B and compute the same query. It touches 1 chunk. Now press One date, all pixels with shape B: the spatial grid fills and the counter goes past 3 000 chunks. Only the query shape changes the answer.
  3. Try the 400 × 400 box over all times with shapes A and C. Count the chunks and note which one wastes less.

Common traps
  • Chunks are the unit of I/O. A query that needs one value still reads its whole chunk. Count chunks, not values.
  • Tiny chunks are also a problem. Millions of 10 kB objects make the metadata calls and request overhead dominate. Aim for chunks of a few megabytes.
  • Lazy does not mean free. Calling .values or a full reduction on a huge cube loads everything. Check the size before you compute.
  • NetCDF is not the same as Zarr. A NetCDF file on disk may be unchunked, or one big object on a server. Chunk layout is a property of the file, so inspect it.
Where it shows up in AI
  • Climate and weather data (reanalysis, forecasts) are distributed as NetCDF or Zarr; time-series models read windows along time and a small set of grid cells.
  • Training pipelines for temporal models (Module 7) sample many small spatiotemporal windows; the chunk shape decides whether that sampling is fast.
  • Feature stores for geospatial models often write per-tile time series in Zarr so that each training example is one chunk read.

Check yourself

1. A cube is (365, 1 000, 1 000) float32 and chunks are (30, 250, 250). How many chunks?
Along time ⌈365/30⌉ = 13 (12 × 30 = 360, so one more). Along y and x ⌈1000/250⌉ = 4 each. Total 13 × 4 × 4 = 208 chunks.
2. With chunk shape A (10 × 256 × 256), how many bytes does a 400 × 400 box over all 1 827 days read? (Box rows and columns 800 to 1 199.)
Spatial chunks: rows ⌊800/256⌋ = 3 to ⌊1199/256⌋ = 4, so 2; columns the same, so 2; that is 4 spatial chunks. Times: 183. Total 732 chunks × 2 621 440 B = 1 918 894 080 B (about 1.9 GB) to read 400 × 400 × 1 827 × 4 = 1 169 280 000 B of values, an efficiency of about 61 %.
3. Why does a chunk shape good for one pixel's full time series suit a single date badly?
A pixel series wants a long, thin chunk along time, so it reads one spatial chunk through all times. A single date wants all spatial positions at one time, which means many spatial chunks, each of which holds the whole time axis. With shape B, that is 3 969 chunks of 7.5 MB for 16 MB of values.

Takeaways

  • An array cube is stored as chunks; the chunk shape is a decision about which questions will be cheap.
  • Count chunks touched, because each chunk is read whole.
  • Zarr stores each chunk as its own object, which is why cloud reads can be partial and parallel.
1.4

Partial reads & the cloud archive

The questionYour 1 000 × 1 000 window lives in a 839 MB COG on a server far away. You could download the whole file, or you could ask only for the bytes you need. How many bytes must be requested, how many requests should you make, and how long will it take?

Intuition

Imagine ordering a book by phone. You could ask for the whole book (slow, expensive, and most of it is unused), or you could say "pages 46 to 52". The second request is only useful if the librarian can find the pages quickly, and if each call does not cost a minute of dialling. So the art is to ask for few calls, each carrying useful content.

HTTP has exactly this feature. A client sends a Range header with an inclusive byte interval, and a server that supports it replies with 206 Partial Content and only those bytes. Object storage (the buckets used for cloud archives) supports this, so a COG can be read as if it were a local file, one window at a time.

Build it up

Step 1, one request. A request for the first 64 KiB of a file looks like this:

GET /scene/B04.tif HTTP/1.1
Range: bytes=0-65535

HTTP/1.1 206 Partial Content
Content-Range: bytes 0-65535/838926336
Content-Length: 65536

The range is inclusive, so 0-65535 is 65 536 bytes. The response tells you the total size of the file, which the reader needs for planning.

Step 2, the cost model. Each request pays a fixed latency (the round trip to the server) and then transfers its bytes at some bandwidth. For a set of requests the total time is roughly

T \approx n_{\text{req}}\cdot L+\frac{B_{\text{total}}}{W}

With the illustrative numbers in the lab, L = 80 ms and W = 25 MB/s, the trade-off is visible. Each megabyte costs 40 ms at 25 MB/s, and each request costs 80 ms before its first byte arrives. Merging neighbouring ranges saves round trips; but a range that carries bytes you do not need wastes transfer time, so the best request covers exactly the useful tiles.

Step 3, what the window needs. From lesson 1.1 we know the window touches 3 tile rows and 3 tile columns. In this layout the tiles are stored row by row, so the three tiles in one tile row are adjacent in the file, and one range can cover all of them. Tile (r, c) of a file with n_x = 20 tile columns starts at

\text{offset}(r,c)=H+(r\,n_x+c)\,B_{\text{tile}}
Worked example: the window in byte ranges

Header and tile index: H = 65\,536 B, one request. Tile size B_{\text{tile}} = 2\,097\,152 B.

Tile row 1, tile columns 2 to 4. Tile (1, 2) has index 1 \times 20 + 2 = 22, so it starts at 65\,536 + 22 \times 2\,097\,152 = 46\,202\,880. Tile (1, 4) ends at 65\,536 + 25 \times 2\,097\,152 - 1 = 52\,494\,335. The request is Range: bytes=46202880-52494335, which is 3 \times 2\,097\,152 = 6\,291\,456 B.

Doing this for all three tile rows gives 4 requests (1 header plus 3 ranges) and 65\,536 + 3 \times 6\,291\,456 = 18\,939\,904 B. Time: 4 \times 0.08 + 18\,939\,904 / 25\,000\,000 = 0.32 + 0.76 = 1.08 s.

Requesting each of the nine tiles separately costs 1 + 9 = 10 requests and the same bytes: 10 \times 0.08 + 0.76 = 1.56 s. Merging neighbours saved half a second.

Downloading the whole 839 MB file: 0.08 + 838\,926\,336 / 25\,000\,000 \approx 33.6 s, and about 99 % of those bytes are never used.

Step 4, real files are not this neat. Real COG tiles are compressed, so their sizes differ. The file therefore stores two lists in the header: TileOffsets and TileByteCounts. The reader fetches them with the first request, then computes the exact range of each tile. The arithmetic in the lab is the simplified version in which every tile is uncompressed and stored in order.

Step 5, where the time goes. Libraries such as GDAL (through its /vsicurl/ paths) and rasterio issue these requests for you. They cache the header, merge neighbouring ranges and can run several requests in parallel. Knowing the model tells you when to expect slowness: many tiny requests are latency-bound, while one huge request is bandwidth-bound.

The formal definition

\texttt{Range: bytes=}a\texttt{-}b\qquad\text{returns } b-a+1 \text{ bytes, status } 206\text{ (not } 200\text{)}
T\approx n_{\text{req}}\,L+\frac{B_{\text{total}}}{W}
a, bfirst and last byte offsets of the range, both inclusive, counted from 0
n_reqnumber of requests, each paying one round trip latency L
Llatency per request (seconds); here 0.08 s, illustrative
B_totaltotal bytes transferred, including the header
Wbandwidth (bytes per second); here 25 MB/s, illustrative
H, B_tileheader size and bytes per tile in the simplified layout

Lab: a range request against a remote COG

Try this
  1. Press Read window, then Pause and Step to advance one request at a time. Read the byte ranges in the log: the second one is the first range of tile row 1.
  2. Change Ranges to one range per tile and read the same window. Count requests and time in the readout. Same bytes, more round trips.
  3. Press Download whole file. Note the time and the share of the file that is useful: a small fraction.
  4. Set latency to 400 ms. The merged version now takes about 2.4 s and the per-tile version about 4.8 s: round trips dominate, so merging matters more. Then set latency to 5 ms and bandwidth to 2 000 MB/s. Both versions finish in a few hundredths of a second. Which parameter dominates decides the best strategy.
Common traps
  • A server that ignores Range returns 200, not 206. The client then receives the whole file, silently. Check the status code in your logs.
  • Many tiny requests are slow even if the bytes are few. Merge neighbouring ranges, and reuse the cached header instead of re-reading it for every window.
  • Signed URLs expire. A long training job can fail halfway if the links it holds have passed their lifetime; refresh them from the catalogue.
  • Egress costs money. On commercial clouds, downloaded bytes are billed; a pipeline that reads whole scenes can cost far more than one that reads windows.
Where it shows up in AI
  • Data loaders for segmentation training read random 256 × 256 windows from remote COGs; the range-request cost of each window determines how many workers you need.
  • Inference services read the windows of a scene in parallel and write predictions back as a COG (lesson 5.7).
  • Catalogue-driven pipelines (Module 2) pass each asset's URL to such readers, so the same code works for a laptop file and a bucket.

Check yourself

1. A window touches 5 tile rows with 3 tiles each. How many requests with merged ranges, including the header, and how many with one range per tile?
Merged: 1 header plus 5 row ranges = 6. One per tile: 1 + 15 = 16. The bytes are identical; only the round trips change.
2. Ten requests with latency 50 ms transfer 100 MB in total at 50 MB/s. What is the time?
Latency 10 × 0.05 = 0.5 s; transfer 100 MB ÷ 50 MB/s = 2 s. Total 2.5 s. Here bandwidth dominates, so merging would save little.
3. The request Range: bytes=46202880-52494335 returns a 200 status and 839 MB. What went wrong?
The server ignored the Range header and sent the whole file. The status should have been 206 with 6 291 456 bytes. Check whether the server, a proxy or a CDN strips Range requests.

Takeaways

  • HTTP byte ranges let a reader fetch exactly the tiles a window needs, if the file's layout allows it.
  • Time = requests × latency + bytes ÷ bandwidth; merge ranges when latency dominates.
  • Check that you received 206 and the byte count you expected.
1.5

Reprojection & resampling

The questionSentinel-2 red and NIR bands are 10 m, its SWIR bands are 20 m, and the land-cover labels you bought come in WGS84 latitude and longitude on a 5 m grid. Your model needs one stack with identical grids. How do you move every source onto the same pixels, and which rule do you use for each kind of data?

Intuition

Two different things must happen. Reprojection changes the map: a new grid is laid over the ground, in a new coordinate reference system, with new pixel positions. Resampling answers the question "what is the value at this new pixel?" The new pixel centre falls somewhere between old pixel centres, so a value must be looked up, copied or blended.

Think of tracing a map onto transparent paper. Where a new grid line falls inside an old square, you decide whether to copy the colour of the nearest square, average the four surrounding squares, or fit a smooth curve through the neighbourhood. Each choice is right for some data and wrong for others.

Build it up

Step 1, the output grid. The output has its own size, pixel size and origin in the target CRS. Every output pixel centre has a ground position, and that position is converted back to a source row and column. This backward mapping is why reprojection never leaves holes.

Step 2, the pixel-centre rule. For an output of M pixels across a source of n pixels, output index j lies at source position

x_{\text{src}}=(j+0.5)\cdot\frac{n}{M}-0.5

with edges clamped to the nearest source pixel. Here n = 3 and M = 5, so the positions are −0.2, 0.4, 1.0, 1.6 and 2.2.

Step 3, the methods. Nearest copies the value of the closest source pixel. Bilinear blends the 2 × 2 neighbours with weights from the fractional position. Cubic (here the Keys kernel with a = −0.5) blends 4 × 4 neighbours with smoother weights. When downsampling, the usual choices are the average for continuous data and the mode (most frequent value) for classes.

Worked example: a 3 × 3 patch to 5 × 5

Source patch (rows top to bottom):

A=\begin{pmatrix}10&20&30\\40&50&60\\70&80&90\end{pmatrix}

Nearest. The positions per axis are −0.2, 0.4, 1.0, 1.6, 2.2, which round (after clamping) to indices 0, 0, 1, 2, 2. Every output value is a copy, giving rows 10 10 20 30 30 / 10 10 20 30 30 / 40 40 50 60 60 / 70 70 80 90 90 / 70 70 80 90 90.

Bilinear, pixel (1, 1). The position is x = 0.4, y = 0.4. In the top row, the neighbours 10 and 20 give 10(0.6)+20(0.4)=14. In the bottom row, 40 and 50 give 40(0.6)+50(0.4)=44. Blending the two rows vertically: 14(0.6)+44(0.4)=26. The bilinear grid's second row is 22, 26, 32, 38, 42.

Bilinear, pixel (1, 2). The position is x = 1.0 (exactly on source column 1) and y = 0.4. The blend is 20(0.6)+50(0.4)=32.

Cubic, pixel (1, 1). The 4 × 4 weights for offset 0.4 are −0.072, 0.696, 0.424 and −0.048 (they sum to 1). Applied along both axes the value is 23.12. Cubic can go slightly outside the source range; the lab shows this on a sharp edge.

Step 4, labels are not reflectance. A class map holds codes such as 1 = water, 2 = forest, 3 = urban. Bilinear blending of codes invents codes. Take the class map \begin{pmatrix}1&1&2\\1&2&2\\3&3&2\end{pmatrix}. Bilinear at output (1, 1) gives 1.16, and at output (1, 2) gives 1.40. Neither is a class. Nearest gives 1 at output (1, 2), which is a real class. Use nearest for labels and masks, and average or mode when downsampling.

Worked example: downsampling 10 m to 20 m

Reflectance 2 × 2 block: (1200+1250+1190+1210)/4 = 1212.5 (mean). Class block [1, 1; 1, 2]: the mean would be 1.25, which is no class, so the mode is used and the answer is 1.

Step 5, aligning a stack. Two grids are aligned only when they share a CRS, a pixel size, an origin (the geotransform) and a shape. Check these numbers rather than trusting that two layers "look the same" in a viewer. Choose a target CRS for the study area: a local UTM zone keeps distances and areas accurate within the zone, and an equal-area CRS suits statistics across large regions. Web Mercator, popular in web maps, inflates areas more the further you are from the equator.

Where it sits in the pipeline. This is the Preprocessing stage: reprojection and resampling put every source on the model's grid before tiling.

The formal definition

v(x,y)=\sum_{i}\sum_{j} w_i(x)\,w_j(y)\,A_{ij}\quad\text{(separable kernel, bilinear or cubic)}
k(s)=\begin{cases}(a+2)|s|^3-(a+3)|s|^2+1,&|s|<1\\ a|s|^3-5a|s|^2+8a|s|-4a,&1\le|s|<2\\ 0,&\text{otherwise}\end{cases}\qquad a=-0.5
A_ijsource value at row i, column j (indices are clamped at the edges)
w_i(x), w_j(y)weights along each axis; they sum to 1 for each position
x_srcsource position of an output pixel centre (pixel-centre rule)
sdistance in source pixels from the sample point to a neighbour
akernel parameter; −0.5 is the common Keys choice

Lab: nearest, bilinear, cubic on an editable patch

Try this
  1. With bilinear and the default patch, press Step until the orange cursor reaches output (1, 1). The readout should give 26.
  2. Switch to nearest and watch the same pixel. The patch values are copied; no new numbers appear.
  3. Press Load class map, set Data to categorical and use bilinear. Red slashes mark output pixels whose blended value is not a class.
  4. Reset, set the values to a sharp edge (0, 0, 100 in each row) and use cubic. Some outputs go below 0 or above 100 (ringing). A smooth method is not automatically a safe one.
Common traps
  • Resampling the labels with bilinear or cubic. You create classes that do not exist. Use nearest for every categorical layer.
  • Reprojecting twice. Each reprojection resamples again, so values drift and blur. Reproject once, from the original file, to the final grid.
  • Forgetting the alignment check. A half-pixel offset is invisible in a viewer and shifts every label against its pixel, which quietly lowers accuracy.
  • Averaging across a cloud or nodata edge. Mask first (lesson 1.6), then resample, or the mean includes invalid values.
Where it shows up in AI
  • Every multi-source EO model: Sentinel-2 at 10 m and 20 m, Sentinel-1 radar and a DEM must share one grid before the network sees them.
  • Segmentation labels are rasterised and resampled with nearest; the model's output is a class map, so any blending at the output stage would break the metric.
  • Super-resolution and downscaling models (STAC MLM tasks, Module 6) are evaluated against resampled references, so the resampling method is part of the benchmark.

Check yourself

1. Bilinear at a point with fractional offsets (x = 0.25, y = 0) between values 40 and 80 in the same row. What is the value?
The row is at integer y, so only x matters: 40(0.75) + 80(0.25) = 30 + 20 = 50.
2. A class map is downsampled 2 × 2 → 1 with values [3, 3; 3, 5]. Average or mode, and why?
Mode: the most frequent code is 3. The average would be 3.5, which is class 3.5 and does not exist.
3. You reproject a reflectance layer, then a cloud mask, then apply the mask. Which step is wrong?
The mask was resampled with a blending rule. Bilinear turns a 0/1 mask into fractional values along cloud edges, and cloud brightness leaks into the blended reflectance next to them. Apply the mask at source resolution first, then reproject the masked data once, or resample the mask with nearest.

Takeaways

  • Reprojection defines the new grid; resampling decides each new value.
  • Nearest for labels and masks, bilinear or cubic for continuous data, average or mode when downsampling.
  • Verify alignment by CRS, transform and shape; resample once.
1.6

No-data, quality masks & cloud masking

The questionA quarter of your scene is covered by cloud, and some pixels were not measured at all (they hold the value 0). You train on the raw mosaic. The model learns that bright means building and dark means water, and it treats the unmeasured zeros as deep water. How do you keep only the trustworthy pixels, and how do you compute statistics that ignore the rest?

Intuition

A satellite product carries side information next to the measurements. Some pixels say "no data here" (a nodata value); others come with a quality band that reports how likely each pixel is to be cloud, cloud shadow or snow. A mask is the rule that turns this side information into a yes or no for every pixel. Using the mask means that each computation, from a mean to a training loss, skips the pixels marked no.

Think of a survey in which some answers are blank and some respondents said "I was not there". You would not count a blank as zero, and you would not average in answers from people who did not see the event. The mask is that bookkeeping.

Build it up

Step 1, nodata. A nodata value is a number that cannot be a real measurement, for example 0 for many reflectance products or −9999 for elevation. It must be declared in the file (the GeoTIFF nodata tag). If it is not, the zeros are treated as dark pixels, and every mean and every model input is biased.

Step 2, quality bands. Many products ship a classification band. Sentinel-2 Level-2A includes a Scene Classification Layer (SCL) in which codes 8 and 9 mark cloud with medium and high probability and code 3 marks cloud shadow. Other products give a continuous cloud probability from 0 to 100. A threshold turns the probability into a mask: a pixel is cloudy when its probability is at least t.

Step 3, a worked 4 × 4 scene. Reflectance band (x 10⁴ units, shown as plain numbers) and cloud probability (%):

Worked example: masking the scene

Apply the rule cloudy if probability ≥ 50. The cloudy pixels are r1c1 (90), r1c2 (85) and r2c1 (80): 3 of 16, a cloud fraction of 3/16 = 18.75\,\%. The pixel r3c3 holds 0, so it is nodata. That leaves 16 - 3 - 1 = 12 usable pixels.

Mean reflectance of the 12 usable pixels: 14\,900 / 12 \approx 1241.7.

Naive mean of all 16 pixels, with no mask: 24\,050 / 16 = 1503.1. This is biased upward by the bright clouds and downward by the zero, and it describes neither the land nor the clouds.

Mean of the valid, non-nodata pixels with the clouds kept: 1603.3. The cloud brightness alone moves the mean by about 360 units, about 29 %.

Step 4, the formal rule. Combine the nodata test and the quality test into one usable mask for each pixel. Statistics and losses then use only the pixels where the mask is 1.

Step 5, the order of operations. Mask at the source resolution first, then reproject and resample the mask with nearest, then the data with its own method (lesson 1.5). Otherwise a bilinear resample spreads cloud brightness into the pixels next to every cloud. Clouds also have halos: thin cloud and shadow edges are often missed, so many pipelines dilate the cloud mask by a few pixels before use.

Step 6, honest training. In a segmentation loss, masked pixels are excluded with an ignore index (a label value, often 255, that the loss skips). That way the model is not asked to predict a class where the input is unreliable.

Where it sits in the pipeline. This is the Preprocessing stage, between reading the windows and tiling them.

The formal definition

M(p)=\mathbf 1\bigl[x(p)\neq x_{\text{nodata}}\bigr]\cdot\mathbf 1\bigl[q(p)<t\bigr]
\bar x_M=\frac{\sum_p M(p)\,x(p)}{\sum_p M(p)},\qquad f_{\text{cloud}}=\frac{\#\{p:\ q(p)\ge t\}}{N}
x(p)the measured value at pixel p (for example reflectance)
x_nodatathe declared nodata value
q(p)quality value at p: cloud probability in percent, or 1 if the class is cloud
tcloud threshold; the pixel is masked when q(p) ≥ t
𝟏[·]indicator: 1 when the condition is true, otherwise 0
M(p)usable mask: 1 keeps the pixel, 0 removes it

Lab: a cloud threshold you can sweep

Try this
  1. Start at threshold 50 and note the cloud fraction and the usable count. Compare with the 4 × 4 example: the lab's scene is different, but the rule is the same.
  2. Press Sweep and watch the masked area shrink as the threshold rises. At 0 almost everything bright is masked; at 100 only the most confident cloud remains.
  3. Find the threshold at which the usable mean stops changing much. Then compare the usable mean with the mean of all valid pixels; the gap is what the clouds would have done to your statistics.
  4. Switch scenes and see how nodata behaves: the black stripe is excluded from every count and never called water.
Common traps
  • Nodata is treated as a measurement. Zeros drag means down and teach the model a fake dark class. Declare nodata once and check that every statistic uses the mask.
  • One mask, several bands. A mask from the cloud band must apply to every band and to the label. Apply it by pixel, not by band index.
  • Bright non-cloud surfaces. Snow, bare soil, sand and urban roofs can look like cloud in a probability product. Check the mask on samples from each of these.
  • Thresholds chosen by eye. Choose the threshold on labelled samples, and report it with the dataset manifest (Module 3).
Where it shows up in AI
  • Cloud-free composites: the median of usable pixels across many dates, computed with the mask on each date.
  • Segmentation training with an ignore index so that clouds and nodata do not teach the network false classes.
  • Foundation models pretrained on EO archives (Module 7) usually expect masked, normalised inputs; feeding them the raw mosaic is a common silent error.

Check yourself

1. A 5 × 5 scene has 5 cloudy pixels and 0 nodata. What are the cloud fraction and the usable count?
Cloud fraction 5/25 = 20 %. Usable 25 − 5 = 20 pixels.
2. Using the 4 × 4 scene, what changes if the threshold is 85 instead of 50?
Only pixels with probability ≥ 85 are cloudy: 90 and 85 (r1c1 and r1c2). The pixel with 80 (r2c1) becomes usable. Cloudy count 2, nodata still 1, usable 13. The usable mean is (14 900 + 3 050) / 13 ≈ 1380.8. The jump comes from one bright pixel that the lower threshold had removed, which shows how sensitive a mean is to the threshold.
3. Why is it wrong to resample the cloud mask with bilinear and then apply it to the reflectance?
Bilinear produces fractional values at mask edges (for example 0.4 instead of 0 or 1). Thresholding those values gives an arbitrary boundary, and the cloud brightness leaks into neighbouring clear pixels through the blend. Use nearest for the mask, or mask before resampling.

Takeaways

  • Nodata is a declared value; quality bands and thresholds turn side information into a per-pixel mask.
  • Every statistic and loss uses the mask; the usable mean is not the naive mean.
  • Mask first, resample the mask with nearest, and choose thresholds on labelled data.
