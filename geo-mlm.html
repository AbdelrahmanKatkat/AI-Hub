6.1

Why describe models with metadata

The questionA colleague sends you a file called landcover_v3.pt and says "it maps land cover from Sentinel-2". Before you can run it on a scene from last month, you need answers: which bands, in what order? What patch size? What scaling? Which classes come out, and in what order? How much GPU memory? Where is the code that turns the file into a map? None of this is in the file name.

Intuition

Think of a tin of food. The metal can holds the food, but the label tells you what it is, how much it contains, what it needs (refrigerate after opening) and whether it contains nuts. You could open the tin and taste it, but you would rather read the label. A trained model is the same: the weights are the contents, and a model record is the label.

Earth-observation teams have a second reason. A model trained on four 10 m bands will silently produce garbage if you feed it six bands, or the same four bands in a different order, or reflectance that was not divided by 10 000. The model does not complain. It returns numbers. So the record has to state the contract: the exact inputs the model expects and the exact outputs it promises.

STAC already solved the discovery half for data (Module 2): a catalogue lists items, each with a bounding box, a date and properties, so a program can search without downloading. The STAC Machine Learning Model extension (MLM) applies the same idea to models. A model becomes an Item that can be searched by task, input bands, framework and size, and whose assets (the weights file, the code) are linked with explicit roles.

Build it up: finding a model by its label

Suppose a catalogue holds three models. The question is: which models do semantic segmentation, take the four bands B02, B03, B04 and B08, and expect 256-pixel patches?

Worked example — three records, one query
Modelmlm:tasksInput bandsPatchMatches?
A: unet-landcover-s2-demosemantic-segmentationB02, B03, B04, B08256yes
B: scene-taggerclassificationB02, B03, B04, B0864no (task and patch)
C: hires-building-netsemantic-segmentationB02 to B12 (10 bands)512no (patch; bands are a superset, which some queries accept)

One model out of three. Notice that Model C is not excluded by the bands test, because it contains all four bands. Whether a superset is acceptable is a decision for the user, and a catalogue search can only be as precise as the record allows.

This is the whole value of the extension. Without the record, the question above needs a human to open the model's documentation (if any) and read the code. With the record, a program answers it in one query.

Where this sits in the pipeline Publish & monitor, and the first step of inference. The record is written when a model is published and read whenever someone searches for or runs it. It is stored as a STAC Item in a catalogue, next to the weights (as an asset), not inside them.

The formal definition

An MLM record is a STAC Item: a GeoJSON Feature with an id, a geometry and bbox (where the model applies, or where it was trained), a datetime, properties and assets. The extension adds fields whose names start with mlm: and declares its schema in stac_extensions:

\mathcal{R}=\big(\text{properties},\;\text{assets}\big),\qquad \text{properties}\supseteq\{\texttt{mlm:tasks},\texttt{mlm:input},\texttt{mlm:output},\dots\}
Itemone STAC record that describes one model (here, a model record)
propertiesthe JSON object holding metadata such as datetime and all mlm:* fields
assetsnamed files or links belonging to the Item (weights, code, container), each with roles
mlm:the field-name prefix that identifies fields defined by the MLM extension, version 1.6.0 at the time of writing
⊇"contains at least"

Two honesty rules sit underneath the schema. First, the record describes what the authors claim; Lesson 6.9 shows how to check claims against the artifact. Second, the extension is additive: a tool that does not understand MLM still reads the Item as an ordinary STAC Item.

Lab

Try this
  1. Press Run query. Watch each record be tested field by field, and read the caption for the reason each one fails or passes.
  2. Change the patch size to 512 and run again. Model A now fails. Explain why in one sentence before you look at the answer in the caption.
  3. Keep the patch at 512 and tick "accept a superset of the bands", then run. Model C now passes. Decide whether that is the behaviour you want for a building model.
Common traps
  • The file name is not metadata. final_v3_best.pt says nothing about bands. Always read the record.
  • The record is a claim. A publisher can write any number. The extension makes claims searchable, not true; Lesson 6.9 covers checking them.
  • Metadata on the wrong level. Fields such as mlm:input belong to the Item, not to the weights file. Putting them on an asset breaks the rule (Lesson 6.2).
Where it shows up in AI
  • Model catalogues such as the Hugging Face Hub and cloud model registries hold a card per model; MLM is the same idea in STAC form, so it can be searched with the same tools as imagery.
  • Geospatial foundation model releases publish pretrained encoders with their band lists and patch sizes so that users can check compatibility before downloading gigabytes of weights (Module 7, lesson model-zoo-stac).
  • Automated inference services read the record to configure themselves, which is the subject of Lesson 6.8.

Check yourself

1. Why is a model file alone not enough to run it on a new scene?
Because the file does not say which input bands and in what order, the patch size, the scaling, the output classes or the memory needed. A model fed the wrong contract returns numbers without any error, so the expected inputs and outputs must be written down somewhere.
2. In the worked example, why does Model C fail the query when the band test is satisfied?
Because its patch size is 512, not 256. Its bands are a superset of the four requested bands, so the bands test passes; the patch test fails.
3. Why does the STAC MLM extension add fields instead of a new file format?
Because a model record is a STAC Item, and STAC is designed to be extended with prefixed fields. Tools that know nothing about MLM still read the Item, and the same catalogue search machinery can find models alongside data.

Takeaways

  • A model without a record forces a reader to guess its inputs, outputs and cost.
  • An MLM record is a STAC Item: properties with mlm:* fields, plus assets with roles.
  • The record is a claim. It becomes trustworthy only when checked (Lesson 6.9).
6.2

The MLM item

The questionYou are publishing a land-cover model. What must the record contain at minimum, where does each piece go (Item or Asset), and how do you write it so that a validator accepts it? Get one field in the wrong place and the record is invalid.

Intuition

An MLM Item is a STAC Item with two kinds of content. The properties describe the model as a whole: its name, what it does, its size, the contract it expects. The assets are the files: the model itself, its weights, its code. The properties are the label on the tin; the assets are the tin's contents.

The first thing to learn is the list of required fields. A valid MLM Item must carry mlm:name, mlm:architecture, mlm:tasks, mlm:input and mlm:output, and at least one asset with the mlm:model role (Lesson 6.4). The rest is recommended, and the extension adds a set of resource fields that help a planner decide where the model can run.

Build it up: the Item, step by step

Start with an ordinary STAC Item and add the MLM parts one group at a time.

  1. Identity. type is "Feature", stac_version is the STAC version (here "1.0.0"), and id is unique in the catalogue.
  2. Where and when. geometry is a GeoJSON polygon in longitude, latitude (WGS84, Module 0), bbox is its envelope, and properties.datetime is the time of the record. These make the model discoverable on a map and by date.
  3. Extensions. stac_extensions lists the MLM schema URL, https://stac-extensions.github.io/mlm/v1.6.0/schema.json. A validator uses this URL to know which fields to expect. An MLM item should also list the extensions it reuses, such as classification and eo (we list both below), because the extension delegates some fields to them. The band names in mlm:input are one example: MLM requires named bands to be described by the eo or raster extension (or by STAC 1.1 bands), so the record below declares eo and puts eo:bands on the model asset, as the MLM repository's own band example does.
  4. Identity of the model. mlm:name is the model's name (Item-only), mlm:architecture is the family (U-Net), mlm:tasks is an array of task values (Lesson 6.6).
  5. Framework and size. mlm:framework, mlm:framework_version, mlm:total_parameters, mlm:memory_size (bytes). Lesson 6.5 shows how each number is derived.
  6. Contract. mlm:input and mlm:output, each an array of objects (Lesson 6.3).
  7. Assets. The model, the weights and the code, each with roles (Lesson 6.4).

Where this sits in the pipeline Publish. The record is written once, validated, and then stored in the catalogue. Its assets (the model file, weights, code) are stored in object storage and referenced by href; the Item itself holds only text and numbers.

The formal definition

\text{Valid}(R)\iff \underbrace{\text{GeoJSON}(R)\wedge\text{STAC}(R)}_{\text{core}}\wedge\underbrace{\bigwedge_{f\in F_{\text{req}}}\text{present}(f)}_{\text{MLM required}}\wedge\underbrace{\bigwedge_{f\in\text{Item-only}}\text{on-Item}(f)}_{\text{placement}}
Rthe record, one STAC Item
F_reqthe required MLM fields: mlm:name, mlm:architecture, mlm:tasks, mlm:input, mlm:output, plus the required asset with role mlm:model
Item-onlymlm:name, mlm:input, mlm:output, mlm:hyperparameters: they may not sit on Assets
∧, ⋀"and" over a list of conditions
present(f)field f exists with a value of the right type

Notice that mlm:name is item-only and also may appear on a Collection; the others are left out of Collection summaries (Lesson 6.7).

Common traps
  • Forgetting stac_extensions. Without the schema URL, fields prefixed mlm: are unknown to validators.
  • Listing MLM as the only extension. The extension reuses others (classification here, and eo, raster, datacube, processing) and an Item should declare them too.
  • Putting mlm:input on the weights file. The contract describes the model, so it belongs on the Item. The weights are a bag of numbers without any shape information.
  • Mixing units in memory. mlm:memory_size is bytes. "50.8" with no unit is ambiguous (MB? MiB? GB?).
Where it shows up in AI
  • Published geospatial models on public registries carry an MLM Item beside their STAC data. The same JSON can be validated with the STAC and MLM schemas.
  • Model examples in the MLM repository (such as a PyTorch U-Net with an EfficientNet encoder) follow the same structure as this record.

Check yourself

1. Which fields may only appear on the Item, not on an Asset?
mlm:name, mlm:input, mlm:output and mlm:hyperparameters. Asset fields such as mlm:artifact_type, mlm:compile_method and mlm:entrypoint go on assets.
2. In the record, why is the classification extension listed although we never write a top-level classification: field?
Because classification:classes is used inside mlm:output, and the MLM extension delegates the class definition to classification. Listing the extensions a record uses is what lets a validator know which schemas apply.
3. The record says mlm:memory_size: 50804568. How many megabytes is that, and what does the number refer to?
50 804 568 bytes = 50.80 MB in decimal units (48.45 MiB in binary units). It refers to the accelerator memory needed in inference for the batch given by mlm:batch_size_suggestion, which is 4 here.

Takeaways

  • An MLM Item is a STAC Item whose properties carry mlm:* fields and whose assets carry roles.
  • Five properties are required (name, architecture, tasks, input, output) plus a mlm:model asset.
  • Placement is part of validity: contract fields belong to the Item, file details to the assets.
6.3

Describing inputs & outputs

The questionA scene arrives as ten Sentinel-2 bands stored in one file, in the order B02, B03, B04, B05, B06, B07, B08, B8A, B11, B12. The model was trained on four bands, in the order B02, B03, B04, B08, with reflectance between 0 and 1, and it expects 256 × 256 patches. Which bands do you read, in what order, how do you scale them, and what do you do with a patch at the edge of the scene? Every one of these choices changes the map.

Intuition

A model's input is a socket. It has a fixed shape, a fixed order of pins and a fixed voltage. A plug that is the right size but wired backwards does not blow a fuse: it simply produces a smoke-free, wrong answer. The contract in mlm:input is the socket's specification, and mlm:output is what comes out the other side, with its own labels for the pins.

Four things must be written down, because each one can be done in several ways:

  • Which bands, and in which order. The model's first convolution has one weight per input channel. Channel 0 means "whatever the record calls band 0".
  • The shape and the axis order. [-1, 4, 256, 256] means batch, then 4 channels, then 256 rows, then 256 columns. The -1 is the batch axis: the runner chooses how many patches to send at once.
  • The scaling. Raw digital numbers (DN) from Sentinel-2 are stored as integers scaled by 10 000. Dividing by 10 000 gives reflectance; clipping keeps the result in [0, 1].
  • The resize rule. What happens when a patch does not match the shape: crop it, pad it, or resample it.

Build it up: from ten bands to four channels

Number the stack from zero. The four bands we need sit at positions 0 (B02), 1 (B03), 2 (B04) and 6 (B08). The runner builds a channel selection from the record's bands list, and it does so by name, not by guessing the position.

Worked example — selecting bands, scaling, clipping

Stack order: B02 = 0, B03 = 1, B04 = 2, B05 = 3, B06 = 4, B07 = 5, B08 = 6, B8A = 7, B11 = 8, B12 = 9. The record asks for ["B02","B03","B04","B08"], so the selection is [0,1,2,6]. Note that not [0,1,2,3]: position 3 is B05, a red-edge band.

Take one pixel whose raw values are B02 = 1534, B03 = 1210, B04 = 980, B08 = 12000. Apply scale 0.0001, then clip [0, 1]:

BandRaw DN× 0.0001clip to [0,1]
B0215340.15340.1534
B0312100.12100.1210
B049800.09800.0980
B08120001.20001.0000

B08 exceeds 1 after scaling, so clipping sets it to 1.0. A bright cloud or a bright built-up roof would do the same. Clipping is a choice the record must state, because without it the model sees values it was never trained on.

Build it up: shapes flowing through the contract

The input shape declares one patch as 4\times256\times256 values. Each value is a 32-bit float, 4 bytes. One patch therefore takes 4\cdot256\cdot256\cdot4=1\,048\,576 bytes, which is exactly 1 MiB. The output declares 6\times256\times256: six class scores per pixel, so one output patch takes 6\cdot256\cdot256\cdot4=1\,572\,864 bytes (1.5 MiB). The output is larger than the input, which is typical of segmentation: the model answers with a score for every class at every pixel.

Worked example — how many patches cover a scene?

A scene of 1000 × 1000 pixels at 10 m is 10 km × 10 km. Patches are 256 pixels with stride s (the step between neighbouring patch origins). Along one axis the number of patches is n=\left\lceil\frac{W-p}{s}\right\rceil+1, with W = 1000 and p = 256.

With stride 128 (50 % overlap): n=\lceil 744/128\rceil+1=\lceil 5.81\rceil+1=7, so 7 × 7 = 49 patches.

With stride 256 (no overlap): n=\lceil 744/256\rceil+1=\lceil 2.91\rceil+1=4, so 4 × 4 = 16 patches. The last window now runs past the scene edge by 24 pixels, and the resize_type rule decides what fills those pixels.

Edge patches: why "pad", not "resample"

The resize enumeration in MLM offers crop, pad and several interpolation-* values. For a land-cover model that outputs labels on the Sentinel-2 grid, resampling is wrong: it moves pixel centres, so a label predicted for pixel (i, j) no longer refers to the ground it covered. pad keeps the grid exact and fills the missing rows or columns with a declared no-data value, which the post-processing then sets to 255. The record says "resize_type": "pad"; a runner that reads it must pad, not stretch.

The output contract

mlm:output names the result (landcover), its task, its shape ([-1, 6, 256, 256], dimension order batch, class, height, width), and the meaning of each class index in classification:classes. Each class needs a value (the integer the map will contain) and a name. The output holds logits (raw scores, not probabilities); post_processing_function states how a map is made from them, here an argmax over the class axis.

Where this sits in the pipeline Preprocess (input contract: bands, scaling, shape, resize) and post-process (output contract: argmax, class codes). Preprocessing output is a tensor held in memory; post-processing output is a single-band raster of class codes, written as a COG (Module 1).

The formal definition

x_{n,c,i,j}=\operatorname{clip}_{[0,1]}\!\big(10^{-4}\,\mathrm{DN}_{n,\,b_c,\,i,\,j}\big),\qquad \hat y_{n,i,j}=\arg\max_{k}\,Y_{n,k,i,j}
xthe input tensor of shape N × C × H × W, here C = 4, H = W = 256
DNraw digital number of the scene (integer reflectance × 10 000)
b_cthe scene band selected for channel c, found by name from bands
clipkeeps values inside [0, 1]
Ythe logits, shape N × K × H × W, K = 6 classes
argmax_kthe class index k with the largest score at that pixel
ŷthe predicted class map written to the output raster
Common traps
  • Band order by position. Selecting "the first four bands" of a stack is only right when the stack is in the model's order. Select by name.
  • Scale twice, or not at all. A record that says "scale 0.0001" and a runner that also divides by 10 000 produce values near zero. State each step once, in one place.
  • Resampling labels. Interpolating a class map blends class codes (2.5 is not a class). Use nearest neighbour for labels.
  • Confusing axis order. PyTorch expects N × C × H × W; many tools store H × W × C. The dim_order field exists to remove the guesswork.
Where it shows up in AI
  • Sentinel-2 foundation models publish input contracts with exact band lists, because a model trained on one band set cannot take another without retraining or adapting its first layer.
  • Segmentation pipelines (Module 5, segmentation-unet) use the same shape table: 256 × 256 × 4 in, 256 × 256 × 6 out.

Check yourself

1. The record asks for B02, B03, B04, B08 from a stack ordered B02 … B12 as in the worked example. Which 0-based positions do you read?
0, 1, 2 and 6. Position 3 is B05, not B08.
2. A raw B08 value is 2400. What is the channel value after scaling and clipping?
2400 × 0.0001 = 0.24; it lies inside [0, 1], so the clipped value is 0.24.
3. A 1000-pixel scene with 256-pixel patches and stride 128: how many patches per axis, and why might resize_type matter for the last one?
Seven per axis, from ⌈744/128⌉ + 1 = 7. The last window extends past the edge; with pad it is filled with no-data, while resampling would move the pixel grid and misplace the labels.

Takeaways

  • The input contract fixes bands (by name), shape and axis order, data type, scaling and edge handling.
  • The output contract fixes the task, the result shape and the meaning of each class code.
  • Labels are never resampled; edges are padded so that every pixel keeps its ground position.
6.4

Model assets & roles

The questionYour record lists three files: a model, a state dict and a Python script. A runner must find "the model" without knowing your file names. How does it know which file is which, what happens if the code asset is missing, and what should a container asset add?

Intuition

In a STAC Item every asset is a file with a name, a link (href) and a type (media type). A file's name cannot tell a program what it is for: infer.py could be training code or a helper. Roles solve this. A role is a label from a small vocabulary that says what an asset is for. A program searches assets by role, the way a warehouse finds a box by its label, not by where it is shelved.

Roles are a list, so one asset can have several: a full model file that also holds the weights can carry both mlm:model and mlm:weights.

Build it up: the roles that matter

  1. mlm:model (required). The main model asset. A valid MLM Item needs at least one. Because the file is the model, the asset must also carry mlm:artifact_type saying what kind of file it is (for example torch.save for a pickled PyTorch module). mlm:compile_method is optional: aot (ahead-of-time compiled) or jit (just-in-time), or null.
  2. mlm:weights (or plain weights). The learned numbers, when they are stored separately from the model definition. A state dict is weights only: the runner still needs the architecture from the code or the model asset to load it.
  3. mlm:source_code with role code (recommended). The script that turns the model into predictions: reading inputs, normalising, tiling, post-processing. If the asset carries mlm:entrypoint (the function to call), the code role becomes mandatory.
  4. runtime, mlm:container. A container asset (an OCI image index, in the example's media type application/vnd.oci.image.index.v1+json) packages the software environment, so the model runs on any machine with a container engine. Its role is runtime.
  5. mlm:training and mlm:inference. Asset objects (recommended) that point to the pipelines for training and for inference, when they are published as separate artifacts.
Worked example — three assets, three jobs

Our record (Lesson 6.2) has three assets. The sizes below are computed in Lesson 6.5 from the architecture: the state dict holds 117 590 parameters at 4 bytes each, which is 470 360 bytes, plus 2 560 bytes of batch-norm running statistics, so about 473 KB. The full module file is of the same order.

Asset keyrolesExtra fieldsWhat the runner uses it for

weights["mlm:weights"](none)a state dict to load into the architecture defined by the code

Our record gives the model asset only the mlm:model role and keeps the weights as a separate asset. The MLM repository's own PyTorch example instead lists mlm:weights on its model asset, which tells a reader that one file is complete. The spec allows either layout. Choose one and say which in the description.

Version check. In MLM v1.6.0, mlm:entrypoint is an asset field. The published JSON Schema rejects it in Item properties, and it accepts it on an asset only when that asset also has the code role, which is how this record is written. Some older examples show it at the top level of the Item; if a validator pinned to another version complains, check its version before changing your record.
Where this sits in the pipeline Publish (packaging the assets) and acquire-to-run (the runner resolves roles to files). Assets are stored in object storage; the Item keeps only links and roles.

The formal definition

\text{runnable}(R)\iff\exists\,a\in A:\ \texttt{mlm:model}\in\text{roles}(a)\ \wedge\ \big(\text{entrypoint}(a)\neq\varnothing\Rightarrow\exists\,c\in A:\ \texttt{code}\in\text{roles}(c)\big)
Athe set of assets of the record

Common traps
  • Naming by file name. Calling a file model does not give it the mlm:model role. The role must be written in roles.
  • Missing artifact type. A model asset without mlm:artifact_type is invalid, because the runner cannot know how to load it.
  • Weights without architecture. A state dict cannot be run alone. Point to the code or the model file that defines the architecture.
  • Item-only fields on assets. mlm:input on an asset is invalid. Contract fields go on the Item (Lesson 6.2).
Where it shows up in AI
  • Model hubs separate weights, configuration and code into files with names and roles, so tools can download only what they need.
  • Container runtimes for GPU inference are published as runtime assets so that the same environment runs on a laptop and on a cluster.

Check yourself

1. A record has an entrypoint on its source-code asset but no asset with the code role. Is it valid?
No. The code role is mandatory whenever mlm:entrypoint is set. The record must add a code asset or drop the entrypoint.
2. Why can a model asset carry both mlm:model and mlm:weights?
The spec lets the model role list the weights role "as applicable": a single file that contains the full model, including its weights. A separate state dict is then unnecessary, but both layouts are valid.
3. The state dict has 117 590 parameters. How many bytes of float32 weights is that, ignoring batch-norm statistics?
117 590 × 4 = 470 360 bytes, about 0.47 MB. Batch-norm running statistics add 2 560 bytes, giving 472 920 bytes in total.

Takeaways

  • Roles say what an asset is for; file names say nothing.
  • A valid model needs an asset with mlm:model and an mlm:artifact_type.
  • An entrypoint demands a code asset. Weights need an architecture to load into.
6.5

Hyper-parameters, size & hardware

The questionYour team has one GPU with 8 GB of memory and wants to run the model on a national mosaic. Will it fit? How many patches per batch? The record says mlm:memory_size: 50804568 and mlm:total_parameters: 117590. What do these numbers mean, where do they come from, and can you check them?

Intuition

Running a model costs memory in two places. The parameters are the model's knowledge: they are stored once, and every patch uses them. The activations are the intermediate feature maps: they are created for each patch and each batch element, and they are the bigger cost for images. A feature map of 16 channels at 256 × 256 takes 16 · 256 · 256 · 4 bytes = 4 MiB in float32, and a U-Net keeps several of them in flight.

So the planner needs two numbers. mlm:total_parameters counts the knowledge (a count of numbers, not bytes). mlm:memory_size is the working size in bytes on the accelerator, at the batch size the record suggests. The hyper-parameters (mlm:hyperparameters) explain how the knowledge was learned; they do not change the memory.

Build it up: counting the parameters

Every learnable tensor contributes its number of elements. A convolution with kernel k, c_in inputs and c_out outputs has k^2c_{in}c_{out} weights, plus c_out biases if it has them. Batch normalisation (BN) with c channels has 2c trainable numbers (scale γ and shift β) and 2c running statistics (mean and variance), which are buffers, not trainable.

Worked example — the first block, by hand

The first block maps 4 input bands to 16 channels with two 3 × 3 convolutions, each followed by BN. Convolutions have no bias here, because BN has its own shift.

Conv 4→16: 3\cdot3\cdot4\cdot16=576. BN(16): 2\cdot16=32. Conv 16→16: 3\cdot3\cdot16\cdot16=2304. BN(16): 32.

Block total: 576+32+2304+32=2944. The full model's blocks (computed with the same rule) are:

BlockParameters
encoder 1 (4→16, 256 px)2 944
encoder 2 (16→32, 128 px)13 952
bottleneck (32→64, 64 px)55 552
up 1 (transposed conv 64→32)8 224
decoder 1 (64→32, 128 px)27 776
up 2 (transposed conv 32→16)2 064
decoder 2 (32→16, 256 px)6 976
head (1×1 conv 16→6, with bias)102
total117 590

Matches mlm:total_parameters. The batch-norm running statistics add 640 buffer values. Each block's BN layers store 4 values per output channel, and the block output widths sum to 16 + 32 + 64 + 32 + 16 = 160, so 4 × 160 = 640. Buffers are not counted in mlm:total_parameters under the convention used here (the trainable-plus-frozen tensors that a framework lists as parameters).

Build it up: the memory size

We estimate the accelerator memory for inference as three parts: the weights and BN statistics (stored once), plus the largest pair of feature maps that must exist at the same time for one layer (input and output), multiplied by the batch size. Gradients and optimiser states are not needed for inference, so they are excluded. The spec defines the quantity as in-memory size during inference in bytes, and it does not fix a batch size; the record must therefore state which batch it used.

Worked example — 50 804 568 bytes

Weights and statistics: (117\,590+640)\cdot4=472\,920 bytes.

The largest layer, by input plus output size at batch 1, is the first convolution of decoder 2: input 32 × 256 × 256 (the upsampled 16 channels concatenated with the 16 skip channels) and output 16 × 256 × 256. That is (32+16)\cdot256^2=3\,145\,728 floats, or 12\,582\,912 bytes.

At the suggested batch of 4: 4\cdot12\,582\,912=50\,331\,648 bytes.

Total: 472\,920+50\,331\,648=50\,804\,568 bytes, the value in the record. In units: 50.80 MB (decimal) or 48.45 MiB (binary). The unit matters: a planner who reads "50.8" as gigabytes will overestimate by a factor of 1000.

A useful consequence: the activation term scales with the batch and with the patch area, but the weight term does not. Doubling the patch side quadruples the activation term; doubling the batch doubles it. The lab below lets you feel both.

Where this sits in the pipeline Model (sizing the job) and inference (choosing batch size). The numbers are written at publish time but read at run time to plan the workers.

The formal definition

P=\sum_{\text{tensors }t}\prod_d t_d,\qquad M_{\text{bytes}}=\underbrace{4\,(P+B)}_{\text{weights}}+\underbrace{s_{\text{bytes}}\cdot b\cdot\max_\ell\big(|x_\ell|+|y_\ell|\big)}_{\text{activations}}
Ptotal number of parameter values (trainable and non-trainable) for mlm:total_parameters
t_dthe size of tensor t along dimension d
Bnumber of BN running-statistic values (buffers)
s_bytesbytes per number: 4 for float32
bbatch size, mlm:batch_size_suggestion
x_ℓ, y_ℓinput and output sizes of layer ℓ, in numbers, for one sample

For a convolution block that maps c_in to c_out channels (two 3 × 3 convolutions and two BN layers), the count is 9c_{in}c_{out}+9c_{out}^2+4c_{out}. The lab adds the block terms of this family (base width w, input channels C, classes K); at w = 16, C = 4, K = 6 the sum is exactly 117 590.

Common traps
  • Bytes versus parameters. total_parameters counts numbers; memory_size counts bytes. A model with 117 590 parameters is about 0.47 MB of weights, not 117 590 bytes.
  • Forgetting the batch. Memory quoted for batch 1 will not fit a batch of 16 on a small GPU.
  • Mixing decimal and binary units. 50.8 MB is 48.45 MiB. Pick one and state it in the description.
  • Trusting an unmeasured claim. The value above is a calculation; the runtime adds framework overhead. Measure it on the target hardware before you commit a fleet to it (Lesson 6.9).
Where it shows up in AI
  • Foundation models publish parameter counts (in the hundreds of millions) to tell users whether a model fits a GPU at all.
  • Tiling jobs (Module 3, tiling-chipping) choose a patch size from the GPU memory left after the model is loaded.

Check yourself

1. What is the weight memory of a model with 117 590 float32 parameters and 640 BN statistics?
(117 590 + 640) × 4 = 472 920 bytes, about 0.47 MB.
2. The patch side doubles from 256 to 512 with the same batch. By what factor does the activation part grow?
By 4, since activations scale with the patch area (512² / 256² = 4). The weight part does not change.
3. A record says memory 50804568 with batch suggestion 4. Your GPU has 8 GB and you want batch 64. Estimate the activation memory and say whether it fits.
The activation term is 12 582 912 bytes per sample, so batch 64 needs 805 306 368 bytes (768 MiB) of activations, plus 472 920 bytes of weights: about 0.8 GB. It fits in 8 GB in this estimate, but the runtime adds overhead, so measure it before you rely on the figure.

Takeaways

  • total_parameters counts numbers; memory_size counts bytes at a stated batch size.
  • Weights are fixed; activations grow with batch and with patch area.
  • Units and batch are part of the claim. Write them down.
6.6

Tasks taxonomy

The questionThree models all "find things in satellite images". One labels whether a patch contains flooding. One outlines every building as its own polygon. One estimates tonnes of biomass per hectare. A user searching the catalogue for "flood mapping" must find the first and not the other two. What word should each record use in mlm:tasks, and why does the choice matter for search?

Intuition

A task is the shape of the answer. Ask the model a question and look at what comes back: one label for the whole picture, one label per pixel, one box per object, one number, a ranked list of similar places, or a new image. The task value in the record names that shape, using a small, shared vocabulary so that a search for one meaning finds every model that means it.

The vocabulary matters because people search with words. If one publisher writes segmentation and another writes semantic-segmentation, a search for the second misses the first. The task enumeration is the agreed list of words.

Build it up: the vocabulary, from simple to specific

  1. Labels for a whole input. classification (one label per input) and scene-classification (one label for a scene or patch image, the EO specialisation). "Is there flooding in this patch?" is a scene question.
  2. Labels for every pixel. segmentation is the general word. semantic-segmentation gives every pixel a class and does not separate objects of one class. instance-segmentation separates each object (each building gets its own mask). panoptic-segmentation combines both: countable objects as instances, and "stuff" such as water or grass as classes.
  3. Boxes around objects. detection and object-detection: each result is a bounding box with a class and a score.
  4. A number. regression: the output is a value (biomass, temperature, chlorophyll), not a class.
  5. Neighbours in embedding space. similarity-search: the model maps a patch to a vector, and the result is "places that look like this one" (Module 7).
  6. Creating images. generative, image-captioning, super-resolution (higher resolution from lower), and downscaling (the reverse, used for climate fields).

The spec says that other values are allowed but should be used sparingly. Prefer a value from this list, and if you must write a new one, explain it in the description.

Worked example — three questions, three values
Question the user asksShape of the answermlm:tasks value
Is there flooding in this 256-pixel patch?one label per patchscene-classification
Which pixels are water?one class per pixel, classes not separatedsemantic-segmentation
Where is each building footprint?one mask per buildinginstance-segmentation
How many tonnes of biomass per hectare?one number per pixel or patchregression

The flood model is the only one with scene-classification, so a search for that value finds it and not the building model. A model can list several tasks (a model that does both semantic and instance segmentation), and the output contract in mlm:output then gives the task for each output.

Where this sits in the pipeline Publish (the task is decided by the model's output) and discovery (search). It is not used by the runner, except to decide which post-processing applies.

The formal definition

\texttt{mlm:tasks}\in\mathcal{T}^{+},\qquad \mathcal{T}=\{\text{regression},\ \text{classification},\ \text{scene-classification},\ \text{detection},\ \text{object-detection},\ \text{segmentation},\ \text{semantic-segmentation},\ \text{instance-segmentation},\ \text{panoptic-segmentation},\ \text{similarity-search},\ \text{generative},\ \text{image-captioning},\ \text{super-resolution},\ \text{downscaling}\}
mlm:tasksan array with at least one value (it is required)
𝒯the enumerated task values of MLM v1.6.0 (the list above)
𝒯⁺non-empty arrays whose elements are all in 𝒯
Common traps
  • Calling everything "segmentation". A building model labelled segmentation cannot be told apart from a land-cover model in a search.
  • Confusing semantic and instance. Semantic gives one "building" class; instance gives each building. The output shapes differ.
  • Using classification for a dense map. A map has a class per pixel, which is segmentation.
  • Inventing a value. A misspelled value fails schema validation (Lesson 6.9), and a near-miss value is invisible to search.
Where it shows up in AI
  • Model zoos filter by task first: a user who wants building footprints wants instance or panoptic segmentation, and the same word appears in the catalogue record.
  • Benchmark suites for EO group their tasks this way (scene classification, semantic segmentation, object detection) because each has its own metric (Module 8).

Check yourself

1. A model outlines each separate building as its own polygon. Which task value is most precise?
instance-segmentation, because each object is separated. semantic-segmentation would merge adjacent buildings into one class region.
2. Why is mlm:tasks an array, and what must it contain?
A model may serve more than one task, so the array lists them. It is required and must contain at least one value, and every value must come from the enumeration.
3. A model outputs one biomass number per patch. Which task, and why not classification?
regression. The output is a continuous number, not one of a set of labels, and classification would imply discrete classes.

Takeaways

  • The task describes the shape of the answer: label per input, per pixel, per object, box, number, vector or image.
  • Use the agreed vocabulary; search depends on exact words.
  • Tasks are required and must be enumerated values.
6.7

Collections, summaries & derived models

The questionYour team has published eleven versions of one U-Net: a base model, country fine-tunes, a cropland specialist. A user opens the collection page and wants to know, at a glance, which tasks the family covers, how big the models are, and where each one came from. Should the collection repeat each item's full input contract? And how is a fine-tuned model linked to the model it started from?

Intuition

A collection is a shelf of items that belong together. A shelf label should say what is on the shelf, not describe every book. So the collection carries summaries: short, simple facts that hold across the items, such as the set of tasks or the range of sizes. The detailed contract (bands, shapes, class lists, hyper-parameters) stays on each item, because it differs from model to model and a summary would be wrong or meaningless.

Lineage is the second idea. A fine-tuned model is not a new model from nothing: it is derived from a base model. A link with the relation type derived_from records that, so a user can walk back to the ancestor and read its contract, licence and training data.

Build it up: what a summary can hold

Consider three models in one collection. Model A is our record (Lesson 6.2). Model B is a smaller illustrative model; Model C is a fine-tune of A.

Worked example — summarising three items
Itemmlm:tasksmlm:frameworkmlm:total_parametersmlm:memory_size (bytes)
A: unet-landcover-s2-demosemantic-segmentationpytorch117 59050 804 568
B: unet-tiny (illustrative)semantic-segmentationpytorch61 52227 262 976
C: unet-landcover-kenya-v2 (a fine-tune of A)semantic-segmentationpytorch117 59050 804 568

The collection summary is then: tasks = {semantic-segmentation}; framework = {pytorch}; total_parameters ranges from 61 522 to 117 590 (a range summary with minimum and maximum); memory_size ranges from 27 262 976 to 50 804 568 bytes.

The contract fields (mlm:input, mlm:output, mlm:hyperparameters) are not summarised. Model B takes different bands from A, so no single input summary would be true of the family, and the spec leaves these item-only fields out of collection summaries.

Build it up: lineage with derived_from

A link is an object in the Item's links array. For lineage the link relation is derived_from, and it points from the fine-tuned model to the base model:

{
  "rel": "derived_from",
  "href": "https://example.org/stac/models/unet-landcover-s2-demo-v1.json",
  "type": "application/json",
  "title": "Base model: unet-landcover-s2-demo"
}

Following these links forms a chain: C → A (and A has no link, so it is a root). For a larger family the links form a tree, and the lineage graph in the lab shows it. A reader who finds C can then check A's licence, training data and contract, without trusting C's own copy of them.

Where this sits in the pipeline Publish and monitor. Summaries and links are written when a model family is published and used to browse, to compare and to audit provenance over time.

The formal definition

S(\mathcal{C})=\Big\{\,f:\ f\in\mathcal{F}_{\text{simple}}\,\Big\}\quad\text{where}\quad \mathcal{F}_{\text{simple}}\cap\{\texttt{mlm:input},\texttt{mlm:output},\texttt{mlm:hyperparameters}\}=\varnothing,\qquad \text{lineage}:\ \texttt{rel}=\texttt{derived\_from}
𝒞a collection of model items
S(𝒞)the summaries of the collection
F_simplethe fields that may be summarised: simple values such as tasks, framework, sizes (a set of values or a min/max range)
∅the empty set: no excluded field may be summarised
relthe link relation; derived_from points from a derived model to its ancestor
Common traps
  • Summarising the input. A summary that says "bands: B02…B08" is false for a model that takes different bands. Keep contracts on the items.
  • Pointing the link the wrong way. The link is on the derived model and points to the base, not the reverse.
  • Copying the base model's metadata. A fine-tune must state its own parameter count, datetime and training data. The link says where it came from; it does not say what it is.
  • Trusting a summary as a fact about each item. A range says "somewhere in here", not "every item has this value".
Where it shows up in AI
  • Model hubs show "fine-tuned from" lines, which are derived_from links in another form.
  • Geospatial model families (one base encoder, many regional fine-tunes) are published exactly this way so that users can compare regions and trace weights back to the base release.

Check yourself

1. Can mlm:input appear in a collection summary?
No. Only mlm:name may appear on a collection among the item-only fields, and the input, output and hyper-parameters are left out of summaries. The contract stays on each item.
2. Using the example, what is the memory summary range for A, B and C?
From 27 262 976 (B) to 50 804 568 (A and C), in bytes.
3. Model C is fine-tuned from A. Which object carries the link, and what is its rel?
Model C's links array carries an object with rel = derived_from and an href pointing at A's Item.

Takeaways

  • Collections summarise simple facts; contracts stay on items.
  • Summaries are ranges or sets, and they describe the family, not each item exactly.
  • derived_from links point from a fine-tune to its base, which carries its own record.
6.8

Running inference from the record

The questionA new scene of 1000 × 1000 pixels arrives and you have only the Item of Lesson 6.2 and the URLs it lists. No documentation, no conversation with the publisher. Can a program run the model and produce a correct map? Which fields does it read, in what order, and where does each one take effect?

Intuition

An MLM record is written so that a machine can act on it. A reference runner is a short program that reads the record field by field, and each field tells it one thing to do: which bands to select, how to scale, how big a patch is, which asset to load, what the classes mean. Nothing is guessed. If a field is missing, the runner stops and says so, instead of running with a default that nobody chose.

Read the record as a recipe. The ingredients are the assets; the steps are the contract; the oven setting is the batch size and the memory figure from Lesson 6.5.

Build it up: the six steps

  1. Read the Item. Load the JSON; check stac_extensions contains the MLM schema; read mlm:input, mlm:output, mlm:batch_size_suggestion.
  2. Fetch the assets by role. Find the asset with mlm:model and load it (with its mlm:artifact_type). If the record has a code role with an entrypoint, import that code; if it has a weights asset, load it into the architecture.
  3. Select and normalise as stated. Pick the bands by name in the order of bands; apply value_scaling in order (scale by 0.0001, then clip to [0, 1]).
  4. Tile as stated. Cut the scene into patches of input.shape (256 × 256), with the stride the runner chooses; pad edge patches as resize_type says.
  5. Run. Send batches of mlm:batch_size_suggestion patches to the model, without gradients.
  6. Post-process as stated. Apply the output's argmax over the class axis, write invalid pixels as 255, and stitch the patches back using the stride and the overlap rule.

Build it up: the arithmetic of one run

Worked example — how many batches?

Scene 1000 × 1000 pixels, patch 256, stride 256: 4 patches per axis, so 16 patches (Lesson 6.3). Batch size 4 from mlm:batch_size_suggestion: 16/4=4 batches.

Memory per batch (Lesson 6.5): weights 472 920 bytes, plus the batch's activations 50 331 648 bytes, so about 50.8 MB, which matches mlm:memory_size. The 16 patches cost 4 runs of about 50 MB each. Running all 16 at once would need about 16 × 12.58 MB = 201 MB of activations, about four times as much, which is why batching exists.

Input bytes per patch are 1 MiB (4 × 256 × 256 × 4), so the scene's 16 input patches take 16 MiB of tensor storage, and the 16 output patches take 24 MiB (16 × 1.5 MiB).

Build it up: the reference runner

The runner below is a sketch that follows the record. It is written in Python with NumPy and PyTorch; it reads only what the record states, and it stops with an error when something it needs is missing. Read it next to the Item to see each line answer one field.

import json
import numpy as np
import torch

rec = json.load(open("item.json"))                 # 1. read the Item
props = rec["properties"]
assert "https://stac-extensions.github.io/mlm/v1.6.0/schema.json" in rec["stac_extensions"]
inp, out = props["mlm:input"][0], props["mlm:output"][0]
bands = [b if isinstance(b, str) else b["name"] for b in inp["bands"]]

batch = props["mlm:batch_size_suggestion"]

model_asset = next(a for a in rec["assets"].values()   # 2. fetch by role
                   if "mlm:model" in a.get("roles", []))
model = torch.load(download(model_asset["href"]), weights_only=False).eval()

def normalise(x, steps):                           # 3. scale as stated, in order
    for s in steps:
        if s["type"] == "scale":
            x = x * s["value"]
        elif s["type"] == "clip":
            x = np.clip(x, s["minimum"], s["maximum"])
        else:
            raise NotImplementedError(s["type"])   # never guess an unknown step
    return x

def patches(scene, p, stride, mode):              # 4. tile; pad edges when resize_type == "pad"
    ...                                            # yields (row, col, patch) with patch shape (C, p, p)

scene = read_bands(scene_path, bands)              # band order follows the record
results = []
for batch_items in chunks(patches(normalise(scene, inp["value_scaling"]), H, 256, inp["resize_type"]), batch):
    x = torch.as_tensor(np.stack([q for _, _, q in batch_items]), dtype=torch.float32)
    with torch.no_grad():                          # 5. run
        logits = model(x)                          # shape (N, 6, 256, 256)
    labels = logits.argmax(dim=1).numpy().astype("uint8")   # 6. post-process as stated
    results += [(r, c, lab) for (r, c, _), lab in zip(batch_items, labels)]
write_map(results, out_path)                       # stitch back, keep the grid, write a COG

The sketch leaves out tiling details, the stitching of overlaps and the file reading, which the runner must handle. The point is the order: each line answers one field of the record, and every value (band names, scaling, shape, batch) comes from the Item, not from the runner's own defaults.

Where this sits in the pipeline Acquire (read the record and assets), preprocess (normalise, tile), model and inference (run), post-process (argmax, stitch) and publish (write the map). The runner stores the output raster; the record is never changed by it.

The formal definition

\hat Y=\pi\Big(f_{\theta}\big(\,\mathcal{B}_{b}\big(\,\tau_p\big(\,\sigma(X;\,\texttt{value\_scaling})\,\big)\big)\big)\Big)
Xthe scene, bands selected by name from mlm:input.bands
σthe scaling steps, applied in order
τ_ptiling into patches of side p (256), with padding as resize_type says
𝓑_bgrouping patches into batches of size b (mlm:batch_size_suggestion)
f_θthe model, with weights θ loaded from its assets
πpost-processing (argmax, invalid pixels set to 255, stitching)
Common traps
  • Defaults that nobody chose. A runner that fills in ImageNet means or a band order "because it usually is" will run without error and be wrong.
  • Ignoring the -1 batch axis. The shape field is a contract: batch is free, the other axes are fixed.
  • Stitching without the grid. A patch placed at the wrong offset shifts every label beneath it.
  • Running with gradients. Inference should not store gradients; it wastes memory that the record's figure does not include.
Where it shows up in AI
  • Automated inference services use exactly this path: the record configures the job, and the operator does not write model-specific code.
  • Open model runners for EO use the same six steps, so one tool can run many models.

Check yourself

1. A 1000 × 1000 scene, patch 256 and stride 256, batch 4. How many model runs?
16 patches, in batches of 4: 4 runs.
2. The record lists bands ["B02","B03","B04","B08"] and the stack has them in another order. What should the runner do?
Select the bands by name, in the order the record lists them. Position in the stack is not the identity of a band.
3. A record has a value_scaling step of type "processing" that the runner does not support. What is right?
Stop with an explicit error. Guessing the step would produce values the model was not trained on.

Takeaways

  • The record is a recipe: assets by role, bands by name, scaling in order, tiles of the stated shape, a stated batch.
  • A runner stops on what it does not understand instead of guessing.
  • Batch and memory come from the record; the runner's job is to respect them.
6.9

Validating and trusting a model record

The questionYour record says 117 590 parameters, 50 804 568 bytes of memory, a 256 × 256 input and six classes. Before a planner buys GPU hours on the strength of those numbers, what must be checked, by whom, and what would make you refuse the record? And if the model's accuracy is in the record, what would make that number honest?

Intuition

A record makes claims, and a claim can be checked in two ways. A schema check asks whether the record is well formed: required fields present, values of the right type, placed on the right level. A claim check asks whether the record is true: does the artifact really have that many parameters, does it really accept that input, does it really use that memory? The first is cheap and automatic. The second needs the artifact and a computer.

Treat a record like a measurement report. A report with the right layout but a wrong number is worse than a report with a missing field, because it looks finished.

Build it up: the checklist

  1. Schema. Validate the Item against the STAC core schema and the MLM v1.6.0 schema. Check the required fields (Lesson 6.2), the enumerated values (tasks, accelerator, resize, value-scaling types), and the placement of item-only fields.
  2. Assets. Every asset's href resolves; the mlm:model asset has mlm:artifact_type; a code role exists if an entrypoint is declared (Lesson 6.4).
  3. Parameters. Load the weights and count the parameters. Compare with mlm:total_parameters; they must be equal under the same counting convention (Lesson 6.5).
  4. Shapes. Run one dummy input of the declared shape, e.g. (1, 4, 256, 256), and check the output is (1, 6, 256, 256). This tests mlm:input and mlm:output together.
  5. Memory. Run a batch of the suggested size and measure the peak accelerator memory. Compare with mlm:memory_size. A small excess is normal (framework overhead); a large gap means the record is wrong or the runtime is unexpected.
  6. Band order. Run on a sample with known labels and check the predicted map. Scrambled bands give confident nonsense, so this check is the one that catches silent errors.
  7. Accuracy. If the record reports accuracy, it must name the test data and the split. A random pixel split leaks spatially (Module 3, spatial-splits), and an accuracy from leaked data is not a fact about new places. Report per-class scores, not only one overall number, because a model can be 90 % accurate by predicting the majority class.
Worked example — checking the claims of our record

Parameters: the record says 117 590. The architecture count (Lesson 6.5) gives 117 590. \checkmark Equal.

Shape: (1,4,256,256) in, (1,6,256,256) out. \checkmark Matches the contract.

Memory: the record claims 50 804 568 bytes at batch 4. If a measured peak is 55 000 000 bytes, the gap is (55\,000\,000-50\,804\,568)/50\,804\,568\approx 8.3\%. That is within what framework overhead usually adds, so the claim stands, and the record should be updated with the measured value and the method. If the measured peak were 100 000 000 bytes, the gap would be 97 %, and the record would be refused until the cause was found.

Band order: a sample whose B08 is large (vegetation) must be predicted as trees or grass. If the model says water, the bands were probably swapped, and the record's band list must be fixed before anything else.

The spec does not define a tolerance for memory, so the threshold is a team decision. Write it in the validation report so that a later reader knows what was accepted.

Accuracy in the record. MLM can describe a model's evaluation, but the claim is only as good as the test data. Report the test region, the date, the split method and per-class scores. An overall accuracy with no split is not evidence for new places.

The formal definition

\text{trusted}(R)\iff\text{schema}(R)\wedge\bigwedge_{c\in\mathcal{C}(R)}\big|\,\text{claim}_c-\text{measure}_c\,\big|\le\tau_c
schema(R)the Item validates against STAC and MLM v1.6.0
𝒞(R)the set of checkable claims: parameters, shapes, memory, band order
claim_c, measure_cthe value written in the record and the value measured on the artifact
τ_cthe tolerance for claim c; exact for counts and shapes (τ = 0), a stated threshold for memory
Common traps
  • Passing the schema and stopping. A valid record can describe the wrong model.
  • Measuring with the wrong convention. Counting buffers as parameters gives a different number from the record's convention.
  • One overall accuracy. It hides classes the model fails on.
  • Testing on the training area. Leakage makes every metric look better than it is.
Where it shows up in AI
  • Model governance in public agencies asks for exactly this report before a model is used for decisions such as land-use enforcement.
  • Model cards on public hubs follow the same logic: state the claim, the data, the split and the limits.

Check yourself

1. Which two kinds of check does validation need, and which one catches a swapped band order?
A schema check (is the record well formed?) and a claim check (is it true?). Only the claim check, run on a sample with known labels, catches a swapped band order, because the schema cannot see the data.
2. Measured memory is 8 % above the claim. Refuse, accept or investigate?
It depends on the team's stated tolerance. An 8 % gap is typical overhead and is usually accepted with the measured value and method written into the record. A gap of several times the claim should be investigated before anything is trusted.
3. A model reports 92 % overall accuracy, tested on random pixels of the training scenes. What is wrong with that claim?
The test pixels are spatially correlated with training pixels, so the split leaks and the number is optimistic. Report a spatial split, per-class scores, and the test region and date.

Takeaways

  • A record is trusted only after its schema and its claims are checked against the artifact.
  • Counts and shapes are checked exactly; memory against a stated tolerance; band order on real samples.
  • An accuracy claim is honest only with its test data, split and per-class results.
